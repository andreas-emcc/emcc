| `@emc2/plugin-sdk/build` | `emc2Plugin({ manifest, importMap })` for a plugin's `vite.config.ts`: shared libraries external, checked against the shell's import map (`web/shell/dist/importmap.json`), and `web.shared` written into the built `plugin.json` with the libraries the plugin imports. Never in the import map itself, nor is `/testing`. **SDK 1.9.0:** `manifestProblem(manifest)`, the manifest guard's check against the data model's plugin manifest schema (the SDK package's `schemas/`, else the repository's `model/schemas/`) |

**Dependencies** (pinned, ADR-0016): `ajv` 8.20.0 and `ajv-formats` 3.0.1 (both MIT), used only by `/build`'s `manifestProblem`, at build and test time in Node. Never in the browser: nothing the shell or a plugin's web part bundles imports `/build`. Everything else is a peer dependency the shell shares.

A plugin web part:

```ts
import { definePlugin, SYMBOLS } from '@emc2/plugin-sdk';

export default definePlugin({
  async activate(ctx) {
    const symbols = await ctx.services.get(SYMBOLS);
    ctx.ui.addPanel({ id: 'symbols', title: 'Symbols', defaultPane: 'right', component: SymbolPanel });   // SDK 1.1.0
  },
});
```

Commands, at the repository root (the npm workspace root, CR-0006): `npm test -w @emc2/plugin-sdk` (type check, then Vitest). The tests read `model/examples/` to check the model types and the shared `sdkVersion` cases.

The SDK owns the list of shared libraries (`SHARED_LIBRARIES`). They are also its peer dependencies, with the same exact versions; a test keeps the two in step.

The symbol type is named `MilSymbol`, to avoid a clash with JavaScript's global `Symbol`.
