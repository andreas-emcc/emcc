# web/

The emc2 web client. Owner: CDA (except `plugin-sdk/`, owned by the PDA). **The npm workspace root is the repository root** (CR-0006): `package.json` and `package-lock.json` at the root list the workspaces `web/shell`, `web/plugin-sdk` and `plugins/*/web`, with one lock file for all of them; every version is pinned exactly. `node_modules` is at the root too, so plugin web parts find their packages.

| Workspace | What |
|---|---|
| `web/shell/` | The web client shell (below): layout, plugin loader, live picture connection, and the shared libraries for plugins |
| `web/plugin-sdk/` | The web plugin SDK, `@emc2/plugin-sdk` (PDA) |
| `plugins/*/web` | The web part of every plugin, found by the glob. The package must be named `@emc2/plugin-<plugin-id>`. Plugins never edit the root `package.json` (CLAUDE.md section 3) |

So plugins compile and test against exactly the versions the shell ships (spike S4, recommendation 15), and `npm test --workspaces` runs their tests too.

**Product name** (T-134; CLAUDE.md section 4, owner 2026-11-04): users see **emcc**: the browser tab's title, the logo's and the splash's labels, the setups' "a newer version of emcc" messages. Internal names stay emc2 (`@emc2/…`, `x-emc2`, `emc2:workspace-switch`, settings keys). The logo's letters are the owner's artwork (`assets/logo.svg`), unchanged.

**The lock file is generated: never edit or merge `package-lock.json` by hand** (CLAUDE.md section 6). After merging `main`, run `npm install` at the repository root and commit the regenerated lock file. The MCA merges branches that change it one at a time.

## The shell (T-014)

Overview 3.2 and 4.11, the SDK v0 and v1 designs (`docs/plugins/sdk-v0.md`, `docs/plugins/sdk-v1.md`), spike S4.

- **Layout:** the **top bar** (ADR-0031 point 1, T-039 part 4, SDK 1.1.0 part 5; `ui/TopBar.tsx`, `ui/tabs.ts`): the **logo** in the upper left corner (`ui/Logo.tsx`, `assets/logo.svg`, the owner's SVG; owner, 2026-10-29), a button that opens the splash: a pane about 400 px square in the middle of the window where the logo draws itself, rebuilt from the owner's splash with the logo's own outlines instead of a web font (ADR-0030); it closes after 10 s, at once on any click inside or outside it, and on Escape; then the view tabs View, the workspaces (below), Settings and Monitor, Settings and Monitor only for a user with `settings.admin` (the server checks it again); on the right the plugins' items (`ctx.ui.addTopBarItem`, by `order`, each in its own error boundary; an item's box is at most 12 rem wide but nothing is clipped, so that a menu below it stays visible: an item must fit in its 12 rem itself), the **setups control** (below), the **clock** (`ui/Clock.tsx`, `ui/dtg.ts`: a date-time group, UTC by default, e.g. `161045Z OCT 26`; a click switches to local time with the military zone letter of a whole-hour offset, `J` otherwise, e.g. `161245B OCT 26`; the full time and offset on hover; it moves on at each full minute; owner, 2026-10-16), then who is logged in, with a "Log out" button ("Login ended", without the button, once the login session has ended; the Status panel then offers "Log in again") (`POST /logout` with `fetch`, then to the IAM's logout page the server names; a form post would be blocked by the CSP's `form-action 'self'`), or a "No login" mark in the no-login mode (ADR-0022, from `GET /api/config`, also on the dev server). The `?continue` that the login's return adds is dropped from the address at start (`main.tsx`). The tab, and in Settings the entry, is kept in the address (`#settings`, `#settings/data-types`, `#settings/plugin/<id>`, `#monitor`); an address of M1's plugin tabs (`#plugin/<id>`) opens that plugin's entry and is replaced by the new one. View stays laid out under the other views, hidden from sight and focus (`aria-hidden`, `inert`), so the map keeps its size and the plugins keep running. View is the **workspace** (ADR-0031 point 4, SDK 1.1.0 part 5; `ui/Workspace.tsx`, `ui/layout.ts`): the Map Pane in the middle (the map view plugin's element, and the plugins' overlays in its four corners), the left and right panes beside it at full height, the bottom pane under the map; the panes are docked, and a pane without panels is not shown. Each pane resizes with its handle (a WAI-ARIA window splitter: drag it with the main button, or the arrow keys by 16 px, Home and End; a cancelled pointer ends the drag) and collapses to a strip. A pane is at least 160 px, at most 60 % of the window, and the side panes leave the map 320 px (in a window narrower than about 640 px each side pane still keeps its 160 px, so the map gets less): the sizes shown are fitted to the window as it is now (`fittedSizes`; the right pane gives way first), while the layout keeps the user's sizes for when the window grows again. The left and right panes stack their panels, each collapsing on its own and starting collapsed until the user expands it (T-153; a setup saved before then opens with every panel collapsed, once; owner, 2026-11-10); the bottom pane shows one at a time, with tabs (arrow keys, Home and End). Every panel moves to the other panes, and up and down (bottom: back and forward) within its pane (owner, 2026-10-16). A hidden panel (collapsed, in a collapsed pane, behind another tab) stays mounted and keeps its state; a move to another pane, or a workspace switch, mounts it again. Default sizes from `looks.md` (compact): 248, 288 and 170 px. The layout is plain data in the store (which pane holds each panel, the user's order, sizes, what is collapsed, the bottom tab), which the setups save and restore as it is (`layoutFromJson` reads it back, keeping panels of plugins that do not run). The right pane keeps the name "Control Pane". A panel's `icon` shows before its title, on its head and on its bottom tab; a title too long for its pane ends in "…" and shows in full on hover (owner, 2026-10-21; in a pane at its 160 px minimum the move buttons leave little more than its first letter). Panel ids (from `addPanel` and `addControlPanel` alike) and top bar item ids are unique within a plugin while registered: a second one with the same id is a `TypeError`. The shell's own **Status panel** (`ui/StatusPanel.tsx`, `ui/status.ts`; owner, 2026-10-16) holds the server and connection status and the plugin list with each plugin's server and web status; it starts at the bottom of the right pane and moves like any panel, and while the live picture is not connected the Map Pane says so too, in a live region that stays on the page, with "Log in again" once the login has ended and "Reload" for a server of another version. Notifications at the bottom left. Every plugin panel, top bar item and overlay renders in its own error boundary.
- **Workspaces** (ADR-0039, SDK 1.2.0 part 5, T-080; owner, 2026-10-27; `workspaces/switch.ts`, `ui/tabs.ts`):
  - **Tabs:** View, then each workspace the user may see (`/api/config`'s `workspaces`, by `order`), for every user, then Settings and Monitor; addressed `#workspace/<id>`, and a page opens on the workspace its address names, before the plugins start. One workspace is shown at a time (`ctx.workspace`, `ctx.workspaces`, frozen). Panels, overlays and actions appear only in their `workspaces` (`appearsIn`; without a list View only; top bar items everywhere, and from SDK 1.6.0 (T-152) an item with `workspaces` only in those, by `topBarItemAppearsIn`, and on the Settings and Monitor tabs only the items of every workspace); each workspace has its own pane layout. A switch unmounts the old workspace's panels and overlays and mounts the new one's, also a panel or overlay that is in both (`mountKey`; SDK `CurrentWorkspace` step 1, the briefs' rule 3; owner, 2026-10-28): its React state starts afresh, and the plugin restores it from its setup share and the fresh snapshot.
  - **A switch**, in the SDK's order (`CurrentWorkspace`): the setup of the workspace left is kept; the new panels and layout are rendered at once (`flushSync`); **the map view's moment**: the shell dispatches `emc2:workspace-switch` (`detail.workspace`, the new id) on the element it gave `MapViewMount.mount`, synchronously, for map-view-2d to end interactions and clear its fade lists and the selection (an agreement between the shell and the map view, not an SDK member); the subscriptions without `workspaces` subscribe again and the switch waits for their fresh snapshots, at most 5 s (a closed channel or a lost connection ends the wait); the plugins' shares of its setup are restored (none on a first visit); then `onChange`. A newer switch ends an older one's waiting. Limits: the server gives a subscription id at most one snapshot per 2 s of the workspaces of its last snapshot; a switch asks for other workspaces, also back and forth, and is answered at once (within the session's 32 snapshots per 2 s); the protocol cannot tell an older snapshot still on its way from the new one, which the next one corrects; while disconnected, the panels keep the old workspace's objects until the reconnect's snapshots (the live notice says so).
  - **Live:** the shared whole-picture and layers-and-counts channels are kept per set of workspaces (`all` and `counts` follow the one shown); a subscription's `workspaces` must be 1 to 64 ids or `'*'`. A channel's batches may skip the sequence numbers of other workspaces' changes.
  - **Setups:** View keeps `setup.current` and `setup.n.<id>`; another workspace has `setup.w.<id>.current` and `setup.w.<id>.n.<id>`, with its layout and the plugins' shares, at most 50 named each; the look and the clock are View's, the same everywhere. While a switch has not restored the new workspace's shares, nothing is saved from the plugins for it. When the page closes, `keepalive` is used while the browser's 64 KiB budget lasts for all workspaces together. The server holds at most 200 of a user's `core` documents: with four or more workspaces full of named setups, a save is refused and says so.
  - **The shared Delete** is one action per workspace, with its edit permission, and deletes only objects in a layer of the workspace it was asked in (others are named, "not in <workspace>"). **Settings › Layers** groups the layers by workspace, each needing its edit permission; `KnownLayers` follows every workspace the user may see (`'*'`), not the one shown (F4).
- **Shared libraries and import map** (`build/vendor.ts`): `vite build` first builds every module of the libraries in the SDK's `SHARED_LIBRARIES` (React, react-dom, OpenLayers, milsymbol, proj4, Lucide, the SDK) into `dist/assets/vendor/` with content-hashed names, and writes `dist/importmap.json`. Then it builds the shell with those libraries external, so shell and plugins share one instance of each, and inlines the import map into `index.html`; the server allows it by its hash. The build fails if an installed library, or a dependency in `web/shell/package.json`, has another version than the SDK's list. OpenLayers is one chunk; React gets generated ES module wrappers. Shared React modules: `react`, `react/jsx-runtime`, `react-dom`, `react-dom/client`.
- **Lucide** (`lucide-react` 1.49.0, CR-0015): all of it, as one vendor module (754 593 bytes, 184 871 gzipped; owner, 2026-10-15: the whole set, not a curated one), so a plugin imports any icon by name. A test checks that every library of `SHARED_LIBRARIES` has its entry in the vendor build.
- **Setups** (ADR-0031 point 5, SDK 1.1.0 part 7; `setups/setups.ts`, `setups/SetupsControl.tsx`; owner, 2026-10-16): the user's arrangement, as the user's own documents under `core` (`/api/user-documents/core/...`, ADR-0027), so that it follows the user to another browser. A setup is one document: a format version, the shell's share (the pane layout, the clock choice and the look choice: `shell.look` = `{ look: default | night-watch | chart-room | signal, scheme: system | light | dark, density: look | compact | comfortable }`; a pane's `size` is null until the user resizes it) and each plugin's share by plugin id (`ctx.setup.register({ save, restore })`, one per plugin, a second replaces the first; a share is plain JSON of at most 64 KiB, else it is not saved and the plugin's status says so, as when its `save` or `restore` throws). **Remembered:** `setup.current` is read at start (`boot.tsx`, in parallel with the plugin list), only if the list of the user's `core` documents names it (the server's 404 for a missing one would be an error in the browser's console, which the ITA counts); the shell's share applies at once, each plugin's after its `activate` has finished, never while it starts; a plugin's share is not saved before it got its remembered one, so its defaults never replace it. Then it is saved as the user works (the store's layout and clock, `ctx.setup.changed()`), at most once a second and only when it changed (what was read at start is not written back), and once more when the page is hidden or closed: with `keepalive` up to 60 KiB (the browser takes 64 KiB in all), a larger setup as a plain call, which a closing page may cut off; it counts as saved only once the server has it, and if the page lives on it is saved again. "Log out" first saves a change not saved yet (after a save under way, at most 2 s), then nothing more, so that no save goes out after the session has ended (`Setups.finish`; ITA, 2026-10-22). Shares of plugins that do not run in this session are kept. A plugin gets its own copy of its share. If `setup.current` cannot be read, nothing is remembered in that session, so a good setup is never overwritten with the default; the Status panel and a warning say so (a named setup restored then is applied, but does not become the remembered one). A setup of a newer format is left alone the same way; a damaged one is replaced. **Named:** each is a document `setup.n.<uuid>` with its name inside (no index document); at most 50; a name is 1 to 60 characters, unique regardless of case. The setups control in the top bar, before the clock, lists them by name (read once, when it is first opened), restores one at a click without asking (it then becomes the remembered setup), saves the current setup under a name (an existing name asks whether to replace it, keeping its document), and deletes one after asking. A plugin still starting when a named setup is picked gets the named share once it has started. **Sizes:** each share is at most 64 KiB, but several large ones can make a setup larger than the server's 256 KiB per document, or 50 named setups more than its 4 MiB per user; the server then refuses the write, and the shell says the setup could not be saved. **Not yet in a setup:** the look, light or dark, and density (ADR-0034) join the shell's share with T-052; the layers' visibility, map type, centre, zoom and dim level are the map view's share (`map-view-2d` function 20).
- **Actions and the menu** (ADR-0032, SDK 1.1.0 part 8; `actions/`; owner, 2026-10-16): `ctx.actions.addObjectAction` and `addMapAction` add to the shell's lists in the plugin's name (`registry.ts`: ids unique within a plugin, the fields checked; a fenced plugin's actions go). `openMenu(at, target)` opens the shell's menu at the point, kept inside the window (`menu.ts`, `ActionMenu.tsx`): for `objects` the object actions that apply to every one of them, by the SDK's own rule (`applicableObjectActions`: scope, one or several, the user's permission) in menu order with separators between groups; for `position` the map actions; for `choose` first a list of the overlapping objects (the name from its properties, else its data type's name, its layer, its symbol drawn small), and after a choice the shell sets the map's selection to that object and shows its actions; one object left goes straight to its actions. The objects come from the server (`get-objects`, at most 1 000; the shell keeps no objects of its own); ones gone meanwhile are left out, and when none is left the menu says so ("These objects no longer exist."). "No actions" in grey when none apply. A WAI-ARIA menu in the browser's top layer (`popover="manual"`, as the SDK's popovers): the focus on the first item, Up, Down (round), Home, End, Enter or Space; Escape, Tab and a press outside close it, and the focus goes back (Tab then moves on from there); when the focus leaves it otherwise, it closes and the focus stays where it went. A handler that throws or rejects, or an `appliesTo.test` that throws, is logged, shown as an error notification and makes its plugin DEGRADED; the plugin keeps running, and an action whose test threw is not offered in that menu. Each registration counts on its own, so a failure is always named after the plugin that registered the action. The layers' names come from the shared layers-and-counts channel, subscribed when a choose list first needs them. **The shared Delete** (`deletion.ts`, `DeleteQuestion.tsx`, `deleteKey.ts`): the shell's own object action (`core-shell`, group `delete`, several objects, `objects.edit`) and the Delete key on the map's selection (on a Mac also Backspace; only in the View tab, outside text fields, without Ctrl, Alt or Cmd, with no menu or dialog open, with `objects.edit`, and not when a key listener before it took the key with `preventDefault`). Delete is listened for on the document from the shell's start, so before the plugins' listeners there, and it takes the key; Backspace on the window, after them, so that map-view-2d's Backspace while drawing (remove the last point) does not delete too. It always asks first ("Delete 3 objects? This cannot be undone."), then sends one change request per object (`changeRequests.deleteObject`, `source.plugin` `core-shell`) in the shell's batches (`batch.ts`, shared with the Layers entry's raise): at most 50 waiting at a time over all of them (the session may have 100; the plugins keep the rest); a request refused with `INTERNAL_ERROR` (the session's queue was full, or the object store failed; both may be sent again) is sent again twice, a second apart. A sticky notice counts up ("Deleting objects: 340 of 1,000") and ends with "Deleted N objects." (it goes like any info), or with how many could not be deleted and why, the first five by name (it stays). An object in a locked layer is refused by the server (`LAYER_LOCKED`, ADR-0042) and named with "its layer is locked". An object already gone, or `ENTITY_NOT_FOUND`, counts as deleted; no answer counts as not deleted ("it may have been deleted"). One Delete at a time. **Move to layer… and Copy to layer…** (ADR-0053, T-155; `layerMoves.ts`, `LayerMoveQuestion.tsx`; owner Q1 and A1 to A5, 2026-11-10): two more of the shell's own object actions per workspace (group `layer`, between edit and Delete; several objects; the workspace's edit permission, `objects.edit` in View). Each asks for a layer in a dialog: the workspace's layers that are not locked, the top one first, nothing chosen until one is picked. A move sends one update per object with the new `layerId` and the complete core content (the id, relations and extensions stay); an object in that layer already is skipped and counted. A copy sends one create per object with a new id: the original's content, data type, field sets, relations, namespaces and name, but `dataSource` `manual`, no `time.observed` or `time.expires`, and never the `externalRef`, so it does not fade or join the original's track. No confirmation; not atomic. Objects in another workspace's layer are named "not in <workspace>". In the shell's batches, with one notice counting up and ending with the outcome ("Moved 8 of 10 objects to Alpha. 2 could not be moved: …"), which stays when any failed. One move or copy at a time. Notifications: `store.notify` returns an id, `updateNotification` changes one in place (one dismissed comes back), and `sticky` keeps info until it is updated or dismissed.
- **The time control** (SDK 1.4.0, ADR-0045 point 3; the owner's design, 2026-11-06; `time/`): beside the clock, only while a running plugin declares `temporal` (`/api/plugins`' `capabilities`). Its button shows the set time (Now or a date-time group), then the interval when it is on (accented when not now) and opens a slider with three markers: the set time and an interval's start and stop. Under it the date picker of the slider's start (left), Now, the Interval toggle and the picker of its end (right). The user's time has both parts at once (CR-0032, owner JA): the set time, always active and drawn over the interval's band, and the interval while the toggle is on (its markers greyed while it is off); Now resets both, the set time following the clock. Under each marker its time, with the date when the slider covers several days; times as the clock shows them (UTC or local). A time goes out when a marker is let go, at each arrow key (Shift: an hour; Page Up and Down, Home, End), at Now, the toggle and a picker; to the minute. Zoom (`choice.ts`): the interval's markers within 10 % of the scale make it 4 times their span around them; a marker held in the outer 3 % grows the scale 1.5 times every half second away from that end; the pickers follow; 10 minutes to 10 years. The first opening shows now ± 12 h, later ones keep the last scale; nothing is saved (point 2). The page's time goes to the server in the live picture (`time`, after each `welcome` when not now) and to each temporal web part (`time/temporal.ts`): `timeChanged` once after its `activate` and at each change; one that throws is DEGRADED. Requests to `/api/plugins/…` carry `X-Emc2-Session` with the live session's id (`main.tsx` wraps the page's `fetch`; owner, 2026-11-06), so that a temporal server part's endpoints get the page's time.
- **Display settings** (SDK 1.4.0 part 5; ADR-0046, ADR-0052; owner, 2026-11-07; `display/`): `ctx.display` for every plugin, read only, the same in every workspace (`display/state.ts`): `resolveDisplay` of the user's choices and the admin's defaults from `GET /api/display` with the loaded relation kinds. The **Display settings** icon (`DisplayControl.tsx`) is the shell's Map Pane overlay at the top right, order 20 (after Coordinates), in every workspace, framed as `map-view-2d`'s map settings icon; it opens a window in its place in the corner, growing to the left over the map as the map settings window does (T-162; owner, 2026-11-10), with Symbols (the size and the speed vector as sliders, the speed vector in the SDK's steps from Off and 5 s to 30 min (SDK 1.5.0 part 3, T-164): a change saves `speedVectorSeconds` and drops 1.4.0's stored `speedVectorMinutes`, which are shown as their nearest step; the labels as check boxes in `LABEL_IDS` order), Relations (a check box per loaded kind; none without kinds) and "Use defaults" (`PUT {}`). A change applies at once; a slider saves on release (pointer or key let go, or the focus leaving), everything else at once, with `PUT /api/display` of the user's whole choices, keeping switches of kinds that are not loaded (the ACA's R5). While a change is held or being saved, a read's answer is set aside and read again after; a refused save says why and shows what is stored. **Settings › Display** (`ui/settings/DisplayEntry.tsx`, after General): the admin's defaults, with the same controls, Save (`PUT /api/settings/display`) and "Built-in defaults"; every open browser gets them at once.
- **Settings › Labeling** (T-170 rounds 3 and 3b; owner, 2026-11-10; `ui/settings/labeling/`), after Layers: the premade security labels, one card per policy of `labelDefinitions` in `GET /api/config` (then any stored policy the definitions no longer have, with a warning), spaced and coloured as round 2's pictures. Its left column has the classifications of each of the policy's sections (its classification sets, named when there are several), highest first, each with its colour's swatch, and the Releasable To list (add a value with nation suggestions; click one to rename it everywhere, or remove it when no label uses it); its right column the labels by section, then by classification, highest first, then those whose classification the definitions no longer have (grey). A label shows the policy and classification on the classification's colour, then its Releasable To part; its accessible name is the whole text. A label is edited below its group (classification, Releasable To toggles, a live preview) and deleted after a question. Duplicates are refused, ignoring case and the order of values. Every change is kept as the draft `labeling` until the entry's one Save (`PUT /api/settings/labeling` with everything), so the entry is marked unsaved and leaving asks first; the live `labeling` notice reads them again, and open edits get "Someone else saved". The label text follows `labelFormat` in `GET /api/config` (the server's `emc2.labeling.*`). Connected to nothing in M6: every label is cosmetic.
- **Looks** (ADR-0034, T-052; owner, 2026-10-17): every user chooses in the top bar's **Look** control (`ui/LookControl.tsx`, before the setups control) the look (the installation's default, or Night Watch, Chart Room, Signal), light or dark (as the computer is, light, dark) and the density (the look's default, compact, comfortable); each applies at once and is part of the user's setup. Before the setup is read the page has the installation's default, light or dark as the computer is. - **The shell's CSS** (T-199; owner, 2026-11-13): `shell/src/shell.css` is the layout and structure (the CDA's): display, flex and grid, positions, sizes, overflow, stacking. `shell/src/shell-look.css` is the look (the UXA's, `agents/uxa.md`): colours, backgrounds, borders and radii, shadows, outlines, type, spacing (padding, margin, gap), cursors, opacity and the animations. `main.tsx` loads `tokens.css` (UXA), then `shell.css` and right after it `shell-look.css`. A new property goes in that test's list first.
- **Panels scroll inside themselves** (T-203 part A, findings P4): in a side pane the open panels share the height equally, each at most its content's, never below its head; each panel's body scrolls, the pane only when even the heads do not fit. - **Settings, one Save per surface** (T-203 part C, findings S1, S5): a settings form, General, Display and Labeling end in a `SaveFoot` (the SDK's `PanelFoot`), pinned to the page's bottom while it scrolls: the count of unsaved changes on the left (`changedValues`: each differing value, a list item or property only one side has counts one), Discard and Save on the right, an entry's own action ("Use defaults", "Built-in defaults") before them. Data types and Layers keep their rows until part D.
- **Settings › Layers** (ADR-0031 point 3, SDK 1.1.0 part 9; `layers/`; owner, 2026-10-17): each layer, the top one first, with its label and number of objects (`known.ts`: the shared layers-and-counts channel, also for the menu's layer names). For an admin with `layers.edit` a layer whose policy has an order of classifications (`classificationOrders` in `GET /api/config`, the server's `emc2.classifications.order.<policy>`; `classification.ts`) gets the classification to change it to and "Also raise objects below it" (needs `objects.edit`); a user with `objects.edit` only gets "Raise objects below <the layer's classification>" (owner, 2026-10-17). Apply asks once, saying exactly what happens; when the layer has changed by the time the admin says yes (renamed, reordered, its label changed, deleted), nothing is sent and the notice says so. The object queries (`get-objects`, `query-layer`) go over the same connection with a `queryId` (UUID v7); each resolves with its answer (the `sequenceNo` stays in the shell) or rejects with `ObjectQueryError`: the server's `query-failed` with its message, a lost connection, no connection, or no answer within 15 s.
- **Login session** (ADR-0022): with login the shell calls `GET /api/session` every minute, which keeps the server's session alive and renews the login. When the login has ended (the live picture closes with `4401`, or `/api/session` or the start answers `401`), the live picture stops for good, waiting change requests end as unknown, and the notice over the map offers "Log in again" (a reload, which goes through the IAM's login page; the Status panel says why).
- **Plugin status in this browser:** the worse of what the plugin reports (`ctx.status.set`) and what the shell saw (a failed panel, overlay, listener or style sheet). It is never sent to the server.
- **Dev server** (`npm run dev -w @emc2/shell`): proxies `/api` and the live picture to the server on port 8080, with the server's own `Host` and `Origin`. It does **not** load plugin web parts, because Vite bundles its own React for the shell, which plugins cannot share; it says so on the page. To run plugins, build (`node tools/build.mjs`) and start the server (`node tools/start.mjs`).

## Commands (at the repository root)

| Command | What |
|---|---|
| `npm install` | Installs all workspaces |
| `npm run build --workspaces --if-present` | Type-checks and builds `web/shell/dist/` (served by the server, with `importmap.json` for plugin builds), then the plugins' web parts |
| `npm test --workspaces` | ESLint, then Vitest, in every workspace |
| `npm run dev -w @emc2/shell` | Vite dev server with hot reload for the shell itself (no plugin web parts); `/api` is proxied to the server on port 8080 |

Nothing is loaded from the internet at runtime (ADR-0030): no CDNs, no remote fonts.
