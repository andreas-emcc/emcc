# server/

Maven multi-module build of the emc2 server. Owner: CDA (except `plugin-sdk/`, owned by the PDA).

| Module | Artifact | What |
|---|---|---|
| `ecore/` | `dev.emcc:emc2-ecore` | The core runtime. Plain Java, no Spring |
| `app/` | `dev.emcc:emc2-app` | Spring Boot edge and launcher; builds `app/target/emc2-app.jar` |
| `service/` | `dev.emcc:emcc-service` | The Windows service's entry for procrun (ADR-0063, M9 C4); builds `service/target/emcc-service.jar`. The JDK only |

Every dependency and plugin version is pinned in `pom.xml`. The build fails on a JDK other than 25 or on an unpinned plugin.

## Build, test, run

Use the scripts in `tools/` from the repository root: `node tools/build.mjs`, `node tools/test.mjs`, `node tools/start.mjs`.
Directly: `mvn -f server/pom.xml verify`, then from the repository root:

```
java -Dspring.profiles.active=dev -jar server/app/target/emc2-app.jar
```

- **Login mode** (ADR-0022), setting `emc2.login.mode`:
  - `oidc` (the default): login with OpenID Connect on the server side ("Login with OpenID Connect" below). Without its settings, or when its IAM cannot be reached at start, the server does not start and says how to choose the no-login mode. It never falls back to no login by itself.
  - `none`: the **no-login mode**. One local user (`local`, "Local user") with all permissions; every change goes out with `source.user` `local`. The server logs `*** NO LOGIN ***` at every start, and the shell shows a "No login" mark.
  - The `dev` profile chooses `none` (and adds the development stop endpoint below). It cannot be combined with `emc2.login.mode=oidc`: the server refuses to start.
- **Without login the server listens on this computer only:** with no `server.address` it binds to the loopback address; any other address makes it refuse to start, unless `--emc2.login.no-login.allow-network=true` is set as well (then it logs a second warning). To show it on other computers: `--server.address=0.0.0.0 --emc2.login.no-login.allow-network=true --emc2.allowed-hosts=<the name the others use>`. Everyone who reaches it then works as the local user, with all permissions.
- ECore starts before the web server accepts requests and stops after the web server has stopped.
- `http://localhost:8080/` serves the built web client from `emc2.web.root` (default `web/shell/dist`, relative to the working directory). `GET /api/health` returns `{"status":"UP","ecore":"RUNNING","version":{...},"manual":false}`.
- **The release's version and manual** (M9 RC2, owner ACQ; for the shell's help menu), read once at start from the folder the server runs in (`emc2.release.directory`, default the working directory, as `settings/`):
  - `version.properties` (written by `tools/release.mjs`): `/api/health`'s `version` is `{"name": <emcc.version>, "date": <emcc.build.date>, "commit": <emcc.build.commit>, "dirty": <emcc.build.dirty>, "sdk": <emcc.sdk.version>}`, a missing key left out; without the file (a developer run) `{"name":"dev","sdk":"<the SDK the server implements>"}`.
  - `manual/`: the built user manual, served at `/manual/` (its `index.html`; `/manual` redirects there), static, GET and HEAD only, open without login, under the shell's headers and CSP, revalidated on every load. Without it `/manual/` answers 404 and `manual` is false.
- **Stopping:** Ctrl+C in the server's console stops it cleanly (the web server finishes its requests, then ECore stops and the persistence manager writes everything). Scripts and tests, which cannot send Ctrl+C on Windows, use the stop endpoint below.
- Run-time folders: `--emc2.data.directory=<folder>` (the live picture, default `data`), `--emc2.plugins.directory=<folder>` (the installed plugins, default `plugins`) and `--emc2.web.root=<folder>`. Integration tests pass fresh temporary folders, so a run never writes into the repository.
- **Java:** any vendor's Java 25 or later runs the server; the release's own runtime (`runtime/`, made with `jlink`) is the default, and the start scripts' option for an admin's own Java is the MCA's (M9 B3). The server logs the Java it runs on at start ("Java <version> (<vendor>) at <home>"); a Java older than 25 cannot load its classes.
- Local overrides: command-line options (e.g. `--emc2.web.root=...`), or the settings files below in the working directory; no profile is needed for them. At the repository root only `application-local.*` is ignored by git, not `settings/`: keep credentials out of a checkout (the MCA is asked for `/settings/` in `.gitignore`).
- **State-changing requests** (every POST, PUT, PATCH and DELETE, whatever the path, so that no spelling of `/api/**` gets around it) must come from the server's own pages: a browser's `Origin` (or, without it, its `Referer`) must be this server's scheme, host and port, otherwise `403`. `Origin: null` is refused. Callers that send neither are no browser (scripts, `curl`, test tools) and go through (ADR-0022: against cross-site requests, together with the `SameSite=Lax` session cookie). Behind a reverse proxy: see below.

## Settings files (ADR-0060, M9 C1)

`SettingsFiles` (an `EnvironmentPostProcessor`, registered in `META-INF/spring.factories`) reads, before the edge starts, from the emcc folder (the working directory, which `%emcc%` names):

1. `application-local.properties`: **deprecated**, read with a warning at every start, and a second one naming (never the values of) its keys that the files below also set;
2. `settings/emcc.properties`: the installation's settings;
3. every `settings/credentials/*.properties`, by name: one file per credential (`login.properties` for the client secret, `http-<name>.properties`, `tls-<name>.properties`).

A later file wins over an earlier one (owner, 2026-11-16); environment variables and the command line win over all; all win over the bundled `application.properties`. Each file is read by Spring's own `.properties` reader (Latin-1, `\uXXXX`). A value that starts with `%emcc%/` or `%emcc%\` is resolved below the emcc folder, in any key (store paths, `emc2.conversions.ffmpeg`, `emc2.labeling.definitions`, `logging.file.name`). The files' names and the overlapping keys are logged at start; values never. They are read after Spring's own configuration, so `spring.profiles.active` and `spring.config.import` in them have no effect. A file whose permissions cannot be checked counts as readable by others.

**The commented templates** the release ships are in `server/app/src/release/settings/` (owner: the CDA's; the MCA's release copies them): `emcc.properties` with every key the server binds, set or commented out with its default, grouped and explained; `credentials/login.properties`, `http-example.properties` and `tls-example.properties`, comments only. `SettingsTemplateTest` fails when a `@Value` key, a `@ConfigurationProperties` record's part or a bundled key (but the fixed internals: `spring.*`, the session cookie, compression, Tomcat's context parameters, `server.shutdown`) is missing from them, or when a credentials template holds a value.

**Credentials' permissions** (ADR-0060 point 3, owner Q2 A): at start every file in `settings/credentials/` is checked, except a `.properties` file that holds no setting: only comments and blank lines, as the templates ship (owner ABV A; a zip carries no Windows rights). A key store or PEM file is always checked. One that others can read gets a warning in the log, naming the file: on Windows an `ALLOW` entry with read for Everyone, Users or Authenticated Users (Java gives the ACL's names, not its SIDs, so on a Windows in another language these groups are not recognised and the check stays silent); on POSIX group or other read. `emc2.credentials.require-private=true` (default `false`) refuses the start instead. There is no Monitor entry (owner, 2026-11-16): keeping the folder private is the admin's task. On Windows, for example, for a service account `NT SERVICE\emcc`:

```
icacls settings\credentials /inheritance:r /grant:r "NT SERVICE\emcc:(OI)(CI)R" "*S-1-5-32-544:(OI)(CI)F" "*S-1-5-18:(OI)(CI)F"
```

(read for emcc's account; full control for Administrators and SYSTEM; nothing inherited). On Linux: `chmod 700 settings/credentials && chmod 600 settings/credentials/*`.

**Hand-edited JSON** (the labeling definitions, and any later one) may carry `//` and `/* */` comments (Jackson's `ALLOW_JAVA_COMMENTS`; still one value, no duplicate names). What emcc writes itself (`data/ecore-config.json`) stays plain JSON.

## Login with OpenID Connect (ADR-0022)

The edge (`server/app` only) runs the Authorization Code flow with PKCE as a **confidential client** (Spring Security's OAuth2 client). The tokens stay in the server's HTTP session; the browser gets only the session cookie (`HttpOnly`, `SameSite=Lax`, `Secure` when the page came over HTTPS). Keycloak is the reference IAM; any OpenID Connect provider will do.

**Settings** (in `settings/emcc.properties`, the client secret in `settings/credentials/login.properties`, or environment variables such as `EMC2_LOGIN_OIDC_CLIENT_SECRET`; **never in the repository**):

```
emc2.login.mode=oidc
emc2.login.oidc.issuer-uri=http://localhost:8180/realms/emc2
emc2.login.oidc.client-id=emc2
emc2.login.oidc.client-secret=<from the IAM>
# The claim with the user's roles or groups (a list of strings); a dotted name reaches into an object.
emc2.login.oidc.roles-claim=groups
# Permission → the roles or groups that have it (brackets, because permission names contain dots).
emc2.login.oidc.permissions[objects.edit]=editors,admins
emc2.login.oidc.permissions[layers.edit]=editors,admins
emc2.login.oidc.permissions[settings.admin]=admins
# * gives a permission to every logged-in user, whatever their groups
emc2.login.oidc.permissions[plugin.fmv.view]=*
```

**`*` (owner ACD A):** in a permission's list, `*` means every user who has logged in, with or without groups. Other groups on the same line add nothing (`*,admins` is everyone). It counts only with login: in the no-login mode (`emc2.login.mode=none`) the local user has every permission, as before. A group named `*` in the token gives nothing of its own.

The server reads the IAM's discovery document at start; an IAM that cannot be reached stops the start.

**The client at the IAM** (Keycloak: a client with "Client authentication" on and the standard flow):
- valid redirect URI `<server>/login/oauth2/code/emc2`, e.g. `http://localhost:8080/login/oauth2/code/emc2`;
- PKCE method `S256` (the server always sends it);
- valid post-logout redirect URI `<server>/`;
- back-channel logout URL `<server>/logout/connect/back-channel/emc2`, with the session id ("Backchannel logout session required");
- a mapper that puts the roles or groups into the ID token under the claim named in `roles-claim` (Keycloak: "Group Membership" as `groups`, without the full path; or the realm roles as `realm_access.roles`).

**What happens:**
- A page that is not logged in goes to the IAM's login page (a top-level navigation; the CSP stays `'self'`) and comes back to the page. `/api/**` answers `401` and never redirects; `/api/health` stays open, and so does the user manual at `/manual/` (GET and HEAD).
- A login that does not succeed (the user cancels at the IAM, a wrong client secret) gets a page that says so, with a link to try again; never a redirect, which could loop between the server and the IAM.
- The user is the IAM's `sub` (`source.user` of every change), shown by `preferred_username`; its permissions are those whose roles or groups the user has. **They are read once, at login**: a role given or taken at the IAM counts from the next login (the SRA should know; T-046).
- **Change requests need the user's permission** (overview 4.4, T-062): every one from a browser session is the session user's, whatever its `source.plugin` says; an object needs `objects.edit`, a layer `layers.edit`, whoever created it. The live session checks it first, before every other check, and refuses with `PERMISSION_DENIED`; the object store checks it again (every `StoreMsg.Apply` says whom it acts for: a user, or no user). Order and messages: `live-picture-protocol.md`. In the no-login mode the local user has every permission.
- The live picture's handshake needs the session and this server's `Origin` (`401`, `403` otherwise; a page of another site cannot use the user's cookie).
- **Logout:** the shell sends `POST /logout` with `Accept: application/json` and gets `{"redirect": <the IAM's logout page>}`, then goes there itself; the IAM ends its session and returns to `/`. Other callers get a `302` to that page. (A form post answered with a redirect to the IAM would be blocked by the CSP's `form-action 'self'`.)
- **The login session ends** at logout, at the IAM's back-channel logout, when the IAM refuses to renew the login (`invalid_grant`), or after 30 minutes without requests. The user's live picture connections are then closed with `4401`, and the shell asks the user to log in again. At login the session gets a new id (against session fixation).
- **No request is served on an expired access token that cannot be renewed:** every request with login checks the token's expiry (no call to the IAM while it is valid). An expired one is renewed on the way; when the IAM refuses, the login ends (`401` for the API, the login page for pages); when the IAM cannot be reached, `503`, and the session stays; for 5 s after that the session's requests get `503` without asking the IAM again (so a hung IAM does not make each of them wait for the timeouts). So a revocation at the IAM (a disabled user, an ended IAM session) counts within one access token lifetime, for every client. Messages on a live picture socket that is open already are not requests: the shell's keep-alive ends that socket within a minute when the IAM refuses.
- The shell calls `GET /api/session` every minute while the page is open: it keeps the HTTP session alive (WebSocket traffic does not count) and renews the access token shortly before it expires. When the IAM refuses, the session ends (`401`). When the IAM cannot be reached or fails, nothing ends (`503`), and the next minute tries again: an IAM outage logs nobody out. Renewals of one session (several tabs) take turns, so a refresh token the IAM rotates is never used twice.
- **How often the IAM is asked** follows the IAM's access token lifetime (Keycloak: the realm's "Access Token Lifespan", 5 minutes by default): a session renews about once per lifetime minus a minute (Spring Security renews a token that expires within a minute). With a lifetime of 2 minutes or less, almost every keep-alive renews through the IAM; with one under a minute, every one does. A shorter lifetime makes a revocation at the IAM count sooner, at the cost of more calls to the IAM.
- Every call to the IAM (discovery at start, tokens, user info, keys) times out after 5 s to connect and 10 s to read. Spring Security reads the keys for back-channel logout tokens with a client of its own, which has no public setting: the server sets the JDK's default timeouts for such clients (`sun.net.client.defaultConnectTimeout` 5 000 ms, `sun.net.client.defaultReadTimeout` 10 000 ms) at start, unless they are set already.
- **Back-channel logout tokens** must be signed with the IAM's key, name its issuer and this client, carry the back-channel logout event and no `nonce`; others are refused (`400`) and nothing ends. A token without the `events` claim is refused by Spring Security with `500` and an error in the log. A captured valid logout token can be sent again (no `jti` is remembered): at worst it ends that user's session once more.
- **Back-channel logout** arrives at `/logout/connect/back-channel/emc2`; the server then sends itself `POST /logout` with the user's session, by default to the address the IAM used (`{baseUrl}/logout`). Behind a reverse proxy that is the public address, which the server must then be able to reach; set `emc2.login.oidc.back-channel-logout-uri=http://127.0.0.1:<port>/logout` instead.
- **Known limits (M1):** a page visited without login creates a short-lived HTTP session (the login's state); over plain HTTP the session cookie cannot be `Secure`, so use HTTPS (or a proxy that ends TLS) anywhere but on this computer; Spring Security's HSTS header, sent over HTTPS only, includes subdomains.
- The tests run the whole flow against a small OpenID Connect provider of their own (`FakeIam`), without Keycloak, also behind a proxy. Checked by hand against a real Keycloak 26.8.0 (the ITA's test realm, 2026-10-14): login with PKCE, logout (also at the IAM), back-channel logout (the live picture closed with `4401` at once), a renewal one minute before the access token expired, and the permissions per user (tabs, `403` from the admin endpoints, `PERMISSION_DENIED` for changes): as with `FakeIam`. The ITA's `run.mjs --keycloak` tests the same with Keycloak.

## Behind a reverse proxy

On port 80 or 443 behind a proxy that ends TLS, set `server.forward-headers-strategy=native` and `server.tomcat.remoteip.internal-proxies=<a regular expression for the proxy's address>` (e.g. `10\.0\.0\.5`), and add the public name to `emc2.allowed-hosts`. Tomcat then takes the browser's scheme, host and port from the proxy's `X-Forwarded-Proto`, `X-Forwarded-Host` and `X-Forwarded-Port`, only from that proxy. The `Host` check uses the forwarded name (the port is not compared: the public port is not the server's), the `Origin` check the forwarded scheme, name and port, and the session cookie gets `Secure`. Without these settings every request behind such a proxy is refused (`403`); `native` without `internal-proxies` does not start, because Tomcat's default would trust every address of the private ranges, and any computer of the local network could then forge the forwarded name. Strategies other than `none` and `native` (`framework`) do not start either: they take forwarded headers from any client. Nor does an empty value (`server.forward-headers-strategy=`): leave the setting out for `none`.

## Edge: headers, caching, compression

- **Content-Security-Policy** on every answer (overview 4.5, ADR-0030): `default-src 'self'`, scripts, connections, images, fonts, workers and media only from the emc2 server (`data:` and `blob:` images and workers, `blob:` media for live video's MediaSource (CR-0046), inline style attributes allowed; none of these reaches another host), no plugins (`object-src 'none'`), no framing. Also `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`.
  - **The shell's inline import map** (T-014): `script-src` also names the SHA-256 hash of each `<script type="importmap">` in the web root's `index.html` (`InlineScriptHashes`). The file is read again when its size or time changes, so a new build needs no restart. Any other inline script stays blocked.
  - `connect-src 'self'` covers the WebSocket on the same host (checked in Chrome with the built shell, and by the ITA's browser tests).
- **Caching:** `assets/` (content-hashed by Vite, including the shared libraries in `assets/vendor/`) for a year (`immutable`); everything else, `index.html` and the plugins' web parts above all, revalidated on every load (`no-cache`); `/api/…` never stored (`no-store`).
- **Compression:** gzip for text answers (scripts, styles, HTML, JSON, SVG) when the client accepts it; the WebSocket uses Tomcat's permessage-deflate.

## Live picture gateway (`dev.emcc.ecore.live`)

The browser's WebSocket `/api/live` (overview 4.5, ADR-0006). The messages are in [`live-picture-protocol.md`](live-picture-protocol.md).

- One **hub** worker collects the changes of `objects.changed` (each with the object before it and both bounds, `StoreChange`) and hands every session one batch per 200 ms (spike S2: browsers need batches at a limited cadence). It also sends the welcome notices and every broadcast (`data-types`, `settings`).
- Per browser, a **session** worker (subscriptions, snapshots, change requests) and a **writer** worker (the only one that touches the socket; it may block while the browser reads, so it has the longest budget, like the persistence manager's file I/O).
- **Subscriptions** (protocol version 2, T-039): several per browser, each with its own id and sequence: the whole picture, layers and counts (`objects: false`, counts followed from the changes' before and after states), or an area of interest. An area subscription keeps an `AreaView` of every object that reaches into its area, with its bound (spike S3, recommendations 3, 4 and 11): it judges each change from the bound before and after (events of objects shown individually, `left` for those that went out of the area), and above the budget divides the area into cube cells of about 64 px (from the view's `resolution`, else a twentieth of the area's extent): at most 3 objects per cell and shapes wider than half a cell stay single, denser cells are clusters, and only clusters whose counts changed or whose mean moved by a pixel are sent; below 90 % of the budget it returns to objects. A move (`area`) asks the store for the new area and answers with one `area-objects` difference, the old and new views brought to the same change. Label filtering, after M1, belongs in `AreaView.reaches` (S3 recommendation 14).
- **Budget:** a subscription's `budget` is capped by `emc2.live.max-budget` (default 100 000, the budget with a GPU), which is also the budget of one that names none.
- **Measured against S3** (`AreaMeasurement`, on demand; 200 000 points, BALTIC-like, 2026-10-12, the dev VM): the store's query for a zoomed-out view (zoom 4 to 6) takes 17 to 42 ms (median; p95 up to 75 ms); the session's fill with clusters about 130 to 145 ms more (p95 up to 230 ms; S3 measured 75 ms for both together with arrays of int handles); at most 1 244 drawn items at zooms 4 to 10, 2 216 objects at zoom 12; one zoomed-out subscription holds about 25 to 26 MB; a batch of 1 000 moves costs a zoomed-out subscription about 3 ms. A whole-world ring costs the store 30 ms with 64 positions, 67 ms with 256, 215 ms with 1 024 and 1.5 s with 8 192: hence at most 256 positions.
- **Area fills run on compute workers** (rule C7; T-047, owner 2026-10-13). A zoomed-out snapshot or move needs its `AreaView` filled: every object in the area put in its cube cell, the clusters summed up, 150 to 250 ms for 200 000 objects. The gateway runs one fill worker (`AreaFill`, owner `core-live`) per compute thread; each session always uses the same one. The session sends it the store's answer and gets back an immutable `AreaView.Filled` (rule C2: workers share no mutable state), from which it makes its own view without the cell arithmetic (`AreaView.of`, map entries only). Until the fill comes back, the snapshot or move stays asked for and the changes that arrive meanwhile are kept, as while the store is asked; a fill that times out or is refused is asked for again, at most 3 times in a row, then the browser gets an `error`; a fill that throws is answered as failed at once, and the fill workers are restartable (stateless). A snapshot that overtakes a move takes the area being moved to. The held objects per connection are counted again when a fill comes back. Each view keeps the set of objects shown individually, so a move's difference costs as many steps as there are such objects (few when clustered). Measured (`AreaMeasurement`, 200 000 objects, zoom 4 and 6, the dev VM under load): the fill worker 230 to 260 ms, the session about 30 ms (p95 under 50 ms) for a snapshot or a move, where it was 150 to 160 ms. Was an exception to rule C7 for T-039 part 1 (owner, 2026-10-12).
- **Limits per browser against a hostile client** (conformance review F1): at most 32 subscriptions; snapshots throttled per id and per session; at most 4 area queries per second per session (so one browser holds the store at most about a quarter of the time with whole-world areas); at most 256 positions per ring; and at most 600 000 objects held by a session's area subscriptions together (three whole views, such as the map view's and draw-symbols'; about 78 MB at most; else the subscription is not opened, or the move is refused). A held view still grows with the picture.
- **Workspaces** (ADR-0039 point 7, T-080; the protocol's "Workspaces are enforced" and "Subscriptions"): a session's user sees View and each declared workspace whose view permission it has (`Workspaces.visibleTo`). A subscription's snapshots and moves ask the store for its workspaces only (`GetArea`'s `workspaces`); each change carries its workspace (`StoreChange.workspace`) and goes only to subscriptions of it, while every `sequenceNo` moves on; the queries take what the user may see. The early permission check is coarse; the store decides.
- **Never silently behind:** each subscription checks that every batch continues where its last ended. A gap, a batch its mailbox refused, or events the hub missed bring it a fresh snapshot.
- **Change requests:** the server sets `source.user` (model rule 8); every request with a readable `requestId` gets exactly one `change-outcome`. `source.plugin` `core-shell` is the shell's own (CR-0015 item 10); every other id of ECore's is refused.
- **Object queries** (CR-0015 items 8 and 9, T-051): `get-objects` (up to 1 000 ids) and `query-layer` (pages of up to 500, in the order of the ids' text, which for UUID v7 ids is the order of creation) ask the object store (`StoreMsg.GetObjects`, `StoreMsg.GetLayerPage`), at most 8 per session at a time, each with a 10 s timeout; every one with a readable `queryId` gets exactly one answer. Each layer's ids are kept in order with every change, in sorted blocks of at most 1 024 (`LayerOrder`, conformance review F1). Measured with a million objects in one layer (random ids, the dev machine, 2026-10-16): a page of 500 about 0.2 ms, a create or delete about 1 to 4 µs, about 0.6 s more at start-up while the stored picture is read (UUID v7 ids, mostly added at the end, cost less); about 4 to 8 bytes per object, but at least one block per layer with objects, so a small layer costs about 4 to 8 KB (10 000 layers of a few objects each, about 40 to 80 MB). One sorted array instead had cost the object store about 0.45 s for a layer's first page and 40 ms per page after changes.
- **Snapshots** go out one part per handler call, one subscription's at a time, with at most 4 parts waiting in the writer (flow control): any size fits the budget and never fills the writer. At most one snapshot per subscription id every 2 s while it asks for the workspaces of the id's last snapshot, also across unsubscribe and subscribe, and at most 32 per session every 2 s (checked again when a held snapshot comes due); a workspace switch (the same id for other workspaces than its last snapshot's, also back and forth) is answered at once, within the session's 32 (owner, 2026-10-28); at most one area query per subscription every 250 ms (the latest move counts). At most 32 subscriptions per browser and 256 positions per area.
- **Limits per browser:** 2 Mi characters of messages waiting (else closed, 1008; worst case 2 to 4 MiB per session, 400 to 800 MiB for 200 sessions), 100 change requests waiting for the store (else rejected at once), at most `emc2.live.max-sessions` sessions (default 200, else 1013). A browser that does not keep up (about 1 000 messages waiting) is disconnected (1013) and gets a fresh snapshot when the shell reconnects.
- **Health:** every 5 s the hub closes the sockets of sessions whose worker or writer hung or failed (1011); every 30 s each browser is pinged, and a connection silent for `emc2.live.idle-timeout` (default 2 min) is closed.
- **`Host` check, against DNS rebinding:** every request, the web client's files included, needs a `Host` header that names this server (`localhost`, `127.0.0.1`, `[::1]`, `server.address` or `emc2.allowed-hosts`, on the port the server listens on). Every request, not those under `/api/**`: deciding by the path would let other spellings of it through (`/api;x/…`, `/%61pi/…`). A browser's `Origin` at the handshake must be the server itself. Reaching the server under another name needs `--emc2.allowed-hosts=<name>`. Behind a reverse proxy: see "Behind a reverse proxy" above.
- **Not enforced yet:** labels (within the workspaces it may see, every session gets everything; access by label comes after M1, and must then filter batches and snapshots per session) and `source.plugin` (believed as the shell sends it, except ECore's own ids; see the protocol document).

## The Windows service's entry (ADR-0063 point 4, M9 C4)

procrun (Apache Commons Daemon) runs emcc in its `jvm` mode: the JVM in procrun's own process, started and stopped through static methods of `dev.emcc.service.Service` in `emcc-service.jar`. It sits outside `emc2-app.jar`, because procrun's class loader does not see the Spring Boot jar's `BOOT-INF/classes`.

- `start(String[] args)` runs `org.springframework.boot.loader.launch.JarLauncher.main(args)`, the same server and arguments as `start.bat`, and then waits, as procrun's `jvm` mode expects (as the CDA reads it: the service ends when the start method returns; the ITA's T1 verifies it with the real procrun). A start that fails ends the JVM with 1, so the service's restart policy applies.
- `stop(String[] args)` ends the JVM with 0 on a thread of its own (`emcc-service-stop`) and returns at once; later calls do nothing. The exit code is always 0, not `SpringApplication.exit`'s as with the development stop endpoint. The JVM's shutdown hook then runs **the same orderly shutdown as Ctrl+C**: the web server's graceful shutdown, then ECore (plugins, sessions, the store, the persistence manager writing everything). procrun kills the process only after its stop timeout.
- Callable only inside the server's own process: no port, no endpoint, nothing for users.
- `ServiceStopTest` runs the built `emc2-app.jar` in a JVM of its own through `Service.start`, as procrun does, calls `Service.stop`, and checks the graceful shutdown before "ECore stopped", the written data folder and exit code 0. It needs the app's jar, so run it with `verify` (as `tools/test.mjs` does) or `package`.

procrun's settings, for the MCA's `service-install.bat` (B2), which sets the paths and the failure actions, with the working directory the emcc folder (`--StartPath`, `--StopPath`):

```
--StartMode=jvm --StartClass=dev.emcc.service.Service --StartMethod=start
--StopMode=jvm --StopClass=dev.emcc.service.Service --StopMethod=stop --StopTimeout=60
--Classpath=emc2-app.jar;emcc-service.jar --Jvm=<emcc>\runtime\bin\server\jvm.dll
```

`--StartParams` takes the server's arguments as `start.bat` passes them (separated by `;`); no secret goes there (ADR-0060). The real service (install, boot, stop, restart, uninstall) is the ITA's T1.

## Development stop endpoint

A development and test aid (owner decision 2026-10-07), used by the integration tests:

```
curl -X POST http://127.0.0.1:8080/api/dev/stop
```

- Answers `202 {"status":"STOPPING"}`, then starts the same clean stop as Ctrl+C. The JVM exits with code 0 when the stop succeeded.
- Exists **only in the no-login profile `dev`**; without it the path is unknown (404).
- Answers **only callers on this machine** (loopback), even when the server listens on `0.0.0.0`; others get 403.
- Refuses requests with an `Origin` header (403). Browsers send one, so no web page can stop a local server; `curl`, Node's `fetch` and test tools do not.
- **`dev` is always the no-login mode:** the server refuses to start with `dev` and `emc2.login.mode=oidc`, because the endpoint has no login of its own; its only protection is loopback and the missing `Origin`.
- The stop runs on a thread of its own (`emc2-stop`), started by the edge. That is a deliberate exception to "threads only in the worker runtime", which binds ECore and the plugins: the edge closes the whole application, including the runtime.

## Worker runtime (`dev.emcc.ecore.runtime`)

ECore's implementation of overview 4.2 and 4.3: workers, mailboxes, watchdog, request/reply, topics and timers. Entry point: `ECore.runtime()`, then `owner("core" | <plugin id>)`.

| Mechanism | Behaviour |
|---|---|
| Worker | One virtual thread, one bounded mailbox, one message at a time. A failing call is logged and the worker continues |
| Compute worker | An ordinary worker whose handler calls run on a bounded pool of platform threads (`RuntimeConfig.computeThreads`, one per processor by default; rule C7), as the worker's own call (sender, fence, context class loader). The budget counts from when the call starts on its pool thread, not while it waits for one; a fenced or stopped call is interrupted on its pool thread. Plugins get one with `WorkerSpec.compute(true)` (30 s budget) |
| Overflow | `DROP_OLDEST`, `DROP_NEWEST`, `COALESCE_BY_KEY` (replace in place, else evict the oldest), `BLOCK_SENDER` (only senders outside workers wait, at most the send timeout) |
| Watchdog | A call over its budget is reported (`HUNG`), and again if it returns after all ("recovered"). **Each report names the type of the message the call handles** (e.g. `StoreMsg.GetArea`; never its content; "(making the message)" while a mapped reply is still being made, "(making a fresh handler)" for a restart's factory) **and the JVM's garbage collection time during the call** (from the last sample before it, so up to one watchdog tick more; "at least" when the samples do not reach back to its start; "unknown" if the JVM cannot tell, which never stops a report or the watchdog), so that a slow call can be told from a paused JVM (`HungCall`; the watchdog samples the GC time on each tick, `GcHistory`, so the only cost per message is one volatile write of its class; MCA, 2026-10-16). The log says it after the report's sentence ("… Restarting with a fresh handler. The call was handling StoreMsg.GetArea; 4 ms of it JVM garbage collection."), and the runtime listener gets the same (`workerHung`, `workerRecovered`); a plugin's `DEGRADED` detail keeps its wording (the ITA matches it; owner, 2026-10-16). A restartable worker gets a fresh handler, made by the factory on the new worker thread under the budget; the stuck thread is fenced (its sends are dropped), and the hung message is not delivered again. At most 3 restarts within 10 minutes by default |
| Ask | Non-blocking; exactly one answer (`Ok`, `Failed`, `TimedOut`) arrives as a message, even into a full mailbox |
| Topics | Typed, never block the publisher; the mapper runs in the subscriber's worker. The publisher's type decides at each publish: a subscription made with another class gets nothing, with one WARN (G19, M9 C9); nothing is kept between publishes, so a plugin restarted with its classes loaded again publishes as before |
| Timers | `once` and `every` (fixed delay, a tick is skipped while the previous one is undelivered) |
| Stop | Per owner: timers and subscriptions first, then workers newest first; a running call may finish within its budget, queued messages are discarded and their asks fail |
| Caps | Per owner (`OwnerLimits`, CR-0005; ECore's own owners are unlimited): outstanding asks (an ask counts from sending until its answer, failure or timeout; one more is answered at once with `Failed("too many outstanding asks")` and nothing is sent) and active timers (a `once` until it fires or is cancelled, an `every` until cancelled; one more makes `once`/`every` throw `IllegalStateException`). Atomic counters, no lock. Each refusal is counted (`refusedAsks()`, `refusedTimers()`), and logged and reported to the listener (`capReached`) at most once a minute per owner, whichever cap refused (CR-0005: "once a minute per plugin"). An ask's slot is given back exactly once, whichever way it ends (answer, failure, timeout, or a request function that throws, even after answering through its handle); a timer that the scheduler refuses ends and gives its slot back |

For other parts of ECore only (never plugins): `WorkerRuntime.deliver(...)` with a drop hook (endpoint requests answer 503 when refused or evicted), `deliverAlways(...)` (answers such as outbound HTTP results), `askFor(...)` (an ask on an owner's behalf, under its cap: a plugin's store and document calls), `startLoop(...)` (the virtual thread of a listener's loop), `startTaskThread(...)` (the platform thread of a connection task's run, or of its closing at a stop), `schedule(...)` and `onFencedThread()`. A fenced thread cannot send, publish, ask or set timers.

Clock and scheduler are injectable (`RuntimeConfig.time(...)`), so the tests drive time by hand and never sleep.

**Known limit: a CPU-bound hang cannot be stopped.** Virtual threads are not preempted, and an endless computation never checks for interrupts. The watchdog still detects and reports it, because it runs on its own platform thread. But the stuck thread keeps one carrier thread busy until the server restarts, even after a restart of the worker. While fewer stuck calls than CPU cores exist, the other workers continue on the remaining carriers. With as many stuck calls as cores, every worker stops. CPU-heavy work belongs in compute workers on platform threads (rule C7). Blocking calls (waits, I/O) are interrupted and do not have this problem.

**Known limits of compute workers.** A call that waits for a pool thread has not started, so the watchdog does not count it: when every pool thread is held by a call that ignores interrupts, the other compute workers wait without being reported (the holding calls are reported hung). A fenced compute call that ignores its interrupt keeps its pool thread until it ends, so the pool has one thread fewer until then. A call still waiting for a pool thread when its worker stops never runs.

## Object store (`dev.emcc.ecore.store`)

The single writer of objects and layers (overview 4.4, ADR-0018). Send it `StoreMsg.Apply(request, replyTo)` with an ask: every request gets exactly one answer, a `ChangeOutcome.Applied` (the change event, also published on `objects.changed`) or a `ChangeOutcome.Rejected` (a change rejection). `ChangeOutcome.of(...)` turns the ask's answer into the outcome a requester reports: a request the store never took is `INTERNAL_ERROR`, a timeout is "outcome unknown".

- Implements model rules 1-8, 10-18 and 21 (`model/README.md`): closed rings, ring orientation, geometry sanity, references, update semantics, gapless sequence numbers, only empty layers deletable; the data type must be available on create and when an update changes it (never checked for stored data), the data source is fixed at creation, `validFrom` is not after `expires`, and an external identity is copied to `meta`, kept, and unique (`EXTERNAL_REF_EXISTS`; deleting frees it). Data model 1.4.0 (SDK 1.4.0 part 3): an object's `fieldSets` keep the stored ones on update, and a listed set is added after them (rule 5's third exception; nothing removes one); its `relations` are replaced as a whole; after rule 16 come rule 17 (each relation's kind declared, except on update an entry the stored object carries; `/data/relations/<i>/kind`; the other object is never checked and nothing cascades) and rule 18 (each set the request adds declared; `/data/fieldSets/<i>`), then (data model 1.5.0, CR-0038) rule 21: a `core.symbol`'s create, or its update that changes `dataType`, adds the sets its data type names and it lacks, after its own, in the data type's order (only symbols, owner NO A; an update that keeps the data type adds none, and stored objects are not migrated), then the declared fields. Rule 3 is the first check of an entity's state, so a create sent again gets `ENTITY_EXISTS`; only the permission and the refusal of what is not applied yet (another workspace, below) come before it.
- **Workspaces** (ADR-0039, data model 1.2.0, T-080; `Workspaces`, fixed by the plugin host before any plugin runs): a layer's `workspace` is View (stored as absent, R2) or a declared one, else `VALIDATION_FAILED` at `/data/workspace`; on update an absent one keeps the stored one and a named one must equal it (R2, the ACA's C1); an object never moves to another workspace's layer (R1, `/data/layerId`). A user's change needs the edit permission of its workspace (`Workspaces.editPermission`), first of all checks; before it, for a user, what is in a workspace it may not see does not exist (`ENTITY_NOT_FOUND`, `LAYER_NOT_FOUND`; a new layer there is as in one nobody declares; owner, 2026-10-27). An undeclared workspace keeps its layers, which only plugins' server parts see and change. The reads take a set of workspaces (`null`: all); each published change carries its workspace. `FakeStore` has no view permission, so there a user with the edit permission alone may change things (for the PDA).
- **Declared fields** (ADR-0038, CR-0025 part 4): a request's `fields` are checked after the content, each at `/fields/<i>` with `VALIDATION_FAILED`: set once per request; declared by a loaded plugin; editable by others, or the requester's own (`source.plugin`, as for its namespace); and a value of the declared type and limits (the SDK's `DeclaredField.problem`, the check plugins use too). Every failing field is listed. Then they are applied after the content: a value sets `extensions.<plugin>.<name>`, `null` removes it (refused for a required field), and a namespace left empty goes. Other plugins' namespaces in the content are still ignored on an update (blind forwarding, ADR-0018), so an editor's older copy never overwrites a field. Not checked: the object's data type (the SDK's editor offers every editable field through its "+"), and the owning plugin's own namespace in the content. An update that is not saved carries no fields (`VALIDATION_FAILED` at `/fields`). **"Editable by others" guards editors and plugins, not hand-built requests:** a browser's `source.plugin` is the shell's claim, so a user with `objects.edit` who builds a request by hand can name the owning plugin and set its other fields, as they can write its namespace through the content today (the CR's rule; owner, 2026-10-26).
- The available data types (`DataTypes`) are `core.general` and those the plugins declare, fixed by the plugin host before any plugin runs.
- Ring orientation unwraps longitudes along each edge's shorter way round (rings across the antimeridian work; a ring around a pole is rejected), then takes the sign of the area in unwrapped longitude/latitude, as rule 1 allows. That approximates the orientation along the geodesic edges: right for the rings a map draws, but a ring spanning tens of degrees near a pole can get the wrong answer.
- Extension ownership (ADR-0018): all namespaces on create; on update only the requester's own namespace (`source.plugin`), foreign ones ignored.
- `StoreMsg.GetSnapshot` answers with the whole picture as an immutable `PictureSnapshot`; `StoreMsg.Find` with every layer and the objects a filter (and an area) selects (the plugins' queries and subscriptions), or a failure naming the limit; `StoreMsg.GetArea` with what a browser's subscription starts from: the objects that reach into an area with their bounds, every layer and the object count per layer (`AreaSnapshot`).
- **Spatial index** (spike S3, conclusion 2): `PictureState` keeps each object's bound and a `CellIndex` of cube cells at level 6 (about 156 km; objects wider than 4 cells in one list every query tests), kept by the store's worker as it applies changes. An area query floods the cells from the area's inside point, takes the objects of cells wholly in the area with its margin without testing them (inside the ring and clear of it, or within the margin of it: at a zoomed-out view the margin, half the area's extent, holds most cells outside the ring) and tests the rest: exactly the objects a full scan finds. Cells and their lists are kept in arrays by cell id. Criterion 22's widest view (200 000 objects, map-view-2d's 216-position ring) reads in about 30 ms alone (`StoreAreaMeasurement`, on demand; 320 ms before). Every applied change is published with the object before it and its bounds before and after (`StoreChange`), so the live gateway judges it per area without a copy of the picture.
- **Expired objects are removed** (rule 15, `removeAfterExpirySeconds`): every 5 s an ECore worker sends `StoreMsg.RemoveExpired` with each data type's effective behaviour (configured, else the manifest's defaults). The store checks and deletes in one go, so an object renewed meanwhile stays; each removal is an ordinary delete by `core` with its change event, at most 1 000 per look. Data types without `removeAfterExpirySeconds`, and stored data types no plugin declares, are never removed.
- **Areas** (`dev.emcc.ecore.geo`, spike S3): `GeoArea` tests whether an object's bound (`Cap`) reaches into a ring with geodesic edges plus a margin (metres, or a share of the area's size), on the sphere, so the poles and the antimeridian are no special cases. A ring vertex exactly on the test arc counts on its positive side (half-open rule); whether the area holds the antipode of its inside point is decided by three points beside it. Bounds are conservative: a long line or polygon may match an area it only comes near.
- **The layer lock** (data model 1.3.0, ADR-0042, CR-0028 part 2 with R1; T-098): the object store keeps a layer's `locked` `false` as absent, and an update without `locked` keeps the stored value (the owner's CR), also a server part's built with the 1.2.0 constructor. A user's change to a locked layer's content is `LAYER_LOCKED` (`ObjectStore.objectLock`, `layerLock`): after the permission, `ENTITY_NOT_FOUND` and `LAYER_NOT_FOUND`, before the rule checks, the declared fields and `LAYER_NOT_EMPTY`; with the same paths and order as the test kit's `FakeStore`. Changes without a user (`Requester.NO_USER`: plugins' server parts, ECore) pass. The lock is stored with the layer in the journal and the snapshot (`ModelJson` reads and writes it). Protocol: `live-picture-protocol.md`.
- At start, ECore creates a layer "Drawing" in View with the configured default label if View has no layers, also when other workspaces have some (T-025; owner, 2026-10-27, decision E; named "Drawing" since M4, owner 2026-10-30, BT and BX: before, "Default"). A picture that already has a "Default" layer keeps it. ECore never creates a layer in a declared workspace.

## Persistence (`dev.emcc.ecore.persistence`)

Write-behind (overview 4.8): the persistence worker stores each change event after it was applied in memory. The file store keeps two files in `emc2.data.directory` (default `data`):

| File | Content |
|---|---|
| `snapshot.json` | The picture at one sequence number. Replaced atomically (temporary file, then rename) |
| `journal.jsonl` | One change event per line, after the snapshot, and the declarations of updates that were not saved (ADR-0041, below). Compacted into a new snapshot every 10 000 saved events |
| `ecore-config.json` | ECore's own configuration: the plugins' settings, each data type's behaviour and the installation's default look (`defaultLook`, absent until set), as users with `settings.admin` set them. Replaced atomically on each change |
| `documents/p-<plugin>/d-<key>.json` | The plugins' documents (SDK v1 `Documents`): at most 1 MiB each and 1 000 per plugin, keys of lowercase letters, digits, `-` and `.` up to 128 characters. The prefixes keep names Windows reserves (`con`, `nul`) off the file system |
| `user-documents/u-<sha-256 of the user id>/` | Each user's own documents (ADR-0027): `user.json` names the user (the IAM's `sub`, `local` without login), `n-<namespace>/d-<name>.json` each document as compact JSON. The hash keeps any user id out of file names |

- On load every document is validated. Every journal line ends with LF, so only the text after the last LF can be cut short by a crash: if it is a complete change event it is kept and gets its LF, otherwise it is cut off with a warning. Either way the next event starts on a fresh line. Any other damage, or a gap in the sequence that no declaration covers, stops the start rather than losing data silently.
- The start also fails if the data directory cannot be written.
- **Data model version:** the snapshot records the data model it holds (`"dataModel": "1.1.0"`; 1.0.0 data is read as it is, since 1.1.0 only adds optional style fields, CR-0014); a new data directory gets an empty snapshot at once, so a journal without a snapshot is M0's. **M0 data (0.1.0) is migrated once,** at the first start (model README, "Migration"): the journal is folded into the snapshot, every object gets `dataType` `core.general` and `dataSource` `manual` (nothing else changes), a copy of the old files is kept in `data-model-0.1.0/`, and the new snapshot is written with an empty journal. Journal events the snapshot already holds are skipped before they are validated, so a crash between the two writes loses nothing. An invalid 0.1.0 document stops the start, and data of a newer major version is refused, never rewritten.
- A dropped event (full mailbox) is detected as a gap and repaired with a fresh snapshot from the store. If the store cannot make it, persistence asks again at the next flush tick (one that cannot be written has its pause, below).
- **Durability:** appends are buffered and made durable on the 250 ms flush tick, at drain and at compaction.
- **A snapshot that cannot be written** (on Windows while another program has `snapshot.json` open: a virus scanner, a backup) leaves the old snapshot and the whole journal as they were. Persistence asks for a fresh snapshot after 1 s, then 2, 4 … up to 1 min, until one is written, and asks for none meanwhile; it warns the first time and once a minute while it lasts (`PersistenceWorker`). During a resync the pause stays at 1 s and it is an error: the changes since the gap are in no file until a snapshot is written, so a restart meanwhile could lose them. A hard kill loses up to the last 250 ms of changes, plus any backlog still waiting in the persistence mailbox (it holds up to 100 000 events and drops the newest when full).
- **Updates that are not saved** (ADR-0041, CR-0025 part 8; the simulator's moves while a simulation runs) are the exception. A server part marks one with `Change.notSaved()`. ECore does not check which plugin uses the mark (ADR-0041 point 7: only the simulator in M3; owner, 2026-10-26): the briefs and the reviews do, and the monitor's `notSavedUpdates` shows who uses it.
  - **Only a move:** the store accepts the mark only on an object update that changes nothing but the `geometry`, the `time` and the symbol's `direction` and `speed` (a tactical graphic's `distances` and `azimuths`, an object's `relations` and a set it adds, SDK 1.4.0, are content, not a move); anything else, and any create, delete or layer change, is rejected with `VALIDATION_FAILED`.
  - **Applied and sent, not written:** it gets its sequence number, version, change event and answer, and goes to the live picture and the store subscriptions like any change (model rule 7 holds for the live sequence). Persistence does not write it.
  - **The journal declares what it skipped,** so that it still loads as a strict chain: before the next saved event, one line for the run of sequence numbers (`{"notSaved":{"from":…,"to":…}}`), and before a saved update or delete of an object moved that way, one line with the version it had reached (`{"notSavedVersion":{"id":…,"version":…,"before":…}}`). No line per move. Loading accepts a gap, or a version jump, only where such a line declares it. Lines the snapshot already holds are skipped with their events. A journal with such lines is applied at the start and written as a new snapshot with an empty journal, so its lines are not replayed again and the count toward the next compaction starts from an empty journal.
  - **After a restart** an object comes back as its last saved change, or a later snapshot (a compaction or a resync during a run holds the moves), left it, and so does the sequence number; numbers and versions used by unsaved updates may be issued again. A clean stop counts the unsaved updates as accounted for ("Live picture accounted for up to sequence N"), so it logs no lost events; a hard kill loses them since the last save or snapshot.
  - **A journal with such lines needs this server version or later:** an older one stops at the first of them as a damaged line.
  - The monitor shows each plugin's updates that were not saved.
- A clean stop stops the store first and waits until persistence has written everything. If the last events never reached persistence, the stop logs an error naming the lost sequence numbers.

## Plugin host (`dev.emcc.ecore.plugin`)

Overview 4.1 and the SDK v0 and v1 designs (`docs/plugins/sdk-v1.md`). At start, after the object store, ECore reads `<emc2.plugins.directory>/<id>/plugin.json` for every folder; folders starting with `_` (the template) or `.` are skipped.

- **Checks, each with a reason in the plugin's status if it fails:** a valid manifest (schema), the folder name equals the id, the id is not `core` or `core-…` (ECore's), the `sdkVersion` range matches the SDK version this ECore implements, `Sdk.VERSION` of the SDK it is built against (1.5.0; npm semver, the shared cases in `model/examples/sdk-version-matching.json`; plugins for 0.x are refused, CR-0005), dependencies are installed, and `dependsOn`, `requires` and `uses` form no cycle (the providers of `requires` and `uses` keys start first when they are loaded, as the shell activates them; a `uses` key nobody provides is no reason; only the plugins on a cycle are refused, then those that depend on them by `dependsOn`, in rounds, and a plugin listing itself in `dependsOn` is no cycle, as in the shell's `plan.ts`; ECore does not refuse for a `requires` key whose provider is gone, which the shell does in the browser; the PDA's D4 review, owner). SDK v1: each declared data type's id starts with the plugin's id and a dot, once per manifest; SDK 1.2.0: each declared field's name once per manifest, and its limits consistent (a minimum above the maximum stops it at `/fields/<i>`); the settings schema compiles without referring outside itself (no `$ref` out of it, no `$id`, no other dialect; nothing is ever downloaded) and the defaults match it; each `network` pointer leads to host-and-port settings. SDK 1.5.0: each set a data type names in `fieldSets` is one the same manifest declares (model rule 20); `DataType` gets the sets as full ids and `manual` (default true), and browsers get both in the data types (`/api/config`, `data-types`).
- **Workspaces** (SDK 1.2.0, ADR-0039): a manifest's `workspaces` each start with the plugin's id and a dot, come once, and name two permissions among the plugin's own `permissions`; otherwise the plugin is refused. Fixed before any plugin runs, as the data types are: View first, then those of the plugins that may start, by `order` (default 100), in start order where it is the same (`PluginHost.workspaces()`, a plugin's `workspaces()`, the store's and the live picture's `Workspaces`). Browsers get the ones their user may see in `/api/config` (`workspaces`). A plugin's server part is not filtered: its queries and subscriptions take the workspaces its `ObjectQuery` names, every one when it names none (N9).
- **Declared fields** (SDK 1.2.0, ADR-0038): fixed before any plugin runs, as the data types are: those of the plugins that may start, in start order (`PluginHost.declaredFields()`, a plugin's `declaredFields()`, the object store's `DeclaredFields`). Browsers get them in `/api/config` (`declaredFields`). A plugin that may start but then fails keeps its fields declared until the next start, as it keeps its data types. A removed plugin's fields stay on the objects and are forwarded, but nothing declares them, so no request can set them.
- **Capabilities** (SDK 1.4.0, ADR-0044; owner, Q11; the ACA's R1 and R3): a manifest's `capabilities` (`temporal` in 1.4.0; another id fails the schema, and the reason names it: `invalid plugin.json: /capabilities/1: unknown capability history (ADR-0044 point 5)`). At load, before any of its code runs, a server part whose class implements an undeclared capability is refused, and so is one that lacks a declared capability when the plugin has no web part, each reason naming the capability as the test kit's `CapabilityCheck` does. A browser's shell reports what the web part implements and its `capabilityMismatch` (`POST /api/web-parts/{id}/capabilities` `{"implemented": [ids], "problem": text or null}`, any logged-in user, `204`, `404` for a plugin that is not running, `400` for a body it cannot read; not under `/api/plugins/{id}/`, the plugin's own endpoints). ECore judges the whole with the server part: the shell's problem, else a declared capability neither part implements, is the plugin's `capabilityFault` until a later report says otherwise, shown in the Monitor; the plugin keeps running (owner, 2026-11-06).
- **The user's time** (SDK 1.4.0, ADR-0045; `plugin/UserTimes`): for a server part that implements `Temporal`, ECore asks `timeDelivery()` once after `init` (a throw refuses the plugin) and delivers each live session's `SessionTimeChange` through it: at the session's start (`now`), at each `time` message (`live-picture-protocol.md`; the set time and the interval in one value, CR-0032), and `now` (both parts at their defaults) once at its end, for every session (owner, Q10; the ACA's R2); a plugin that starts while sessions are open gets each at once. The mapper runs on the session's thread; one that throws makes its plugin DEGRADED. An endpoint request's `userTime()` is the time of the session its `X-Emc2-Session` header names, for a temporal plugin and a session of the request's own user; otherwise `now` (owner, 2026-11-06). When a `time` message races with the session's end, the plugin may get `now` twice, the last after the time, never a time as the last word.
- **Field sets and relation kinds** (SDK 1.4.0, ADR-0050, ADR-0051): fixed with the declared fields, from the plugins that may start, in start order (`PluginHost.fieldSets()` and `relationKinds()`, a plugin's `fieldSets()` and `relationKinds()`, the object store's `DeclaredFields`). A manifest whose set id comes twice or names a field the plugin does not declare, or whose relation kind is outside the plugin's namespace or comes twice, refuses the plugin. A relation kind's line gets its defaults (width 1, solid, no arrowhead), `defaultOn` false. A channel's `fieldSet` is passed on as given, not checked (owner, 2026-11-06).
- **Data types:** fixed before any plugin runs: `core.general`, then those of the plugins that may start, in start order (`PluginHost.dataTypes()`, a plugin's `dataTypes()`). ECore warns once per stored data type no plugin declares. Each data type's effective behaviour is the configured one, else the declaring manifest's defaults (`PluginHost.behaviours()`).
- **Start order:** dependencies and the providers of required web services first, ties by id. **Stop:** reverse order, before the object store stops.
- **Class loader per plugin:** `<id>/server/*.jar` plus the platform, the Plugin SDK and JSpecify; nothing of ECore, Spring, Jackson or the test kit.
- **Life cycle:** the entry class is created, `init` and `start` run in a lifecycle worker per plugin with a budget of 5 s each, with the plugin's class loader as context class loader (also for every handler call and handler factory). A plugin that throws or overruns is disabled (status `FAILED` with the reason), and so are the plugins that depend on it. A `required` plugin that fails stops the start of the server.
- **SDK mapping:** one to one onto the worker runtime. A plugin's workers, timers and subscriptions belong to the runtime owner named by its id. A plugin publishes only to topics named `<id>.…`. The effective status is the worse of the plugin's own and ECore's; a hung worker that is not restarted makes the plugin `DEGRADED`.
- **Endpoints:** `GET /api/plugins/{id}/…` is delivered into the plugin's worker, with the user of the browser session (the local user, who has every permission, in the no-login mode). ECore answers itself with 403 when the endpoint `requires` a permission the user lacks (never delivered), 404 (unknown plugin or path), 503 (the mailbox refused or evicted the request), 504 (no answer within the endpoint's timeout) or 500 (the plugin's mapper failed); exactly one answer is sent. `POST` and 405: next bullet.
- **POST endpoints** (SDK 1.2.0, CR-0026 with the ACA's R2 to R5): `POST /api/plugins/{id}/…` with a JSON body, for commands; `register` refuses a `POST` endpoint without a permission. Every method reaches `PluginEndpoints`, which answers 404, 405 with `Allow`, 403, 415, 413 and 400 itself, in the order and by the rules of the SDK's `Endpoints` Javadoc, before the plugin sees anything. What ECore adds:
  - **The body** is read on the edge's request thread, never a worker, only once the checks before it have passed, and at most `maxBody` + 1 bytes (a `Content-Length` above `maxBody` gets 413 unread). It is parsed as model JSON is (R2), but up to the SDK's 1 000 levels (`Endpoint.MAX_BODY_DEPTH`; model documents keep Jackson's 500). The query of a form-encoded request is not read, since the container would read the body for it.
  - **Spring's multipart and form handling are off** (`spring.servlet.multipart.enabled`, `spring.mvc.formcontent.filter.enabled`): no endpoint takes uploads or forms, and with them on Spring would read such a body whole (multipart up to 10 MB, forms without a limit) before any controller decides.
  - **Cross-site requests** never get here: `OriginCheckFilter` refuses them with 403. A request with neither `Origin` nor `Referer` comes from no browser and passes (the filter's own rule, R5); the JSON content type, which a cross-site form cannot send, is a second layer. Login as for `GET`: 401 without a session.
  - **Logs (R3):** every delivered `POST` once answered, by the plugin or by ECore (503, 504, 500): `Plugin <id>: POST <path> by user <id> answered <status>`, never the body. A refused `POST` (403, 415, 413, 400) at most once a minute per plugin, with the number left out since; a parse error's detail, which may quote the body, goes to the client only. Paths and user ids are cut at 200 characters, with control characters and line separators escaped.
- **Service endpoints and raw bodies** (SDK 1.6.0, CR-0041 part A; ADR-0055 points 3 and 5): `Endpoint.service` endpoints are served at `/api/services/{id}/…` (`ServiceController`), open in the login mode too (no 401, no session; `SecurityConfiguration`), with the Host and Origin checks as everywhere (a system that sends no `Origin` passes). Their caller is `Caller.SERVICE` with its address (`getRemoteAddr`) and `Caller.SERVICE_USER`, who has no permissions, and their `userTime` is now. A browser request reaches only the ordinary endpoints and a service request only the service ones; any other is 404. Every service call is logged once answered, whatever its method, with the caller's address and never the body; its refusals (403, 404, 405, 413, 415, 400) as a `POST`'s are, at most once a minute per plugin. A `POST` that `accepts` media types takes the body as bytes, unchanged and undecoded (`EndpointRequest.rawBody()`): its `Content-Type` must be one of them with at most a `charset` parameter (else 415), then the size as for JSON (413, by `Content-Length` or once read). `register` lets a `POST` name no permission when it is a service endpoint or `checksUserItself()`. Browser requests carry `Caller.USER` with the browser's address.

ECore and the data model are 1.6.0 (`Sdk.VERSION`, `ModelJson.DATA_MODEL`; a 1.5.0 store is read as it is, the major being the same).
- **SDK 1.7.0 (CR-0042, T-192):** a data type's `fadeSetting` (a JSON Pointer into its plugin's settings) is kept as written and sent, where declared, in `/api/config`'s and the `data-types` message's data types; the shell resolves the stepped fade. ECore and the data model are 1.7.0 (`Sdk.VERSION`, `ModelJson.DATA_MODEL`; a 1.6.0 store is read as it is).

ECore and the data model are 1.8.0 (a 1.7.0 store is read as it is).

- **Local folders** (SDK 1.4.0, CR-0030 part 6, ADR-0049 point 4; model rule 19): `context.folders()` reads the folders a manifest declares in `folders` for the plugin, read only; the plugin does no file I/O of its own (`PluginLocalFolders`). The plugin host refuses a manifest that names a folder id twice or whose `setting` is not a `string` property of its settings schema. - **Listeners** (SDK v1): ECore opens a plugin's TCP or TLS connections itself, only to endpoints its current settings name at its manifest's `network.endpoints`, and runs each loop on a virtual thread of its own; reconnects follow the plugin's back-off (at least 100 ms), at most `emc2.listeners.max-per-plugin` (100) per plugin. - **The ready line** (M9 B3, owner ABB B; `ReadyLine`): once ECore and the edge are ready (Spring Boot's application-ready event), the server logs one INFO line, which the release's start scripts print as the address to open. **Its text is a contract for the scripts; keep it stable:**
  - `emcc ready at http://<host>:<port>/` without a certificate;
  - `emcc ready at https://<host>:<port>/` with HTTPS;
  - `emcc ready at https://<host>:<port>/ (http://<host>:<redirect-port>/ redirects to it)` with `emc2.https.redirect-port`.

  `<port>` is the port the server listens on (also when `server.port=0` picks one); `<host>` is `server.address`, or `localhost` when that is empty or every address (`0.0.0.0`, `::`), an IPv6 address in brackets. A script finds the line by its start, `emcc ready at `, and takes the address up to the first space.
- **HTTPS** (ADR-0061, M9 C2): the edge serves HTTPS on `server.port` when the settings name Spring Boot's SSL bundle `emcc`, normally in `settings/credentials/https.properties` (template `https-example.properties`): `spring.ssl.bundle.jks.emcc.keystore.location`, `.password`, `.type` (`PKCS12` or `JKS`) and `spring.ssl.bundle.jks.emcc.key.alias` where the store holds more than one key, or `spring.ssl.bundle.pem.emcc.keystore.certificate`, `.private-key`, `.private-key-password`. Paths may start with `%emcc%/`. `HttpsSettings` then sets `server.ssl.bundle=emcc`, the bundle's `options.enabled-protocols=TLSv1.3,TLSv1.2` and `reload-on-update=true` (owner, C2: a renewed certificate applies without a restart), each unless set. Plain HTTP is then off; a bundle that cannot be read stops the start (no fallback to HTTP).
  - **The redirect port** `emc2.https.redirect-port` (empty: off; owner Q3 A) listens where the server does and answers every request with `307` (owner, C2: not kept by browsers) to `https://<the same host>:<the HTTPS port><path>?<query>`, after the Host check, so never to a host of the request's choosing. Set without HTTPS, or equal to `server.port`, it stops the start.
  - **A missing file:** a key store, certificate or key that the bundle names as a file on this computer (`keystore.location`, `truststore.location`; PEM `keystore.certificate`, `keystore.private-key`, `truststore.certificate`) and that does not exist stops the start in the server's words: "HTTPS cannot start: <setting> (in <settings file>) names <path>, which is not a file." Anything else the bundle cannot read stops it with Spring's reason.
  - **HSTS** over HTTPS only: `max-age=31536000` without `includeSubDomains` (owner, C2: this host only), `emc2.https.hsts-max-age` seconds, 0 sends none.
  - **What T1 sees:** the session cookie gets `Secure` from the request being HTTPS (Tomcat); the live picture's WebSocket is `wss` on the same port; OIDC's redirect URI (`{baseUrl}`) becomes `https://` by itself, so the IAM must accept it; login, logout and the cookie's other flags are unchanged.
  - **Monitor:** `/api/monitor`'s `https` (beside ECore's snapshot): the server certificate's subject, issuer, end and `valid`/`soon` (30 days)/`expired`, read from the bundle at each answer, so a reloaded certificate shows at once; null over HTTP. The shell's Core has an HTTPS tile.
- **TLS credentials** (ADR-0062, M9 C3), shared by listeners and connection tasks, one file each, `settings/credentials/tls-<name>.properties` (the layout is the documented one; the names come from the keys):
  - `emc2.tls.<name>.trust-store` (required) with `.trust-store-type` and `.trust-store-password`; and, when the peer asks for a client certificate, either `.key-store` with `.key-store-type` and `.key-store-password`, or a **PEM identity**: `.key-store-type=PEM` (optional), `.certificate` (the chain, the client's certificate first) and `.private-key`, with `.private-key-password` if the key is encrypted. Paths may start with `%emcc%/`.
  - **Types:** `PKCS12`, `JKS` or `PEM`; without a type, by the file's extension: `.jks` JKS, `.pem`/`.crt`/`.cer` PEM, any other PKCS #12. A PEM trust store is a file of CA certificates without a password. A PEM key is PKCS #8, plain or encrypted (OpenSSL 3's and TAK Server's tools' form), or unencrypted `RSA PRIVATE KEY` or `EC PRIVATE KEY`; OpenSSL's old encrypted form (`Proc-Type: 4,ENCRYPTED`) is refused with the `openssl pkcs8 -topk8` line that converts it. The key must belong to the first certificate.
  - **Deprecated:** `emc2.listeners.credentials.<name>.*` (`.trust-store`, `.trust-store-password`, `.key-store`, `.key-store-password`; `.jks` JKS, any other PKCS #12) is still read, with a warning per name in the log; where both name a credential, `emc2.tls.<name>.*` wins as a whole.
  - **At start:** a missing key, a wrong type or a file that does not exist stops the start, naming the setting. Every credential is then read once: one that cannot be read (a wrong password, a broken PEM) gets a warning in the log and does not stop the server (owner, C3); a client certificate that has expired or expires within 30 days gets one too. A changed credential needs a restart (ADR-0062 point 5).
  - **Use:** a credential that cannot be read, or whose client certificate has expired, refuses `tls(name)`/`sslContext(name)` and a listener's connection with the reason (`the TLS credential <name>: its certificate (CN=…) expired on <date>`), so the link's status says it (ADR-0062 point 4).
  - **Monitor:** the core's `tls` lists every credential: its name, the keys it was read from, the client's chain and the trusted certificates, each with subject, issuer, expiry and `valid`, `soon` (within 30 days) or `expired`, or why it cannot be read. Never a path or a password.
  - **Settings:** `GET /api/settings/tls-credentials` (`settings.admin`) answers `{"names": [...]}`, sorted, for a settings field of kind `tls-credential` (CR-0048 point 1.3); ECore does not refuse an unknown name at save.
- **Connection tasks** (SDK 1.2.0, ADR-0036, T-079): a plugin's server part opens its own sockets, of any kind, inside tasks that `context.connections().start(spec, factory)` runs, each run on a platform thread of its own, a daemon: the only plugin code that may block (rule C6). Not a virtual thread (CR-0027): on Windows a virtual thread blocked writing a socket may never wake while another blocks reading it (JDK-8334574), which a task and its reading child do. The plugin's `close` calls at a stop run on a short platform thread too. So a plugin's tasks are up to `Connections.MAX_TASKS` (100, children included) platform threads, which the Monitor's JVM figure of platform threads counts. If no thread can be had, the task fails with the reason (its name and its place in the cap free up), and a stop's closing falls back to a virtual thread. ECore checks no endpoint (ADR-0036 point 3).
  - **A run** gets a fresh task from the factory (plugin code too: a factory that throws is a run that threw). When it ends, its context is fenced (what it sends afterwards is dropped), what it registered with `closeOnStop` is closed and its child tasks stop. Then the spec's `Restart`: `never()` ends it (`Stopped`, or `Failed` with the reason when it threw), `onFailure` restarts it when it threw, `always` also when it returned, after the listeners' back-off rule (at least 100 ms; delays grow after early ends and start over after a run that lasted the back-off's longest delay).
  - **The inbox** holds what workers `post` (never blocking: `ACCEPTED`, `DROPPED` or `CLOSED`), with the spec's capacity and overflow; `coalesceByKey` keeps an item's latest by its `Coalescing` key. It outlives the task's runs, and closes when the task stops (`take` answers `null`).
  - **Stopping** a task (its `ConnectionRef.stop`, or the plugin's stop) closes what its run registered, so that a blocked read or accept ends; the closing runs on a short thread of its own, so a `close` that blocks never holds up the caller. A run that has not ended 5 s later makes the plugin `DEGRADED` (and it stays so, as for a hung worker).
  - **The name is free again at once** (`ConnectionRef.stop`): a new task of the name is accepted at once, and its first run waits until the stopped one's run has ended, so two never run side by side (owner, 2026-10-24 and 2026-10-26); a successor stopped while it waits ends at once (its `Stopped` event, its inbox closed), and the name still passes on only after the earlier run has ended. A stopped task does not count toward the cap, so a stuck run keeps its thread. **A waiting successor holds no thread** (M9, C7 gap 1): its first run begins when the stuck run gives up the name; a successor that was stopped while it waited hands its wait over to the next start of the name and is gone, so a plugin that stops and starts a stuck link or compute task again and again keeps at most one waiting task; the monitor shows the stuck run and the newest task, and the log warns at each such start. **Across a restart of the plugin** (C7 gap 6) the new start's engines take over the last start's runs that have not ended, by name: a connection or compute task of such a name waits for it the same way. What remains: the stuck run itself keeps its thread (and a compute task its place in the cap) until it ends; ECore cannot end a thread that ignores its stop. The plugin's stop waits at most 2 s for what the runs registered to be closed, before the plugin's class loader is closed, and logs a warning for a run still closing then. A run that lives long should hand each client's socket to a child task rather than register it with `closeOnStop` itself, where it stays until the run ends.
  - **Child tasks** (`startChild`) are named `<parent>/<name>`, unique among their siblings, and stop with their parent's run.
  - **Events** (`Running`, `Restarting` with the reason and when, `Stopped`, `Failed`) reach the worker given at `start` in order; above 100 waiting, only the latest is kept.
  - **Caps and credentials:** at most `emc2.connections.max-per-plugin` (100) tasks per plugin that are not stopped, children included. `tls(name)` and `sslContext(name)` use the TLS credentials (`emc2.tls.<name>`, above; shared with listeners); an unknown name is refused, the stores are read once, and an expired client certificate is refused each time. **The sockets of `tls(name)` check that the peer's certificate names the host they connect to** (HTTPS endpoint identification), as listeners do (owner, 2026-10-26); a task that needs another check uses `sslContext(name)`. A cap below 1 stops the start, naming the setting.
  - The monitor view shows them (below).
- **Compute tasks** (SDK 1.9.0, CR-0048 point 5, ADR-0064; M9 C7; `PluginComputes`, `ComputeHub`): a plugin that declares `compute` in its manifest starts compute tasks with `context.compute().start(spec, factory)`, each run on a platform thread of its own named `ecore-compute-<plugin>/<task>`, on a second `TaskEngine` per plugin, so the restart with back-off, the inbox (senders never wait; `take` and `poll` the only waits besides the declared folders), the stop and the fence are the connection tasks'. **The counting** (owner YQ1 A): a task counts against the plugin's number from its start until it is stopped or hung, and against the server's cap `emc2.compute.max-threads` (default the cores minus one, at least one, 1 to 1024, read at start) until its thread has ended, its back-off and a hung task included. A start above either, or of a plugin that declares none or is switched off, is refused, never thrown: a stopped ref (`post` answers `CLOSED`) and `ComputeEvent.Refused`, counted per reason; a second start of a running name throws. **The admin's number** (PQ1 A): `GET`/`PUT /api/settings/plugins/{id}/compute` (`settings.admin`; `{declared, reason, allowed}`, `PUT {"allowed": n}` 0 to the declaration), stored in ECore's config (`computeThreads`; a plugin missing there gets its declaration) and applied at once: lowering it stops the newest tasks first, each `Stopped` with "the admin lowered the plugin's compute threads to N". **A task that will not stop** within `Computes.STOP_GRACE` (5 s) is `Hung`, its plugin DEGRADED; it keeps its place in the cap while its thread lives. **The fence:** after the stop, what the task sends, posts to itself or posts to a connection task is dropped (`CLOSED`); it sends only to its own plugin's workers. **The Monitor** (ADR-0064 point 5): the core's "Compute threads" (held of the cap) and, per declaring plugin, declared, allowed, running, the refusals and each task's state, CPU time from the thread CPU clock (owner: not JFR), busy share (the time not waiting for its inbox, between two answers), counters, details and inbox.
- **Output channels** (SDK 1.2.0, ADR-0037, T-081): an output plugin offers one channel per output link (`context.channels().offer(spec, worker, toMessage)`); other plugins' server parts `watch` the list and `send` updates and removals to the channels they choose, without a layer. One registry for the server (`ChannelRegistry`), each plugin's `channels()` over it (`PluginChannels`). **SDK 1.4.0 (CR-0030 part 1, ADR-0048 point 4):** a channel takes the kinds its spec names (ground truth by default); `send` of an item whose `kind()` the channel does not take throws `IllegalArgumentException`, a sender's mistake, and nothing is put in its inbox, as the test kit's `FakeChannels` does.
  - **The inbox** of a channel keeps the latest item per `coalesceKey()`, each in the place where it first arrived: a later item replaces a pending one in place. The key is the object id, a sensor report's sensor, and from SDK 1.5.0 a sequenced report's sensor and dwell number, so a ground radar's dwells do not replace each other (CR-0040). Over 10 000 pending objects (`Channels.MAX_PENDING`) the oldest goes and is counted; drops are logged at most once a minute per channel.
  - **Handing over:** at most 16 items (`Channels.MAX_IN_FLIGHT`) wait in the offering worker's mailbox (always queued, whatever its overflow policy); the plugin's mapper makes each into its message in that worker when it takes it, and the next one goes. A handed-over item still arrives after `withdraw`, which drops only the pending ones; if the worker stops first, it is counted as dropped. One thread at a time hands a channel's items over, so they reach the worker in the order they were taken from the inbox, whichever plugin or thread sent them (a removal is never overtaken by an older update).
  - **`send`** never blocks: `ACCEPTED` (also when it replaced a pending item), `CLOSED` when no channel has that id now, `DROPPED` from a worker thread the watchdog has fenced. It may be called from any thread, connection tasks included.
  - **`watch`** delivers the current list, then a new one at each change; when several are undelivered, the worker gets the latest.
  - **When a plugin stops,** its channels are withdrawn (watchers get the new list, senders `CLOSED`) and its watches cancelled; from then on its `offer` and `watch` throw `IllegalStateException`, also in a handler that still runs.
  - **Locking (rule C4, ADR-0021; the ACA's P3-2):** the registry's one lock is a leaf lock: no mapper, no sending to a worker and no logging while it is held.
  - **The cap:** at most `emc2.channels.max-per-plugin` (100) channels per plugin; one more makes `offer` throw `IllegalStateException`, a link offered twice `IllegalArgumentException`. The monitor view shows each channel (below).
  - **Declared kinds** (SDK 1.9.0, CR-0048 point 4, PQ2 A; M9 C8; `PayloadSchema`): the manifest's `channelKinds` are read with the plugin, each name once and each `payload` schema compiled then, or the plugin is refused: the schema is self-contained (every `$ref`, `$dynamicRef` and `$recursiveRef` starts with `#`, no `$id`, no `$schema` but draft 2020-12's; model rule 23; only keywords count, so a payload property named `$ref` and the data in `enum`, `const`, `default` and `examples` are no references) and the library's loader fetches nothing (ADR-0030). A channel's `declaredKinds` are only its own plugin's declared kinds, offered with a `toDeclared` mapper (the old `offer` refuses them). `send(channel, DeclaredItem)` checks, outside the registry's lock, the kind, the payload's size as compact UTF-8 JSON (at most 64 KiB) and the kind's schema (formats asserted), and throws `IllegalArgumentException` with the first problem, in the test kit's words (`FakeChannels`); nothing refused reaches the inbox. Declared items share the inbox, the newest per kind and id, never replacing an object's item, and reach the worker through `toDeclared`. The Monitor's channel row names the declared kinds it takes.
  - **A channel's state** (SDK 1.9.0, CR-0050 point 2, UQ4 A; M9 C10): `ChannelRef.state(state, detail)` sets READY, DEGRADED or NOT_SENDING with a plain-text detail (0 to 128 characters, no control characters, else `IllegalArgumentException`); the same state again changes nothing, and nothing changes once withdrawn. A channel starts READY, also when offered again. Watchers get the new list (`ChannelInfo.state()`, `stateDetail()`), coalesced as for any change. The Monitor's `ChannelStatus` carries `state` and `stateDetail`.
- **Streams to the web part** (SDK 1.8.0, CR-0044 E1, ADR-0057 point 5; T-208; `plugin/StreamHub`, `PluginStreams`, the edge's `StreamController`): `context.streams().open(spec)` opens a stream (at most 32 per plugin, a name once); its `StreamRef` travels to the connection task, whose `write` never blocks: under the stream's own leaf lock ECore keeps the start buffer (the chunks since the last start point, at most `emc2.streams.start-buffer-bytes`, default 16 MiB; past it, empty until the next start point) and adds the chunk to each viewer's lock-free queue. Each viewer has one virtual thread of ECore's (owner, 2026-11-14) that writes its queue, blocking, and flushes when it is empty. A viewer whose queue would pass `emc2.streams.viewer-queue-bytes` (4 MiB) loses it and resumes at the next start point, header first (counted as a loss); one whose write takes nothing for 30 s is closed (checked every 5 s, so after 30 to 35 s; a quiet stream closes no viewer). A viewer ends with the stream's close, the plugin's stop, the login session (`LoginSessions`), a gone browser, and before the web server's graceful shutdown (`StreamViewersStop`), each logged with plugin, stream, user and reason. A failed one may start again after a minute. **M9 C5** (the SRA's M9-S3; owner, 2026-11-17): each process gets an **empty environment** (`h264_mf` needs none, measured) and **a working folder of its own**, `emcc-conversion-*` in the system's temp folder, removed when it ends; `-max_alloc` (64 MiB, the largest single memory block) and `-max_streams` (16 input streams) are fixed. **The restart time:** a launch for a plugin's target stream comes at least `emc2.conversions.restart-seconds` (default 10, 1 to 600) after the last one for it; a start inside it is `Waiting` (input dropped) without holding up the others, and runs when the once-a-second timer finds the time over. **The start check** (`ConverterCheck`): when ECore starts, it asks the converter once, each run with an empty environment, its own folder and 10 s, for `-version`, `-encoders`, `-decoders` and `-formats`; it logs the path and version, or a WARN (a converter that hangs delays ECore's start by at most 4 x 10 s; at most 1 MiB of each answer is read), and a converter without the `h264_mf` encoder, the `mpeg2video` decoder or `mpegts` (demuxer and muxer) makes every start `Failed(UNAVAILABLE)` with what is missing. ## JSON (`dev.emcc.ecore.json`)

`ModelJson` maps the SDK's model types to and from JSON (from data model 1.6.0 a `core.text`'s `text`: its `value`, and `rotation` and `size` only when given; the store's own copies keep it) and validates every document it reads against the JSON Schemas in `model/schemas` (packaged into the jar). Extension numbers keep their exact value. It runs the SDK's codec contract test over `model/examples` (a layer's `workspace` and a request's `fields` included), and checks that the invalid `fields` and `workspace` examples fail as `InvalidDocumentException`.

## Rules enforced by tests

- `ecore` must not depend on Spring or on `dev.emcc.app` (ArchUnit).
- Every `ecore` package is `@NullMarked` (JSpecify): non-null by default, `@Nullable` where needed.
- Only `dev.emcc.ecore.runtime` creates threads or executors (also the compute pool and listeners' loops); nothing in ECore calls `Thread.sleep` (ArchUnit).
- ECore uses the SDK's model and JSON types anywhere, its plugin interfaces only in the plugin host (`dev.emcc.ecore.plugin`) (ArchUnit).
