emc2 · Common data model

Data model v0

The information that the core, the plugins and the browsers exchange: map objects, layers, and the messages that change them. Written in JSON and specified in JSON Schema, so that Java and TypeScript share one contract (ADR-0007).

Frozen at 0.1.0. Data model v0 was frozen together with SDK v0 on 2026-10-06, with the owner's approval after the ACA's reviews (tag contracts-0.1.0). Since then it changes only through change requests. This page shows model/ as it is on main at f12ba56 (2026-10-09), including the compatible clarification of CR-0004 (how numbers are compared). The normative contract is model/, meaning its schemas and its README, owned by the PDA. This page is a readable view of it.

2 Conventions

TopicConvention
FormatJSON in UTF-8, property names in camelCase. JSON Schema draft 2020-12; schema ids are URNs (urn:emc2:schema:<name>), so no tool ever tries to download them.
IdsLowercase UUIDs, generated by whoever creates the entity, so the requester knows the id at once and retries are safe. Use UUID version 7, which is time-ordered; the SDKs provide a generator.
TimestampsRFC 3339 in UTC with a trailing Z, millisecond precision, e.g. 2026-10-05T09:05:00.000Z.
CoordinatesWGS84 [longitude, latitude] or [longitude, latitude, altitude] in decimal degrees. Longitude first, always. Altitude in metres above the ellipsoid (HAE).
Distances and bearingsDistances are geodesic metres. Bearings are degrees clockwise from true north.
NumbersNumbers in the core fields (coordinates, radii, opacities, versions and so on) have double precision (IEEE 754), as the SDKs hold them (Java double, TypeScript number), and are compared as doubles. A writer may write the nearest double for a longer decimal. Only free-form JSON keeps exact decimals: extension data, and a plugin manifest's settings (CR-0004).
Empty valuesAn empty optional object or array ({}, []) means the same as a missing one. Writers leave it out; readers accept both (rule 13).
Plugin idsLowercase words separated by hyphens, e.g. draw-symbols. The plugin id is also the plugin's extension namespace.
Type names<namespace>.<name>, where the namespace is core or a plugin id, e.g. core.symbol.

3 Map object

Everything drawn on the map is a map object. The part its creator controls (content) travels in change requests, together with the id. The object store adds the bookkeeping: version and meta.

FieldTypeMeaning
idUUIDrequiredGlobally unique, never reused. Chosen by the creator.
typetype namerequiredOne of the core types below, or a plugin type <plugin-id>.<name>. Plugins should prefer a core type plus an extension, so that every plugin can show the object.
layerIdUUIDrequiredThe layer the object belongs to. Must exist.
geometryGeometryrequiredWhere the object is (section 4).
symbolSymboloptionalAPP-6 symbol (section 5). Required for symbols and tactical graphics, forbidden for shapes.
styleStyleoptionalStroke and fill, mainly for shapes (section 6).

metaobjectobject storecreated and modified (when, and by which plugin, user or external system), and externalRef (system, id) for objects that come from another system, such as a CoT uid.

Core object types

core.symbol

A single-point APP-6 symbol. Geometry must be a Point; symbol is required.

core.multipoint

An APP-6 tactical graphic defined by control points. Geometry is a LineString, Polygon or MultiPoint; symbol is required.

core.shape

Any geometry drawn with a style. It has no symbol.

4 Geometry

Four GeoJSON types (RFC 7946) plus four emc2 types for shapes GeoJSON lacks, which CoT and NVG need. All positions are WGS84, longitude first.

Pointcoordinates: one position
MultiPointcoordinates: one or more positions
LineStringcoordinates: two or more positions
PolygonRings of ≥ 4 positions, closed; first ring outer, others holes
Circlecenter, radius (m)
Ellipsecenter, semiMajorAxis, semiMinorAxis (m), rotation (bearing)
CorridorCentre line coordinates, total width (m)
ArcBandcenter, innerRadius, outerRadius, startBearing → endBearing clockwise. A sector has innerRadius 0
Edges are geodesic (rule 10). The edge between two consecutive positions is the shorter geodesic between them, whatever the map projection. Renderers densify edges, so a shape looks the same in Web Mercator and in polar projections. An edge may cross the antimeridian (from 179° to −179° is 2° long), so geometries are never split there. Limitation in v0: a polygon that encloses a pole cannot be expressed; use a Circle or ArcBand around the pole instead.

5 Symbol and modifiers

A symbol names the standard, its symbol identification code (SIDC) and optional modifiers. It is drawn by the symbology plugin with milsymbol (ADR-0010).

One APP-6E symbol, two spellings (owner, 2026-10-05): when digits 21–30 are all zero, writers write the short 20-digit form, as with every empty value (rule 13). Readers accept both forms, and every comparison treats them as equal, including symbol caches keyed by appearance.

The version digits follow milsymbol 3.0.4. The meaning of APP-6E digits 21–30 is not checked against the standard's text.

Modifiers: a closed list of 30 names

Named as in milsymbol's options. A misspelt name is rejected; adding a name later is a minor change. Two are machine values, the rest are text as displayed (1–128 characters).

7 Security label

Every object and every layer carries a confidentiality label in the structure of STANAG 4774 (ADatP-4774). Labels are stored, shown and forwarded; access control based on them comes after M1 (owner, 2026-10-10). The binding of labels to data (STANAG 4778) is not part of the model.

JSON fieldADatP-4774 XML
policyIdentifier.namerequiredConfidentialityInformation/PolicyIdentifier (text)
policyIdentifier.urioptional…/PolicyIdentifier/@URI
classificationrequiredConfidentialityInformation/Classification. A string, because the values depend on the policy
categories[].tagNameoptionalCategory/@TagName
categories[].typeCategory/@Type: permissive, restrictive, informative
categories[].uriCategory/@URI
categories[].values[]Category/GenericValue, one per value
creationDateTimeoptionalCreationDateTime
reviewDateTimeoptionalConfidentialityLabel/@ReviewDateTime
  • Default label: configured on the server (ECore) and handed to plugins by the SDKs. Plugins use it for everything they create.
  • Object and layer labels (ADR-0020): an object's label covers the object; a layer's label covers the layer's own data (name, order, existence).
    • Seeing an object: a user sees it only if cleared for both its label and its layer's label.
    • Seeing a layer: a user sees it only if cleared for its label.
    • No constraint between them: stored labels are not checked against each other, so existing data never needs a migration.
  • This JSON form is emc2's own. Before the real STANAG 4778 binding is built, the mapping must be checked against the official ADatP-4774 XML schema, and aligning with ADatP-4774's JSON encoding is decided then.

8 Extensions

A plugin stores its own data on an object under its plugin id. Only that plugin writes it; everyone else forwards it untouched (blind forwarding), so no information is lost on its way through the system. Values are JSON objects that only the owning plugin understands.

How an update merges extensions (rule 5)

Stored object

"extensions": {
  "cot-in": { "stale": "…08:25…" },
  "notes":  { "text": "at the bridge" }
}
+

Update from cot-in

"extensions": {
  "cot-in": { "stale": "…08:40…" }
}
=

Result

"extensions": {
  "cot-in": { "stale": "…08:40…" },
  "notes":  { "text": "at the bridge" }
}

On update, the object store applies only the requesting plugin's own namespace. Present: it replaces the stored value. An empty object {}: it removes it. Absent: it is kept. All other namespaces always come from the stored object, whatever the request contains. (notes is a hypothetical plugin used for the illustration.)

On create, all namespaces in the request are accepted. An imported object therefore keeps the extensions it was exported with, for example an emc2 export read back through NVG.

  • The object store enforces this (ADR-0018). Foreign namespaces in an update are ignored, never rejected, so blind forwarding never fails. The SDKs do not filter.
  • Extension data keeps its numbers exactly as written, even beyond double precision (CR-0004). The SDKs hold it as their own JSON type, never as plain doubles.

visiblebooleanrequiredDefault visibility for users.
labelSecurityLabelrequiredCovers the layer's own data.
extensionsmapoptionalAs for objects.
version, metaobject storeAs for objects.
  • Layers are flat in v0, with no groups or folders.
  • Background maps are not layers in this sense; they belong to the map view and the background map plugins.
  • ECore creates a layer named "Default" when there are none, and only empty layers can be deleted (rule 11).
  • Layers change through the same change requests as objects (entityType: "layer").

ChangeEvent: published to everyone

On topic objects.changed after a change is applied.

  • sequenceNo: global, gapless order of all changes on one server
  • requestId, entityType, operation, entityId
  • version after the change; previousVersion (null on create); baseVersion if sent
  • state: the complete entity after the change, null on delete
  • label: the entity's label, also on delete, so receivers can filter without the state
  • at, by: when and by whom
ChangeRejection: to the requester only

When the object store does not apply a request.

  • code: one of the codes below

11 Rules beyond the schema

JSON Schema cannot express everything. These rules are just as binding for the object store, the SDKs and the plugins. The object store rejects a request that breaks rules 1–4 or 11, and implements rules 1–8 and 10–13.

  1. Polygon rings are closed: the first and last positions are equal. Either orientation is accepted and normalized so that, going along the outer ring, the inside lies to the left; holes run the other way. The orientation is determined along the geodesic edges, not in longitude and latitude, so a ring from 179° to −179° is a small ring, not one around the whole Earth.
  2. Geometry sanity: for an ArcBand, innerRadius < outerRadius; for an Ellipse, semiMinorAxis ≤ semiMajorAxis.
  3. References: layerId must exist (LAYER_NOT_FOUND); a create needs a new id (ENTITY_EXISTS); an update or delete needs an existing entity (ENTITY_NOT_FOUND).
  4. Clients never send version or meta. The object store sets them.
  5. Update semantics: the core fields are replaced as a whole, so a missing field is removed. Extensions merge per plugin as in section 8.
  6. Delete increases the version by one. Its event has state: null and carries the entity's label.
  7. Sequence numbers are global and gapless per server.
  8. Actor: source.plugin names the requester; source.user comes from the login session, never from the client.
  9. Axis order: the schema only catches swapped coordinates when the latitude value is outside ±90. Every converter is tested with a point where latitude ≠ longitude.
  10. Edges are geodesic and never split at the antimeridian. Renderers densify them. A polygon around a pole cannot be expressed in v0.
  11. Only empty layers can be deleted (LAYER_NOT_EMPTY).
  12. Every change request gets exactly one answer, a change event or a change rejection, with the request's requestId. An update equal to the stored state is still applied, with a new version and an event.
  13. Empty means absent for optional objects and arrays: extensions, symbol.modifiers, style, properties, label.categories and details. Writers leave them out when empty; readers accept both forms; comparisons, including the codec round trip, treat them as equal. Not for the value of one extension namespace: on update, {} there removes that namespace (rule 5).

13 Versioning and validation

  • One SemVer version for all schemas, in model/package.json. Data model v0 is 0.1.0, frozen together with SDK v0 for milestone M0 (2026-10-06, tag contracts-0.1.0). Changes go through change requests.
  • Minor change: every previously valid document stays valid, e.g. a new optional field, a new modifier name, a relaxed limit. Major change: anything else; stored data then needs a migration through the persistence manager.
  • No field may change its meaning in a minor version, even if the schema stays the same (for example a unit, or what an empty value means).
  • Before 1.0.0 the data model is numbered like the SDKs: compatible additions during M0 are 0.1.x, 0.2.0 is breaking, and M1 brings 1.0.0.
  • History (later): the event log is append-only and never rewritten. Old events are read through upcasters that turn them into the current form when read.
  • The plugin manifest schema (plugin.json) also lives in model/, so it is tested the same way, but it is versioned with the SDK and described in docs/plugins/sdk-v0.md.
  • All parts of emc2 come from one repository and are released together, so a running system always uses one model version. That is why the schemas can be strict: unknown fields are rejected. Documents do not carry the model version; the WebSocket protocol and the persistence manager record it.
  • Validation: cd model, npm ci, npm test. The tests validate every schema and example, check that each invalid example fails for its stated reason, and that each example under invalid-by-rule/ passes the schema but breaks a rule (for the object store's and SDKs' contract tests).
