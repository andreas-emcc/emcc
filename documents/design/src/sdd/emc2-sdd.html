1 Introduction

1.1 Purpose

This document describes the technical design of emcc. emcc is the product name (owner, 2026-11-04); inside the code and the repository the system keeps the name emc2, so paths, package names (@emc2/…), plugin ids and settings keys (emc2.*) keep it. It is written for the agents and people who build, review and operate the system. It will grow with the project. This version covers the architecture and the data design (data model 1.7.0, frozen with plugin SDK 1.7.0, and SDK 1.8.0 as far as it is decided), up to milestone M8, and names what waits for M9. Detailed designs of each part are added as they are made (see Appendix A).

1.2 Scope

emcc is a web-based mock-up of a military command and control (C2) system, built to showcase what AI agents can do. Users see and edit objects – APP-6 symbols, vessel symbols, tactical graphics, shapes and texts – on a map that all users share live. Objects are exchanged with other systems through standard formats: Cursor on Target (CoT), NATO Vector Graphics (NVG) and GMTI (STANAG 4607) in and out, AIS and ADS-B in, and from M8 full motion video (STANAG 4609) in; KML comes later. Background maps come from WMS servers and, offline, from Natural Earth; terrain analysis uses local height data. A simulator in its own workspace moves tracks along routes, simulates ground radars on them, and sends both out through the plugins. Everything beyond a small core is a plugin.

2 Goals and constraints

#Quality goalConsequence for the design
1Robust under concurrencyNo deadlocks or race conditions by design. A hung part never hangs the whole application.
2Extensible through pluginsAll features beyond the core are plugins, built according to one design pattern.
3Works disconnectedEvery function has a way to work offline (Natural Earth for maps); the browser fetches nothing from the internet (ADR-0030).
4ScalesAt least 100 000 objects on the map, many users, more servers later.
5SecureReal IAM from the first demo, permissions enforced on the server. A security label on every object.
6Maintainable by agentsSmall parts with one owner each, and written contracts between them.

Constraints: the server runs on Linux (main target) and Windows; the client runs in a current web browser with the popover attribute (Chrome and Edge 114, Safari 17, Firefox 125, Firefox ESR 128 or later; owner, 2026-10-16); the system is self-hosted; login uses Keycloak or a similar IAM; the map is 2D first, with 3D possible later as separate modules. The full object count needs a client with a GPU (ADR-0017). The project is licensed under the Apache License 2.0, and its dependencies must have permissive licences, with two approved exceptions in release bundles: the Java runtime and, from M8, a minimal LGPL ffmpeg run as a separate process (ADR-0016, section 10.5). Releases are Windows x64 up to M8; Linux releases and tests come in M9.

3 System context

All users share one live picture held by the server. Browsers connect over HTTPS and a WebSocket. TAK systems, AIS and ADS-B receivers, NVG services, GMTI radars, UAVs and WMS servers are set up by separate projects; for emcc they are existing external systems. For tests, the External Services Agent runs a TAK Server, a GeoServer, Keycloak, an NVG service, and playbacks of recorded AIS, ADS-B, GMTI and FMV data on the development computer (section 11).

4 Architecture overview

4.1 Building blocks

  • app (Spring Boot edge) handles HTTP, WebSocket, login and sessions (ADR-0022) and static files. It is thin: it translates requests into ECore messages and back. Spring is used nowhere else.
  • ECore is plain Java. It hosts plugins, runs all workers and the plugins' connection tasks, delivers messages, holds the master copy of all objects and offers central services: persistence, security, settings, logging, metrics and notifications. Since M5 it gives optional functions only to the plugins that declare them as capabilities (ADR-0044), and lets plugins read the local folders an admin sets, read only (ADR-0049). In M8 it adds a stream hub, which serves a plugin's live streams to its web part, and a conversion service, which converts MPEG-2 video to H.264 in a separate ffmpeg process (ADR-0057, section 8.5).
  • Plugin SDKs (Java and TypeScript) are the contracts between core and plugins. They are frozen per milestone and changed only through change control: 1.0.0 in M1, 1.1.0 in M2, 1.2.0 in M3, 1.3.0 in M4, 1.4.0 in M5, 1.5.0 in M6, 1.6.0 and 1.7.0 in M7, and 1.8.0 in M8, still being built. Each is a compatible addition, so a plugin built for an earlier 1.x keeps working.
  • Shell is the web client frame (since M2, ADRs 0027, 0029, 0031–0034, 0039). A top bar holds the tabs (View, the workspaces that plugins declare such as Simulation, Settings and Monitor), small controls from plugins such as bookmarks, the setups control, the look, the clock and logout; from M5 also the time control, shown only with a temporal plugin (ADR-0045). Settings is a list, in categories since M7: General (the default look), Data types, Layers, and one entry per plugin. The View tab has the Map Pane with docked left, right and bottom panes, whose panels the user moves; the arrangement is saved as setups, remembered automatically or by name, in each user's own documents. One display settings window, opened from the Map Pane, holds each user's symbol size, labels, speed vector, relation lines and display filters (since M5, ADR-0046, ADR-0052). The shell keeps the lists of object and map actions for the right-click menus, with the shared Delete, Move to layer and Copy to layer (ADR-0032, ADR-0053), and gives the design tokens their values in three looks, light and dark, and two densities. The map itself is a plugin (map-view-2d), so a 3D map view can be added later as another plugin.
  • The UX agent's design (M8, ADR-0056): the User Experience Agent owns the looks' values, the shared components' look and the shell's look CSS, while the layout stays the CDA's. Its redesign gives Settings and the Monitor cards, lists as a table with a form beside it, one Save per editing surface, and the looks their own control shapes, tabs and edges. A look sets only look properties, never layout, sizes, icons, wording or behaviour.

Any kind may also be ingoing (consumes external data) or outgoing (sends data out), using push or pull. Since M3 such plugins open their own sockets in connection tasks, and are configured as links in their settings; every output link is also an output channel that other plugins can send to (section 8.3). A plugin that later needs its own process is connected through a stub plugin that implements the same SDK interfaces and forwards over inter-process communication.

  • Manifest (plugin.json): its schema lives in model/ but is versioned with the SDK. It declares the identity, kind, compatible SDK versions and start order (dependsOn); the web services a plugin provides and requires; whether it is required; its internet use and, from SDK 1.2.0, its own connections, for the server part only (internet and connections: declarations, shown in the monitor view; ECore checks no host, ADR-0030, ADR-0036); its settings with defaults; its permissions; from SDK v1 its data types (ADR-0023); from SDK 1.2.0 its workspaces (ADR-0039) and its declared fields (ADR-0038); from 1.4.0 its capabilities (ADR-0044), field sets (ADR-0050), relation kinds (ADR-0051) and local folders (ADR-0049); from 1.6.0 its Settings category and symbol palettes; and from 1.8.0 an icon. The plugin host rejects dependency cycles.
  • Installed layout: plugins/<id>/plugin.json, server/*.jar and web/.
  • Build wiring: a plugin's server part is a Maven module of the server build, registered with one line in server/pom.xml. Its web part is an npm workspace of the repository root, so all web parts share one lock file and the exact library versions the shell ships (CR-0006).
  • Template: plugins/_template/ is built and tested like a plugin, but never installed. Plugin agents copy it, and a test kit (ArchUnit rules, a fake plugin context, a fake object store, codec contract tests) checks every plugin's rules in its own build. The web test kit has fakes for the context, the map view and the services.
  • 19 plugins on main after M7: map-view-2d, basemap-osm, basemap-naturalearth, basemap-wms, symbology, coordinates, bookmarks, terrain, draw-symbols, draw-shapes, draw-tactical, layer-panel, object-list, simulator, cot, ais, adsb, gmti and nvg, each built by its own Plugin Coding Agent from a brief by the PDA. fmv, the 20th, is being built for M8 on integration/sdk-v1.8.

6 Concurrency design

RuleContent (normative – see overview 4.2 and ADR-0004)
C1Plugins never create threads, executors or thread pools; they request workers, connection tasks (from SDK 1.2.0), timers and the deprecated listeners from ECore.
C2A worker handles one message at a time; its state is only touched by itself.
C3Workers communicate only through immutable messages (Java records).
C4Plugins use no locks, monitors or blocking synchronizers. ECore shares a lock between plugins only if it is a leaf lock: no plugin code runs and no other lock is taken while it is held, and plugins cannot see it (ADR-0021).
C5Every request/reply has a timeout; events are preferred.
C6–C8Blocking I/O only in connection tasks (or the deprecated listeners), and plugins open sockets only there; CPU-heavy work in compute workers; no Java preview features.
  • Mailboxes are bounded and declare an overflow policy: DROP_OLDEST, DROP_NEWEST or COALESCE_BY_KEY, which keeps only the newest message per key and suits track position updates. BLOCK_SENDER (with a timeout) exists only inside ECore; plugins never block on a send.
  • Connection tasks (since M3, ADR-0036) run a plugin's own sockets of any kind: TCP client or server, UDP, multicast. ECore starts each on a platform thread of its own, restarts it with a back-off, caps the tasks per plugin, closes their sockets when they stop, and fences a stopped task. A task posts what it receives to workers as messages; workers hand it data to send through a bounded inbox, never blocking. Connection tasks use platform threads rather than virtual threads because of a JDK bug on Windows (JDK-8334574, CR-0027); workers stay on virtual threads.
  • Plugin code runs only in the plugin's own workers, and in its connection tasks. Functions a plugin hands to the SDK (handler factories, mappers) run inside the target worker under its time budget, so only data and handle ids would cross a future process boundary.
  • Watchdog: a worker that exceeds its time budget (5 s by default) is marked HUNG. If it is restartable, ECore fences the stuck instance and starts a fresh one on the same mailbox, up to a restart limit; otherwise its plugin is marked DEGRADED. Java cannot safely force-stop a thread, so a stuck thread is isolated and reported rather than killed.
  • Caps per plugin (CR-0005): at most 10 000 outstanding asks and 1 000 active timers, so one plugin cannot fill the scheduler for everyone. Refusals are counted, logged and shown in the monitor view (M1).
  • Enforcement in three layers: static architecture rules (ArchUnit, from the SDK's test kit) in every plugin's build, which also refuse sockets outside connection tasks; the watchdog at run time; and review before every merge, plus concurrency stress tests by the Integration Test Agent.
  • Streams (M8, ADR-0057): ECore's stream hub runs each viewer of a plugin's stream on a virtual thread of its own, so a slow viewer never holds up the plugin or the other viewers: past a bound it loses data, and the monitor counts it. The plugin hands its stream to the hub as immutable chunks from its connection task and never waits for a viewer.
  • External processes (M8, ADR-0057): only ECore starts a program, the shipped ffmpeg, one process per converted stream, and talks to it through pipes behind one narrow call, with timeouts for its start, a stalled conversion and its stop. Plugins never start programs, as they never create threads.
  • In the browser, the rules keep their spirit in the one Web Worker, the symbology plugin's for tactical graphics since M5: copied messages, no shared memory, a timeout per request (ADR-0043).

7 Object changes and the live picture

  • Single writer for objects and layers (ADR-0005, ADR-0018): all changes are ordered by sequence number, and race conditions on objects cannot occur.
  • Permissions first (since M1, overview 4.4): a user's change request needs objects.edit for an object and layers.edit for a layer, checked before anything else; without it the answer is PERMISSION_DENIED and nothing changes. In a workspace that a plugin declares (since M3), its own edit permission takes their place (ADR-0039). Changes from plugins' server parts and from ECore itself are not checked. The browser only hides what a user may not do.
  • The layer lock (since M4, ADR-0042): while a layer is locked, the store refuses a user's change to its content with LAYER_LOCKED: creating, changing, moving or deleting its objects, and changing or deleting the layer itself. Locking, unlocking and the draw order stay changeable by whoever may edit the layer. Changes without a user pass, so incoming data and the simulator's moves keep flowing into a locked layer.
  • Exactly one answer per change request (ADR-0018): a change event for everyone, or a change rejection with a fixed code (section 9.7) for the requester only, both carrying the request's requestId. If no answer arrives, the SDK reports "outcome unknown".
  • Extension ownership is enforced by the object store (ADR-0018): an update applies only the requesting plugin's own extension namespace and keeps every other one as stored. Since M3 a request may also name declared fields of other plugins that those plugins let others edit; the store checks each against its declaration and applies only them (ADR-0038).
  • Last write wins in version 1. Change requests already carry baseVersion, so optimistic locking can be added later without changing the model.
  • From the browser: the shell fills in requestId and the calling plugin; the server sets the user from the login session and never trusts it from the client. The shell's own changes, the shared Delete and the Layers entry's raise of a layer's classification, carry the reserved source.plugin core-shell (ADR-0032, CR-0015).
  • Move and copy to layer (since M6, ADR-0053): two shared object actions of the shell, like Delete. A move is an update with the new layerId, so the id, the relations and every extension stay; a copy is a create of a snapshot with a new id and no externalRef. Both stay within the current workspace, and the lock applies.
  • Objects the browser does not hold (since SDK 1.1.0): a plugin reads objects by id, and a layer's objects page by page, from the server, independent of the area of interest; the objects list uses this.
  • Live picture (protocol in server/live-picture-protocol.md): over one WebSocket, each browser opens subscriptions (since M1, spike S3). An area subscription gets a snapshot of its area of interest, then deltas, and clusters with counts when the area holds more objects than its budget; a panel can subscribe to the layers and their object counts only. The map view applies batches at its own cadence (ADR-0017). Since M3 a page subscribes to the layers of the workspace it shows, and the server sends a declared workspace's layers only to users with its view permission (ADR-0039).
  • History later: a change event holds everything needed. Storing events in an append-only log gives audit and timeline playback without redesign. A running simulation's moves are the exception: they are not stored (section 8.2).

8 Workspaces, simulator, sensors and video

Milestone M3, the Simulator, added the mechanisms of sections 8.1 to 8.3 (ADR-0036 to ADR-0041), following the owner's answers in docs/architecture/m3-simulator-decisions.md. M4 extended them with new inputs and the in/out playbook, M5 with sensors and GMTI (section 8.4), M7 with NVG, and M8 with full motion video (section 8.5). M9 brings a simulated camera (section 8.6).

8.1 Workspaces

  • A workspace is a top-bar tab with the View layout (ADR-0039): the Map Pane and the docked panes, with its own map state, panel layout, setups and layers. View is ECore's own; a plugin may declare more in its manifest, each with a permission to see it and one to change its layers and objects. The simulator declares Simulation.
  • A page shows one workspace at a time. Switching works like a new connection with another filter: fresh snapshots, the new workspace's panels and map state. Two workspaces at once means two browser windows.
  • Plugins choose where they appear: panels, overlays and actions name their workspaces, and appear in View only otherwise. Simulation reuses the map view, background maps, layer panel, symbols, shapes, coordinates, objects list and bookmarks, with no copied code.
  • A layer names its workspace (data model 1.2.0). In a declared workspace, View's layers can be shown as a read-only reference. The server enforces the workspace's permissions: its layers and objects reach only users who may see it, in subscriptions, queries and fetches alike.
  • First layers (M4): when there are none, the server creates "Drawing" in View and the simulator "Simulation" in its workspace.

8.2 The simulator

  • One shared simulation per server (ADR-0040), run by the simulator plugin's server part: one worker owns its state and a timer ticks it once per second, for at least 1 000 tracks. It runs with no browser open, and is kept over a restart, then paused. Its own permissions: to see, to edit and to run.
  • Tracks and routes are ordinary objects in the Simulation workspace: tracks are placed with draw-symbols; a route is a line object whose points carry a speed and an altitude, each instant or ramped. A time can be typed instead of a speed. Units are each user's choice; values are stored in SI units. Tracks move along geodesics, with their position, direction and speed updated by change requests.
  • Groups and events: selected objects are put on a route as a single object, a convoy (one after the other) or a formation (keeping their offsets, turning with the route). Events at route points change a field of the passing object, or hide it. Start, pause and reset work per route and for all. Since M4 the simulator names unnamed tracks after their route, so that CoT carries a callsign.
  • Outputs: the simulator lists the output channels it finds (section 8.3). A Ground truth output sends every track of the simulation to the chosen ones at each tick; since M5 a Sensor output sends what a simulated sensor detects (section 8.4, ADR-0048).
  • Scenarios (M5): a whole simulation is exported to a scenario file and imported again; since M7 from a Scenario item in the top bar.
  • Unsaved moves (ADR-0041, from spike S6): while a simulation runs, its moves are applied and sent as usual but not written to disk; the journal declares the gaps. The simulator saves its tracks and its own state before a route runs, when it pauses, stops or is reset, and when a user changes the simulation. After a restart it places the tracks from that saved state, paused.

8.3 Data in and out

  • Connection tasks (ADR-0036, section 6) carry every plugin's own sockets. A connection that listens binds to loopback unless an admin chooses an interface; a multicast link needs an interface an admin names. Hosts and ports come from the plugin's settings, never from a browser request, a message or an object's data (ADR-0030).
  • A link is one configured connection of an in or out plugin (ADR-0037), set up by an admin in the plugin's settings: a name, which becomes the data source of what it receives (ADR-0023), a transport and a direction (in, out or both, on one connection). An input link writes into one target layer, chosen with a layer picker in the settings form. An output link sends the objects of its source layers, and never sends an object back to the link it came from.
  • Every output link is also an output channel. Other plugins' server parts find the channels through the SDK and send to them without a layer: the simulator does. A channel says what it can do (for example, send a delete) and which declared fields its protocol uses. A slow output keeps only the latest update per object, never a growing queue.
  • Release limit: each output link has a highest classification it may send, by default that of the server's default label; objects above it, and objects it cannot carry, are skipped and counted in the monitor view.
  • cot sends and receives CoT over a TCP client (TAK Server, with TLS), UDP or multicast. APP-6 maps to the CoT type; the object's name becomes the callsign (M4). Its check against a real TAK Server with WinTAK passed in M3.
  • ais and adsb (M4) were built by the in/out playbook, as its first test, and are input only. ais reads NMEA 0183 AIVDM sentences over UDP or TCP, adsb the SBS-1 (BaseStation) text of a decoder on TCP port 30003. Each keeps one symbol per ship or aircraft, at its last position. The External Services Agent plays recorded AIS and ADS-B data back for their tests.
  • nvg (M7, ADR-0055) reads and writes NATO Vector Graphics, as files and through the NVG web service. An import becomes ordinary objects of the drawing plugins' data types, texts as core.text; a composite's parts stay linked by a relation; a re-import updates objects by their externalRef; and anything in a layer can be written out as NVG.
  • Declared fields (ADR-0038): a plugin declares fields in its own namespace that other plugins' editors may set, such as a CoT team or role. Since M5 it groups them into field sets that an object carries (ADR-0050), and since M6 a data type brings its plugin's sets (ADR-0054). The shared editor in the web SDK shows one set at a time.

8.4 Sensors and GMTI

  • A simulated ground radar (M5, ADR-0048) is a sensor on a simulated track, one sensor per track. It scans a job area in dwells, detects the tracks it covers and sends dwells with their reports to the Sensor outputs a user picks. Its presets go from a wide wedge to a narrow one. Built in M8 and not yet released: the Narrow wedge follows recorded AFSERS radar data, and a Systematic scan mode covers the search area in order and revisits the targets it finds, beside the earlier Random one.
  • gmti sends and receives STANAG 4607 Edition 4 (AEDP-4607). A received dwell becomes detections, drawn with symbology's sensor report symbol (data type gmti.detection, since M6), the platform, and dwell areas; a pairing line joins each detection to its platform (a relation, ADR-0051). Built in M8 and not yet released: one dwell area per revisit, kept until it fades.
  • Fading (M7, CR-0042): a data type may name a stepped fade in its plugin's settings, e.g. full until 10 s, then 5 % steps to invisible at 100 s. The map view draws it once a second, with no change events.
  • Display settings per user (M5, ADR-0046, ADR-0052): each user switches relation lines, dwell areas and sensor coverage on and off, and sets symbol size, labels and the speed vector, in one window.

8.5 Full motion video (M8)

  • In (ADR-0057): fmv receives STANAG 4609 Class 1 motion imagery over UDP, unicast or multicast, through input links in connection tasks. It decodes the ST 0601 and ST 0102 metadata in its own Java code. Each stream becomes two map objects linked by a relation: the camera, an APP-6 symbol at the sensor's position, and its field of view, an open ArcBand aimed at the frame centre. They change at most twice a second, and ST 0102's classification sets their label.
  • The stream channel (SDK 1.8.0, CR-0044): a plugin declares a stream endpoint with a permission, and hands ECore its stream. ECore keeps the latest PAT and PMT and the packets since the last keyframe, so a new viewer sees a picture at once, and limits the viewers per stream and in all. The channel carries any binary stream, not only video. When access by label comes, it also checks each viewer's clearance for the stream's label.
  • Formats: H.264 passes unchanged and plays in every browser. H.265 passes unchanged and is never converted; it plays where the browser can decode it. MPEG-2 is converted to H.264.
  • The web part: the FMV panel lists the streams with their format, size, bit rate and the age of their metadata, and opens each video in a floating window above the map (SDK 1.8.0's FloatingWindow). mpegts.js, the plugin's own dependency, plays it; for it the Content-Security-Policy's media sources add blob: to 'self' (CR-0046). Nothing is fetched from the internet.
  • A renamed link keeps its objects: each item of a settings list gets a stable id that ECore fills in and shows nowhere (CR-0047).

8.6 A simulated camera (M9)

ADR-0058, after spike S10, plans a simulated UAV camera for M9: a camera sensor on a simulated track, with four pointing modes (a fixed point, an object, fixed angles and a sweep). ECore renders its view from orthophotos draped over the terrain, encodes it with ffmpeg and muxes it with exact ST 0601 metadata, because plugins create no threads. An fmv output link sends it as STANAG 4609 over UDP to an address an admin sets, so emcc's own FMV panel sees it as it sees a real camera, through an input link. Imagery comes from a folder and, optionally, a WMS whose tiles the fmv plugin fetches and ECore caches. S10 measured about 1.5 cores per 720p camera on the CPU, and no GPU is needed. Encoding generated frames needs ffmpeg beyond CR-0045, so an amended or new CR comes first, which also chooses the Linux encoder.

9 Data design

The common data model is specified in JSON Schema (draft 2020-12) in model/, owned by the PDA, and is the normative contract for both Java and TypeScript (ADR-0007). Data model 1.7.0 (CR-0042) came with plugin SDK 1.7.0 in M7 and is on main (tag contracts-1.7.0): a data type's stepped fade. Before it came 1.6.0 in M7 (CR-0041, tag contracts-1.6.0: core.text, a plugin's category, symbol palettes, folders relative to emcc, display classes, colour settings), 1.5.0 in M6 (CR-0038, CR-0039: a data type's field sets, sensor report data types, settings fields shown by another field's value), 1.4.0 in M5 (CR-0030, CR-0031: tactical graphics' amplifiers and points, field sets, vessel symbols, relations, capabilities, local folders), 1.3.0 in M4 (CR-0028: a layer's lock and its rejection code), 1.2.0 in M3 (CR-0025, tag contracts-1.2.0: a layer's workspace, declared fields, connections and workspaces in the manifest), 1.1.0 in M2 (CR-0014: style fields), 1.0.0 in M1 (CR-0010: data types, data sources and time) and 0.1.0 in M0. Every version since 1.0.0 is a compatible addition, so no stored data needed a migration. In M8, SDK 1.8.0 changes no object or layer schema; of the schemas in model/ it changes only the plugin manifest's, which is versioned with the SDK: an optional icon, and annotations for the settings forms (groups, hints, units and a stable id per list item). Frozen versions change only through change requests. This section summarises it. The normative text is model/README.md with the schemas; documents/design/emc2-data-model-v0.html describes version 0.1.0 only.

  • Positions are WGS84 [longitude, latitude] or [longitude, latitude, altitude]; altitude is metres above the ellipsoid (HAE). Distances are geodesic metres; bearings are degrees clockwise from true north.
  • Edges are geodesic (ADR-0019): the edge between two positions is the shorter geodesic, whatever the projection. Renderers densify edges, so a shape looks the same in Web Mercator and polar projections. Geometries are never split at the antimeridian, which differs from GeoJSON. A polygon that encloses a pole cannot be expressed; a Circle or ArcBand around the pole can.
  • Ring orientation is normalised so that the inside lies to the left of the outer ring, determined along the geodesic edges, not in longitude and latitude.
Coordinate rule: coordinates are always WGS84 in longitude, latitude order – in code, on the wire and in storage. Projections (Web Mercator, polar stereographic and others) and coordinate formats (decimal degrees, DMS, UTM, MGRS) apply only at display, input and format boundaries. Every converter is tested with a point where latitude ≠ longitude.

9.5 Security label

Every object and every layer carries a confidentiality label in the structure of STANAG 4774 (ADatP-4774): a policy identifier, a classification (a string, because the values depend on the policy), optional categories (tag name, type, values) and optional creation and review times. A default label comes from the server configuration; the SDKs give it to plugins for everything they create.

  • Object and layer labels (ADR-0020): a user sees an object only if cleared for both its label and its layer's label, and sees a layer only if cleared for its label. Stored labels are not constrained against each other, so no data ever needs a migration.
  • When: labels are stored, shown and forwarded. Access control based on them comes after M1 (owner, 2026-10-10), with security policy definitions (the order of classifications and the meaning of categories, in the style of a SPIF) as configuration.
  • Binding (STANAG 4778) is not part of the model; it sits behind a LabelBinder interface (section 10.3). Before the real binding is built, the JSON mapping is checked against the official ADatP-4774 XML schema.

9.6 Extensions

A plugin stores its own data on an object under its plugin id. Only that plugin writes it; everyone else, including ECore and outgoing plugins, forwards it untouched, so no information is lost on its way through the system (ADR-0007).

  • On update, the object store applies only the requesting plugin's own namespace: present replaces it, {} removes it, absent keeps it. All other namespaces come from the stored object; foreign namespaces in a request are ignored, never rejected (ADR-0018).
  • On create, all namespaces are accepted, so an imported object keeps the extensions it was exported with.
  • Exact numbers: extension data keeps every number exactly as written, even beyond double precision (CR-0004).
  • Declared fields (since 1.2.0, ADR-0038): a plugin may declare fields in its own namespace, with a type, label, unit and limits, and mark them editable by others. A change request names the fields it sets (fields); the object store checks each against its declaration and applies only those, so other plugins' editors can set them without touching the rest of the namespace.
  • Field sets (since 1.4.0, ADR-0050, ADR-0054): named groups of a plugin's declared fields. An object lists the sets it carries; a request may add a set, and nothing removes one. Since 1.5.0 a data type names its sets, and the store adds them to a symbol on a create and on a change of data type.

9.9 Numbers, types and versioning

  • Numbers: core numbers have double precision (IEEE 754), as the SDKs hold them, and are compared as doubles. Only free-form JSON – extension data and plugin settings – keeps exact decimals (CR-0004).
  • Types: the Java records and TypeScript types are written by hand in the SDKs. ECore maps JSON with Jackson and validates incoming documents against the schemas. A contract test checks the mapping against every example in model/examples/.
  • Versioning: one SemVer version for all schemas. A minor change keeps every valid document valid; anything else is major and needs a migration of stored data. No field may change its meaning in a minor version. Version 1.0.0 since M1; compatible additions are 1.x: 1.1.0 in M2, 1.2.0 in M3, 1.3.0 in M4, 1.4.0 in M5, 1.5.0 in M6, and 1.6.0 and 1.7.0 in M7. The plugin manifest schema is versioned with the SDK instead, 1.7.0 on main and 1.8.0 being built. Each release was built in steps on an integration branch, reviewed by the ACA and frozen by the owner before it reached main.
  • History (later): the event log is append-only and never rewritten. Old events are read through upcasters that turn them into the current form.

Deferred (each a minor change later): layer groups; event ordering across several servers; polygons around a pole. Texts, deferred for NVG until M7, are core.text since 1.6.0.

Data types and data sources (since data model 1.0.0, ADR-0023): every object has a dataType and a dataSource.

  • dataType is the kind of information the object is, for example cot.cot, and is separate from type, which says what the object is on the map. Plugins declare their data types in their manifests, prefixed with their plugin id. ECore builds the list at start-up and has one built-in type, core.general.
  • dataSource is where the object came from: manual for drawn objects, or the name of the input link it came through.
  • Behaviour such as expiry and fading is set per data type; since 1.7.0 a data type may name a stepped fade in its plugin's settings (section 8.4).
  • Since 1.5.0 a data type may also bring field sets, be left out of the editors' choice (manual: false), or mark its objects as sensor reports.

10 Cross-cutting concerns

10.1 Coordinates and projections

The map view uses OpenLayers with proj4 definitions from configuration, so any projection with a proj4 definition can be used, including polar stereographic. Background map plugins declare the projections they support. Reprojecting Web Mercator tiles does not reach the poles. Since M1, a background drawn from Natural Earth vector data (public domain, CR-0009, ADR-0025) works in every projection, including polar ones, and needs no internet. Since M4, WMS servers add detailed maps, polar ones included where the server serves polar projections natively: basemap-wms passes the maps through its server part, and a WMS background is offered only in the projections its server lists, never reprojected (ADR-0035). An admin picks each background's layers from the server's list in the plugin's own settings panel. Coordinate formats are provided by the coordinates utility plugin (proj4js and mgrs in the browser; Proj4J and NGA mgrs-java on the server). Since M5 the terrain plugin computes range, bearing and viewsheds from local DTED height data (ADR-0049); a demo zip of the Sundsvall area ships next to the release (CR-0037), and GeoTIFF height data comes in M9.

10.2 Persistence and local files

The persistence manager is the only path to storage. It stores objects and layers (from change events), plugin documents (namespaced JSON), settings, and since M2 each user's own documents, such as bookmarks, setups and since M5 display settings (ADR-0027, ADR-0046). A file store is used today; PostgreSQL + PostGIS follows in M9 (ADR-0024), with the question whether it keeps an append-only event table for history. Writes are write-behind: a crash may lose the last moments of changes, which is acceptable for now. A running simulation's moves are not written at all (section 8.2).

Local files (since M5, ADR-0049): a plugin reads files only from the folders its manifest declares, through the SDK, read only and confined to the folder; an admin sets each path, absolute or, since M7, relative to the emcc folder (%emcc%/). The Monitor shows them.

The file store keeps a snapshot of the picture (snapshot.json, replaced atomically) and a journal with one change event per line (journal.jsonl), compacted into a new snapshot every 10 000 events. On load every document is validated; a cut-off last journal line is repaired or dropped with a warning, and any other damage or an undeclared gap in the sequence stops the start rather than losing data silently. Stored documents are written in the canonical form (rule 13), so they are deterministic.

10.3 Security

Since M1, login uses OpenID Connect against Keycloak, run on the server side (ADR-0022). The edge runs the Authorization Code flow with PKCE as a confidential client, and tokens never reach the browser. The browser holds only a session cookie, which also authenticates the WebSocket, so the Content-Security-Policy stays 'self'. Groups from the IAM map to emcc permissions through configuration, and plugins declare and check their own permissions through the SDK. The server enforces every permission; the browser only hides what a user may not do (section 7).

A no-login mode stays available for portable use, demonstrations and tests:

  • There is one local user, with all permissions.
  • A warning is logged at every start, and the browser shows a "No login" mark.
  • The server listens on loopback only, unless a second setting explicitly allows other addresses.
  • A server configured for login never falls back to it.
  • Labels: every object and layer carries a STANAG 4774 label from the first version. Filtering by label comes after M1 and follows ADR-0020 (section 9.5). STANAG 4778 binding sits behind a LabelBinder interface with a mock implementation for now.
  • Browser: the edge serves the web client with a Content-Security-Policy that allows only the emcc server ('self'), so no web part can contact or leak data to another host (ADR-0030).
  • Edge hardening (M0): the API and the live picture answer only under the host names the server is configured for, against DNS rebinding. The live picture limits message sizes, request rates and the number of sessions.
  • Workspaces and the layer lock (M3, M4): a declared workspace's layers reach only users with its view permission, and need its edit permission for changes (ADR-0039); a locked layer refuses users' changes to its content (ADR-0042). Both are enforced by the server.
  • Connections and outputs (M3): a plugin's listening connection binds to loopback unless an admin chooses otherwise, and each output link has a highest classification it may send (section 8.3).
  • Video (M8): every stream viewer is checked by the server for the plugin's view permission, and, once access by label comes, for the stream's label. Only ECore starts the ffmpeg process. The Security Review Agent's next review looks at the stream endpoint, ECore's process and ffmpeg as a parser of outside data.
  • Reviews: the Security Review Agent's first review, of everything on main after M7 with its dependencies, runs during M8 and reports to the owner only (T-046).
  • Plugins are trusted (ADR-0003). The class loader per plugin avoids dependency conflicts; it is not a security sandbox. A server part reaches outside hosts only through the SDK. Its outbound HTTP and its own connections may go to any host (owner, 2026-10-18 and 2026-10-22), but never to one taken from a browser request, a message or an object's data (ADR-0030); ECore checks no host, and the reviews check the plugins.

10.4 Logging and monitoring

Logging uses SLF4J; each plugin's log entries are tagged with its id, and an admin can set one plugin's level. Since M7 a release also writes the log to logs/emcc.log, rolling, so that it can be collected and analysed. Since M1 the monitor view (admins only) shows ECore's own counters, polled every two seconds; since M3 each plugin's connection tasks and links, with their rates, the addresses they listen on and the objects they skipped; since M5 the declared folders and capabilities; and in M8 the streams and their viewers. OpenTelemetry export is planned for M9 (ADR-0013). Per plugin, the number and state of workers, mailbox depth, message rate, handler time, hung events and refusals at the caps are exact. Memory is not shown per plugin (spike S5): ordinary workers share virtual threads, so the monitor shows the JVM's total allocation rate and ECore's share only. Each plugin reports its status (OK, DEGRADED or FAILED); ECore may set a status too, and the worse of the two counts. The monitor view shows live health; external dashboards are optional and self-hosted.

10.6 Client rendering

Drawing the full 100 000 objects needs hardware-accelerated WebGL, i.e. a GPU (ADR-0017, from spike S2). Without one, about 10 000 individually drawn symbols stay usable; above that, the area of interest's budget and its clusters (since M1) keep the map usable. Changes reach the map view in batches, which it applies at its own cadence. The map view detects software rendering at start-up and tells the user and the monitor view; it never drops objects silently. Since M5, tactical graphics are drawn by mil-sym-ts in one Web Worker, loaded only with the first graphic, so a zoom does not block the map (ADR-0043; spike S1: 1 000 graphics redrawn in 51–129 ms). Since M7 the map view draws a data type's stepped fade once a second from the clock, with no updates from the server. Video is decoded by the browser itself, through Media Source Extensions (section 8.5).

10.7 Repository and build

One git repository holds everything, with exactly one owning agent per folder (ADR-0015). The Java parts form one Maven multi-module build in server/, including the plugins' server parts. The TypeScript parts are npm workspaces of the repository root – the shell, the web SDK and every plugin's web part – with one lock file (CR-0006). Shared browser libraries are provided once by the shell through an import map, and plugin builds treat them as external (spike S4). Scripts in tools/ build, test and start the whole system on Windows and Linux. Each contract release is built in steps on an integration branch (integration/sdk-v1.x) and reaches main with its milestone. The Integration Test Agent's full run (over 300 flows in real browsers against the real server, the login specs against Keycloak included) or a quick run of a few minutes gates each merge. Release candidates are also tested against the external services (TAK Server, the NVG service) and with the release zip itself.

11 Deployment

Deliverables are self-contained: a Java runtime image built with jlink/jpackage, the built web client, the plugins, configuration, and from M8 the ffmpeg binary in the release's own tools folder. Installing them requires no network access. Every function has a way to work offline: for maps that is Natural Earth. Internet-only sources such as basemap-osm are separate plugins that can be left out of a disconnected installation (ADR-0030).

Each milestone ends with a release candidate the owner tests on another computer: a zip for Windows x64 with its own Java runtime, the demo scenario, the user manual (since M5) and a README (M1; M2 RC1; M3 RC2; M4 RC2; M5 RC2, 2026-11-10; M6 RC1, 2026-11-11; M7 RC3, 2026-11-12). The Sundsvall height data ships as a separate demo zip next to it (CR-0037). Its start script runs in the no-login mode, or, from M4 RC2, against a Keycloak realm it is given. M7 was the first release for outside users, who demonstrate emcc in a controlled environment; its readme carries a disclaimer and makes no promise that stored data carries over. From M7 the release writes its log to logs/emcc.log. Linux releases and tests come in M9.

For development and tests, the External Services Agent runs the external services on the development computer, each portable in its own folder with start, stop, status and logs commands: a TAK Server, a GeoServer WMS server, Keycloak with a lasting demo realm (since M4), an NVG service, and playbacks of recorded AIS, ADS-B, GMTI and FMV data, with a replay manager (external/). They are never part of a release.

Known limits of the current design:

  • A polygon that encloses a pole cannot be expressed (rule 10); use a Circle or ArcBand.
  • A handler stuck in an endless computation is detected and reported, but cannot be stopped: virtual threads are not pre-empted. It keeps one carrier thread busy until the server restarts.
  • Write-behind persistence may lose the last moments of changes in a crash; a running simulation is restored from its last save, paused.
  • Connection tasks run on platform threads until the JDK fixes JDK-8334574 on Windows; the cap on tasks per plugin keeps their number bounded.
  • A receiving multicast link stays stopped until an admin names a network interface.
  • A layer stays in its workspace; objects move and copy between layers of the current workspace only (ADR-0053).
  • Without a GPU, about 10 000 individually drawn symbols stay usable; more need the area of interest's clusters (ADR-0017, spike S3).
  • Labels are still cosmetic: access by label, and each stream viewer's clearance for the video's label, come later (ADR-0020, ADR-0057).
  • H.265 video plays only in browsers that decode it; it is never converted. Releases are Windows x64 only until M9.
