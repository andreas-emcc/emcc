# ACA review of CR-0025: SDK 1.2.0 and data model 1.2.0 (T-078)

- **Reviewed:** `docs/change-requests/CR-0025-sdk-and-data-model-1-2-0.md` on `integration/sdk-v1.2` at `e24d649` (`pda/cr-0025` `3f92e72`), status Proposed, nothing built.
- **Against:** ADR-0036 to ADR-0040, `docs/architecture/m3-simulator-decisions.md` (Q1 to Q30, A1 to A18), the overview's normative sections, and spike S6's answer (`spikes/s6/README.md`, merged as `8691a1c`).
- **By:** the ACA, 2026-10-22. Owned by the ACA. This folder holds the ACA's reviews of contracts and plans; it is not `docs/reviews/`, where the CRA's and SRA's reports stay with the reviewer until the owner releases them (`CLAUDE.md` section 8).

## Verdict

**CR-0025 fits ADR-0036 to ADR-0040 and the owner's answers.** It covers every contract consequence the ADRs name, keeps every addition optional for plugins built for 1.1.0, and takes the owner's choices for the fade list, the geodesics and the channels.

**Recommended: approve it with the seven changes R1 to R7 written into the CR first.** They are small edits by the PDA. R1, R2, R3, R5 and R6 close gaps in what the ADRs and the normative rules require (R3 keeps overview 4.1 true, R6 keeps rule C6); R4 and R7 complete a detail. **The owner approved R4 on 2026-10-22.** The notes N1 to N9 can go into the build, the design pattern and the briefs.

**Updated 2026-10-22:** the PDA has revised the CR twice: R1 to R7 and the notes are in, and part 8 carries the owner's spike S6 decision with the CDA's store design. **The recheck's verdict is in "Recheck of the revision" below: approve CR-0025 once seven text edits are made.**

Spike S6 needs no addendum: it found that the store and the live picture carry 1 000 tracks at 1 Hz on the ordinary path, and recommends no batched submit in SDK 1.2.0 (its proposals 3 and 4). Its proposal 1 was persisting moving objects less often. The owner decided instead on 2026-10-22 that a running simulation's moves are not written to disk at all (ADR-0041).

## The seven points the CR asks about

1. **Record constructors.** Keeping each record's 1.1.0 constructor is enough for a 1.x release, as it was for `Style`.
   - Construction and accessors stay source and binary compatible. A record pattern compiled against 1.1.0 still runs, since it calls the accessors. Only recompiling such a pattern fails.
   - The ACA found no record pattern or deconstruction of `LayerContent`, `ChangeRequest`, `Change` or `ObjectQuery` on `integration/sdk-v1.2`.
   - See N5 for a test.
2. **`x-emc2` in settings schemas.** It fits ADR-0037 point 2 and JSON Schema 2020-12, where an unknown keyword is an annotation that validators ignore. ECore's `SettingsSchema` pre-check refuses only an outside `$ref` or `$dynamicRef`, `$id` and another dialect (checked in the code), so it lets the keyword through. How the validator library itself treats the unknown keyword is not shown by that code: the CDA's tests in T-081 should compile and validate a schema with `x-emc2`, and check that nothing fails or logs noisily. See N3 and N7.
3. **`PluginRules`.** Agreed: socket classes only in classes that implement `ConnectionTask`, and their nested classes.
   - A task as a class rather than a lambda is a fair price for a rule the build can check. The lambda in ADR-0036's sketch was a sketch, not the API.
   - Add R6, name resolution, to the same rule. See N4.
4. **The layer picker's "New layer".** Agreed: the plugin keeps each link's actual layer in its documents, and creates it when the setting names none or the layer is gone.
   - That is what ADR-0037 point 2 asks ("made again at the next data").
   - The plugin knows the layer's label and the link's data. ECore creating layers from settings would move plugin logic into ECore.
   - See N1.
5. **CR-0020 in the release.** Agreed; it is the ACA's view of 2026-10-22. The route editor ends its `draw` and `edit` when its panel closes, another route is chosen, or the route is deleted meanwhile. The owner decides CR-0020 itself with the batch.
6. **Rule 5's exception for a layer's absent `workspace`.** Necessary, and for a security reason beyond convenience.
   - Under rule 5, a field missing from an update is removed. A 1.1.0 plugin's layer update, for example a rename in `layer-panel`, would remove `workspace` and move a simulation layer into View. The ground truth would then be shown to everyone, against ADR-0039 points 5 and 7 and Q25.
   - The exception prevents that. See R2 for an explicit `core.view`, and R1 for objects.
7. **Input channels "defined"** read as specified in the CR and reserved in `sdk-v1.md`, not in the 1.2.0 API. Agreed.
   - ADR-0037 point 5 says they are defined with output channels and built when a first plugin needs them, and no plugin does in M3.
   - The specification is consistent with output channels (coalescing by object id).

## Changes to write into the CR (R)

- **R1. An object moved to another workspace's layer** (part 5, "Changes"; ADR-0039).
  - The CR says a change to a workspace's objects needs its edit permission. It does not say what an object update that changes `layerId` to a layer of another workspace needs. Such a move could carry the ground truth into View, or View's objects into a simulation.
  - Recommended: in M3 such an update is rejected with `VALIDATION_FAILED`, as a layer's move is. ADR-0039 point 5 keeps layers in their workspace, and moving or copying comes later.
  - Write the rule next to rule 5's exception in `model/README.md`, and in the SDKs' documentation.
- **R2. An explicit `core.view` on an update** (part 5).
  - The CR treats it as absent, so it keeps the stored value. On a simulation layer, a request to move it into View then succeeds without moving it, which the requester cannot tell.
  - Recommended: the store keeps `core.view` as absent, so View's layers carry no `workspace` (writers may send it, readers accept both, by analogy with rule 13's empty values). On an update it compares an explicit `workspace`, `core.view` included, with the stored one, and rejects a different one. Only an absent `workspace` keeps the stored value. Plugins may then pass `ctx.workspace.current.id` as the CR says.
- **R3. GeographicLib on ECore's class path only** (part 7, "Where it goes").
  - A plugin's class loader shares only `dev.emcc.sdk.` and JSpecify with ECore (`PluginClassLoader.SHARED`). The SDK's own classes, loaded by ECore's class loader, find GeographicLib there.
  - So ECore keeps the jar on its own class path and does **not** share it with plugins. The library then stays behind the SDK's types by construction, and a plugin may still bundle its own copy without a conflict.
  - `PluginRules` should forbid `net.sf.geographiclib` in plugin code. The SDK's dependency brings it to a plugin's compile class path, and the rule makes a direct use fail in the build instead of at runtime.
  - Overview 4.1's class loader "which only sees the Plugin SDK and the plugin's own jars" then stays true.
- **R4. Multicast's default interface** (part 2, "Listening addresses"; ADR-0036 point 4).
  - The default is the loopback interface. Loopback does not carry multicast on every platform: Linux's `lo` has no `MULTICAST` flag by default, and Windows' loopback pseudo-interface is uncertain.
  - Write the fallback into the CR: unless a check on Windows and Linux in build part 2 shows that loopback carries multicast on both, a multicast link without an `interface` stays stopped, and its status says that an admin must name one. Nothing is then open to the network by default, which is what ADR-0036 point 4 is for.
  - The ITA's multicast test peers then need a named interface.
  - This is stricter than the letter of ADR-0036 point 4 and Q2 ("binds to loopback by default"), for multicast only, though it keeps their intent. **The owner approved it on 2026-10-22**; the build's check records the platforms and the case tested.
- **R5. The listening addresses in the monitor view** (part 2; ADR-0036 point 6).
  - ADR-0036 point 6 requires the monitor view to show the addresses each plugin listens on, and the SRA compares the listening ports with the settings.
  - With free-form `detail(key, value)`, that depends on each plugin's choice of key. Add `listening(SocketAddress)` and `peer(SocketAddress)` to `TaskContext`, or reserve those two detail keys, so the monitor view can list them for every plugin.
- **R6. Name resolution only in connection tasks** (part 2; rule C6).
  - Resolving a host name blocks on DNS: `InetAddress.getByName` and `getAllByName`, and the constructor `new InetSocketAddress(host, port)`, which resolves at once.
  - `ListenAddress.from` and every check of the settings must only parse. Resolving happens in the task.
  - `PluginRules` should allow those calls only where sockets are allowed. Outside tasks, `InetSocketAddress.createUnresolved` and IP literals stay possible.
- **R7. The highest classification across policies** (part 3; ADR-0037 point 8).
  - Labels name their policy, and the order of classifications is per policy. A bare text setting cannot say which policy it means.
  - Make the setting `{policy, classification}`, as `cot`'s label setting is, with the default from `defaultLabel()`.
  - State that an object whose label has another policy counts as above the limit and is not sent, as an unknown classification already does.

## Notes for the build, the design pattern and the briefs (N)

- **N1. "New layer" in the cot brief and the design pattern.**
  - Say whether two links that name the same new layer share one; ADR-0037 point 2 allows sharing, so one is the natural reading.
  - Have the plugin report each link's actual layer in its status, since the setting keeps showing "New layer".
- **N2. A TCP server's accept loop** catches the cap's `IllegalStateException` from `startChild`, closes the new client and counts it. Otherwise one flood fails the server task, and its restart drops every client.
- **N3. One annotation keyword.** `"x-emc2": { "kind": "layer", "allowNew": false }` leaves room for later kinds without adding more `x-emc2-*` keywords. Optional.
- **N4. HTTP stays out of tasks.** `PluginRules` says explicitly that `java.net.http` and URL connections stay forbidden inside tasks too (rule C6: HTTP through the SDK). The design pattern shows datagram code in a nested helper class, since a helper outside the task cannot take a `DatagramSocket`.
- **N5. A compatibility test in the SDK** builds each of the four records with its 1.1.0 constructor and checks the new component's default: no workspace (View), no fields, no workspace filter.
- **N6. GeographicLib-Java 2.1.** The ACA did not verify its version, release date, size or checksum. The MCA's licence check verifies them when it is installed, and the owner's approval covers the dependency.
- **N7. Settings reach every browser** (overview 4.11), and with them the layers named in links. That is fine in M3, where the picker offers View's layers only. It needs another look when the picker offers a declared workspace's layers.
- **N8. Channel ids are the plugin and the link name**, and the simulator saves its chosen outputs by them (ADR-0040 point 2). The simulator's brief should show a chosen output whose link was renamed or removed as missing, rather than dropping it silently.
- **N9. `ObjectQuery` without a workspace filter means every workspace** (CR part 5), while every other default is View. Server parts are trusted and unfiltered (ADR-0039 point 7), and today only `cot` queries the store, by external reference. The design pattern should say that a server part which passes objects on to browsers or outputs filters by workspace itself.
