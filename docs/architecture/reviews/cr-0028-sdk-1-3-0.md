- **Against:**

## Verdict

**CR-0028 fits ADR-0042, ADR-0035, ADR-0038 and the M4 plan.**
- It covers every contract consequence of ADR-0042, and the plan's five parts.
- It keeps every addition optional for plugins built for 1.2.0.
- It answers the plan's question on icons over the map. The shell already stacks a corner's overlays in a column, sorted by `order`.

**Recommended: approve it once R1 is written in.** R1 is a short text edit by the PDA. N1 to N4 can go into the build.

## The owner's three questions (the ACA's recommendation first)

1. **An update without `locked` keeps the stored value, as for `workspace`: yes.**
   - Otherwise every writer built before 1.3.0 unlocks a layer by accident. That includes:
     - `layer-panel` until T-099;
     - the Settings list's Layers entry;
     - any server part that builds a `LayerContent` with the 1.2.0 constructor.

     It even happens with the draw-order change that the lock lets through (ADR-0042 point 3).
   - It costs one more exception to rule 5, beside `workspace`'s. A 1.3.0 writer clears the lock with an explicit `false`.
   - It is a detail of ADR-0042 point 1 ("stored and sent like the layer's other fields"), not a change to the decision. Once the owner decides, the ACA records it as a dated line in ADR-0042's index row, as for earlier details.
2. **The version step right after build step 1: yes.** This holds under four conditions, as for 1.2.0:
   - nothing reaches `main` before the owner freezes the whole release. `main` gets it in one merge, with the tag;
   - plugins that declare `^1.3.0` merge only into `integration/sdk-v1.3`;
   - if a later step changes a member from step 1, the PDA says so in that step;
   - the owner gives the exception of 2026-10-26 again: the MCA sets the pins and the lock file, and the CDA sets ECore's version lines.

   PCA-layer-panel, PCA-map-view-2d and PCA-draw-symbols can then build against 1.3.0 at once, instead of waiting for WMS and the fields list.
3. **CR-0023 as written: yes.** Checked against:
   - **ADR-0035 points 1 to 7:** the `wms` source, tiles or one image, native projections only, the admin's own panel, and no login or tile cache.
   - **ADR-0030:** the browser asks only the plugin's endpoint. The server part builds each request itself, to the host in its settings, and never forwards the browser's query.
   - **Overview 4.4:** the panel's own endpoints require `settings.admin`.
   - **ADR-0007:** `wmsGetMapUrl` swaps the box only for WMS 1.3.0 in EPSG:4326, tested where latitude ≠ longitude.
   - **ADR-0039:** nothing conflicts with workspaces.

   Its "SDK 1.2.0" and "M3" read as 1.3.0 and M4, as CR-0028 says and ADR-0035's index row already notes.

## Against the ADRs and the plan

- **ADR-0042:**
  - **Points 1 and 2:** the field, and the layer's edit permission to set or clear it.
  - **Point 3:** the CR's "an update whose result differs from the stored layer only in `locked` and `drawOrder`" is the right reading. It is checked on the result, after an absent `locked` and `workspace` are kept.
  - **Point 4:** every request from a web part is a user's in the web fake. `FakeStore.applyAs(by, user, change)` stands for a browser's request, as it already does for permissions.
  - **Point 5:** `apply` and `applyAs(by, change)` pass, and the Javadoc says a server part never gets the code.
  - **Point 6:** see R1.
  - **Point 7:** the code, details that name the layer, and no event.
  - **Point 8:** the brief edits in the Impact.
- **ADR-0038 with BO:** part 3 is what the index row records. The props stay, and `changedFields` still names only what the user changed, so blind forwarding (point 3) is unchanged.
- **The M4 plan:** parts 1 to 5 are as planned. The `FakeChannels` fix is extra and harmless.

## R1, before approval: where `LAYER_LOCKED` comes among the store's answers

**The problem.** The CR says "`VALIDATION_FAILED` and `PERMISSION_DENIED` come first, then `LAYER_LOCKED`, then the store's other content checks". That is not the order the store has (`ObjectStore.apply` on `main`):
1. the answers for what a user may not see (ADR-0039 point 7);
2. `PERMISSION_DENIED`;
3. `ENTITY_NOT_FOUND` for a missing entity;
4. the rule checks: `LAYER_NOT_FOUND`, and `VALIDATION_FAILED` for the model's rules and the workspace;
5. the declared fields;
6. `LAYER_NOT_EMPTY`.

Only the schema's `VALIDATION_FAILED`, when the request is decoded, comes before the permission. The CR's sentence also leaves out where the lock check goes against `ENTITY_NOT_FOUND` and `LAYER_NOT_FOUND`. The lock check needs both: it reads the stored object or layer, and the layer that a create or a move names.

**Proposed text:**

> `LAYER_LOCKED` comes after the permission check, and after `ENTITY_NOT_FOUND` and `LAYER_NOT_FOUND` have found the entity and the layers it names. It comes before the rule checks (`VALIDATION_FAILED`), the declared fields and `LAYER_NOT_EMPTY`. The schema's `VALIDATION_FAILED` at decoding stays first. Both fakes keep the same order.

This keeps ADR-0042 point 6 ("after the permission check"). A request to a locked layer then gets one answer, whatever else is wrong with it.

## Notes for the build

- **N1:** in `change-rejection`, the `details` description says "For VALIDATION_FAILED". It now covers `LAYER_LOCKED` too, and `code`'s description gains it.
- **N2:** the `path`, stated as a list:
  - **`/data/layerId`:** an object update in the locked layer, since an update carries every core field (rule 5), `layerId` among them. The same holds for a create in the layer and a move into it;
  - **`""`:** a move out, an object's delete, and a layer's update or delete.
- **N3:** a layer may be created with `locked: true`. No lock check applies to a layer's create, since nothing is stored yet; only its permission is checked. One line in `model/README.md` keeps the CDA and the fakes alike.
- **N4:** the Impact's ACA line: overview 4.4 already states the rule. It was merged with ADR-0042 as `d0eaa70`.

**For the MCA, not the CR.** The board has no row yet for the lock in `draw-symbols`, `draw-shapes` and the simulator's route editor (ADR-0042 point 8; the CR's Impact names them). T-099 is `layer-panel` only.
