# ACA review of SDK 1.4.0 part 3: field sets, vessel symbols and relations, and its brief edits

- **Reviewed:** `pda/sdk-1.4-part3` at `e4c83e8` (from `integration/sdk-v1.4` `f75085f`): the model in `dda8b1d`, the Java SDK in `a32ae24`, the web SDK in `d85f80d`, the docs in `71cdb23` and `887af08`; the brief edits in `47cb8b9` (`cot` functions 23 to 25, `ais` section 10, `adsb` section 10, `draw-symbols` functions 27 to 29, `symbology` functions 11 to 13, `map-view-2d` function 33, the playbook v3).
- **Against:** CR-0030 part 3 (owner GS, 2026-11-05; the Decision's four-digit vessel code and Q3); CR-0031 (owner HL, 2026-11-06; Q1 to Q3); ADR-0047, ADR-0050 and ADR-0051; `model/README.md` rules 5, 13 and 16; ECore's `ObjectStore` and the shell's settings form, read for the two points below that depend on them.
- **By:** the ACA, 2026-11-06. The PDA reports the tests green (model 104, Java SDK 109, test kit 295, web SDK 287) and ECore and the app compiling against the branch; the ACA did not run them.

## Verdict

**Approve part 3 for `integration/sdk-v1.4`, and the seven brief edits for the owner's approval.** The contract matches CR-0030 part 3 and CR-0031 as the owner decided them, every addition is optional for plugins built for 1.3.0 (older constructors, optional members, throwing defaults), and the two departures from the CR's wording are improvements that need a dated note (R4). The remarks block nothing; R2 and R3 are the ones for the owner's eye.

## The PDA's seven points

| | Point | ACA |
|---|---|---|
| 1 | **Rules 17 and 18, after rule 16** | **Right, and checked against ECore.** `ObjectStore.create` checks the content (rules 3, 14, 15), then the external identity (rule 16), then the declared fields; `update` has no rule 16. So 17 and 18 between 16 and the fields is ECore's own order, and the fake store has the same. Rule 17 before 18 is a free choice; both reject with `VALIDATION_FAILED` and a path, so a client sees the first problem either way. See R5 for rule 16's own order bullet. |
| 2 | **`manifest-field-set-unknown-field` invalid by rule 18, not by the schema** | **Right.** JSON Schema cannot compare one array's strings with another array's objects, so the check is ECore's at plugin load, as rule 18's third bullet says. CR-0030 listed it among the invalid examples; a dated note in the CR (R4). |
| 3 | **`catalog()` stays APP-6's; `vesselGroups()` lists the ship types** | **Right.** The APP-6 catalogue is a tree of symbol sets and entities with SIDC parts; a two-digit ship type with a group and a colour does not fit it, and `draw-symbols` 28 and a legend need exactly what `VesselGroup` carries. The CR's "catalog takes it" was a sketch; a dated note (R4). |
| 4 | **`context.fieldSets()` and `relationKinds()` as throwing defaults** | **Right,** as `declaredFields()` was in 1.2.0, abstract at the freeze; the web's `ctx.fieldSets` and `ctx.relationKinds` optional the same way. The cost is a runtime failure instead of a compile error for a plugin on an older ECore; in M5 every caller is built in the same integration as ECore's part 3 half, and the test kit's fake has both. |
| 5 | **`cot` adds its own set without the `ObjectWriter`** | **Right.** `content.withFieldSet("cot.unit")` on every create and update is what the writer does inside (`ObjectWriter.build`), and rule 5's third exception keeps the sets other plugins added. An object from before M5 gets the set at its next event, which ADR-0050 point 4 allows. One sentence to add: R1. |
| 6 | **`ais`'s symbol type: a stored link without the key is read as APP-6** | **Right by ADR-0047 point 7, and the shell's form bears it out.** `emptyOf` fills a schema default only into a list item the admin adds (`SchemaForm`'s "Add"); an existing link without the key shows the choice as not set and is not rewritten. So the brief's check is of the shell's form (the CDA's, T-098), not of ECore, and the setting's description must say what absent means, since the form's hint reads "Default: vessel" (R2). |
| 7 | **The vessel group colours** | **A sound proposal, with one thing for the owner to look at in the browser** (R3): four of the nine fills are near the four identity outline colours, and in C2 the identity is what must show first. |

## Remarks (no approval needed)

| | Remark | For |
|---|---|---|
| R1 | **`cot` forwards `relations`.** Function 23 builds each update's content from the CoT event; one sentence says it carries the stored object's `relations` as `draw-symbols` 29 does, so a later kind on a CoT track (Link 16, ADR-0051 point 10) is not emptied by the next CoT report. Nothing carries one in M5, so this is cheap now and a hunt later. | PDA (brief), PCA-cot |
| R2 | **`ais`'s `symbolType`: say what absent means, in the schema.** The shell's form fills the default `vessel` only into a link the admin adds, shows an existing link without the key as not set and does not write the key for it. So the brief's check in section 10 is of the shell's form, not of ECore. The setting's `description` says "absent: APP-6, for links stored before M5", because the form's hint under the field reads "Default: vessel", which would otherwise mislead the admin. | PDA (brief), PCA-ais |
| R3 | **The group fills against the identity outlines.** Cargo green, tanker red, passenger blue and high-speed yellow sit near the neutral, hostile, friend and unknown outline colours, so a neutral cargo ship is green in green and a hostile tanker red in red, with a 2 px outline to tell them apart. The ACA recommends the owner's browser check look at exactly those four, in both looks, and that `symbology` 12 allows a 1 px gap in the look's ground colour between fill and outline if the identity does not read; the convention of the tracking sites (which the fills follow) is worth keeping otherwise. | Owner, PDA (brief), PCA-symbology |
| R4 | **The CR's notes and the joint run.** CR-0030's Decision gets a dated note for the two departures (`catalog()` unchanged and `vesselGroups()` added; the manifest example invalid by rule 18, not by the schema) and the build's limits (32 sets per manifest, 64 per object, 16 kinds). The run into `integration/sdk-v1.4` is one merge of the SDK part 3 with `symbology`'s `validate.ts` fix, `draw-symbols`' `symbolParts.ts` fix and the two plugins' "Other fields" tests, as the PDA found; and the CDA's part 3 half (`ModelJson` for `fieldSets` and `relations`, `ObjectStore`'s rules 5, 17, 18 and move check, the manifests' two lists, the two context lists) goes before the first writer of a set (`cot`, `ais`, `adsb`, the writer's `fieldSet`), since such an object would not decode until then, as part 2's R7. | MCA |
| R5 | **Rule 16's order bullet.** It still ends "then rules 14, 15 and 16"; add "then 17 and 18, then the declared fields", so the one bullet that gives the order is complete, and rule 17's own bullet points to it. | PDA |
| R6 | **The web `FieldSet`'s `plugin` and `name`.** The manifest has only `id`; the shell derives `id` (full), `plugin` and `name`. "For the other agents" names the line's defaults the shell fills in; add these two members. | PDA |
| R7 | **`ChannelInfo.fieldSet` and the simulator.** It reaches the simulator's server part as the Java record through `ChannelRegistry` (`ChannelInfo.of`), so ECore needs nothing. The simulator's web part gets its channel list through the simulator's own endpoint (CR-0026), so the simulator's brief, in the next round, says it serialises `fieldSet` and offers that set. | PDA (simulator brief) |
