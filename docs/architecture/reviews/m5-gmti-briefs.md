# ACA review of the M5 GMTI briefs: `gmti`, the simulator's sensor and scenarios, and `map-view-2d`'s relation lines

- **Reviewed:** `pda/m5-gmti-briefs` at `ec4c7df1`: `gmti.md` (new, T-141), `simulator.md` functions 27 to 32 and criteria 35 to 46 (T-141, T-143, T-150), `map-view-2d.md` function 34 and criteria 72 to 76 (T-150), in `f7d5520b` and `3ef58aaa`.
- **Against:** ADR-0048 (points 3 to 7 and 8), ADR-0051 (points 3, 5, 6, 8 and 9), ADR-0050 point 7, ADR-0041 point 1, CR-0031 (its Impact: the caps, R4, R6, R7), the ACA's reference `docs/architecture/gmti-4607.md` (sections 4, 5.3, 6.2 and 7's open points), the ESA's playback sheet `external/gmti/README.md` on `esa/m5-ports-emcc`, and the owner's answers of 2026-11-06 (IJ: Q5 to Q7 and Q9, A1 to A13; ID and IE on the Event panel).
- **By:** the ACA, 2026-11-06.

## Verdict

**Approve the three briefs for the owner's approval, with two corrections first:** R1 (the VISTA counts in the `gmti` brief name a file the playback does not serve) and R2 (the simulator's pairing update as written would be refused by the store under ADR-0041). Both are text changes; neither touches a decision of the owner. The rest are remarks.

The briefs settle every open point of the reference's section 7 (the field set `gmti.report`, the symbols by class, the time and classification settings, multicast, the ESA's player), and ADR-0048's points 3 to 7 are each visible in a function and a criterion. The owner's answers are in the right places: Q5 in simulator 27, Q6 in 28, Q7 in 32, Q8 in `gmti` section 3, Q9 in 28 and criterion 39, ID and IE in 26 and 31.

## Remarks

| | Remark | For |
|---|---|---|
| R1 | **The VISTA expectation names the wrong file.** `gmti` section 7's table expects "32 dwells, 297 reports" from port 8113 and says the ESA's sheet confirms it. Those are the counts of the dissector's re-recording of the VISTA stream, which the sheet lists as not served; port 8113 plays the pcap: 186 packets, 85 dwells, 528 reports, at most 18 per dwell. Criterion 16's live check would fail as written. Take the sheet's numbers; the `.gmti` file stays a unit fixture. The ACA has added the same note to the reference's 6.2 on this branch. | PDA (brief) |
| R2 | **The pairing update cannot be "not saved".** Simulator 30 puts the relations in the platform's tick update, "not saved while running like the move". ADR-0041 point 1 lets the store accept the mark only on an update that changes nothing but `geometry`, `time`, `direction` and `speed`; the CDA's part 3 half counts a change of `relations` as a change, so the store refuses that update and the platform neither moves nor pairs at that tick. The brief says instead: the update at a revisit, which changes the relations, is an ordinary saved update; the ticks between revisits stay unsaved moves. That is one saved update per sensor per revisit (about 15 KB at 200 detections every 10 s), which R4's measurement covers. If that costs too much, extending ADR-0041 point 1 with `relations` is a CR for the owner, not the brief's call; the ADR's reason (what survives a restart) would allow it, since the sensor writes the list again at its next revisit. Criterion 43 changes with it. | PDA (brief), owner if the CR is wanted |
| R3 | **Dismounts.** Simulator 28 detects tracks whose symbol is of symbol sets 10, 11, 15 and 30. STANAG 4607 has a dismount class (137), the reference's 4.3 maps it, and `draw-symbols` places dismounted individuals (symbol set 27). Add 27, or say why not. | PDA (brief) |
| R4 | **A sector across north.** Simulator 27's bearings are "start, end, clockwise, 0° to 360°"; say that an end below the start wraps (300° to 60° is a sector across north), and let criterion 36 include one. | PDA (brief) |
| R5 | **`ObjectWriter.objectId(key)`: in CR-0030's build, and only if it answers during the create.** The writer is CR-0030's own addition (Q1) and 1.4.0 is not frozen, so a method on it is a compatible addition within the CR's build, recorded by a dated note in its Decision as HR did; no new CR, and the `gmti` brief may rely on it. But the writer already has `object(externalId)`, the object as the store last reported it, which gives the id once the create is applied; a second method earns its place only if it returns the id the writer chose at the first write, while the create is still in flight. Then the first dwell's detections pair too (rule 17 never checks the other object, ADR-0051 point 3), and `gmti` section 3's "no platform object yet: no pairing" goes. The PDA writes it that way or drops it for `object(key)`. | PDA, MCA (the note) |
| R6 | **The lines need part 5 before anyone sees them.** `map-view-2d` 34 draws a kind only when its switch is on, and until the shell has `ctx.display` its `defaultOn` decides; `gmti.pairing` is off by default. So `gmti` criterion 16's last clause and `map-view-2d` criterion 72 in the browser need SDK part 5 and the shell's window (ADR-0052). The board orders it so; the unit tests run before with the fake's display. | MCA |
| R7 | **`P4` of an empty dwell.** `gmti` out takes the packet's classification from the highest label of the item's detections; an empty dwell has none. Say which label it uses then (the link's, or the lowest the policy has). | PDA (brief) |
