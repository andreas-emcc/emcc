# Plugin design pattern

> **The SDK as it is today:** [the SDK reference](reference/README.md), with [the rules](reference/rules.md) in one place. The status lines below are this file's history.

- Status: **v1** (2026-10-10, T-034), for SDK 1.0.0 and data model 1.0.0, both frozen by the owner (2026-10-10; on `main` since 2026-10-12, tag `contracts-1.0.0`). **Updated 2026-10-15 for SDK 1.1.0 (M2; T-049)**, frozen by the owner on 2026-10-15 (on `main` since 2026-10-22, tag `contracts-1.1.0`): the parts marked "1.1.0". **Updated 2026-10-22 to 2026-10-26 for SDK 1.2.0 (M3; T-076, CR-0025):** the parts marked "SDK 1.2.0" or "1.2.0". **Updated 2026-10-30 to 2026-10-31 for SDK 1.3.0 (M4; T-092, CR-0028):** the parts marked "1.3.0". **Updated from 2026-11-05 for SDK 1.4.0 (M5; CR-0030, CR-0031):** the parts marked "1.4.0". v0 was 2026-10-08 (T-016). Owner: PDA. Applies to every plugin; questions from PCAs are added to the FAQ.
- Read with: your brief (`docs/plugins/briefs/<id>.md`), [the SDK reference](reference/README.md), the Javadoc and TSDoc, and `plugins/_template/`, which follows this pattern. `sdk-v1.md` and `sdk-v0.md` are the SDK's history.

The rules here are **normative** for plugins. Where they repeat `CLAUDE.md` or the SDK design, those are the source.

## 1. Start from the template

1. Copy `plugins/_template/` to `plugins/<id>/`. Delete the part you do not need (server or web). The server part's `transport` package is the transport pattern for in/out plugins (M4, T-093): keep it and follow `docs/plugins/in-out/playbook.md` if your plugin exchanges objects with another system over its own connections; otherwise delete it with its tests, the `links` setting and `connections` in `plugin.json`, and the two lines in the entry class that start it (from M9 the template runs its links end to end, D3). **Keep the manifest guard** (`web/test/manifest.test.ts`): it checks the manifest against the schema (`manifestProblem`), and the texts and the hints, which ECore and the shell do not check; it replaces a plugin's own manifest check script.
2. Rename. Each forgotten rename fails the build or a test:

   | What | Template | Your copy | What fails if you forget |
   |---|---|---|---|
   | Manifest id | `"id": "template"` | `"id": "<id>"` | `InstalledLayoutTest` (folder ≠ id) |
   | Maven artifact | `emc2-plugin-template` | `emc2-plugin-<id>` | Maven: duplicate project in the reactor |
   | Java package | `dev.emcc.plugins.template` | `dev.emcc.plugins.<id without hyphens>` | `ArchitectureTest` (no classes), `InstalledLayoutTest` |
   | Entry class | `server.entryClass` | your class | `InstalledLayoutTest` |
   | npm package | `@emc2/plugin-template` | `@emc2/plugin-<id>` | npm: duplicate workspace; the web test |
   | CSS class prefix, panel id | `template-` | `<id>-` | review |
   | CSS file | `"web": { "css": ["template.css"] }` | `["<id>.css"]` | the web test (the build names the file after the id) |

3. Register the server part with one line in `server/pom.xml`: `<module>../plugins/<id>/server</module>`. The web part needs no registration (it is a workspace through a glob). **The server part's parent** is the SDK's stand-alone `dev.emcc:emc2-plugin-parent` (from M9, D3): keep it and its `relativePath`, so the same POM builds in this repository and outside it from the SDK kit; a bundled library pins its version in your own POM.
4. Run `npm install` once at the repository root (the npm workspace root, CR-0006) for the new workspace, and commit the regenerated `package-lock.json`; never edit or merge a lock file by hand (`CLAUDE.md` section 6).
5. Fill in `plugin.json` from your brief, and write `plugins/<id>/README.md` (section 11).

## 2. Folders and names

```
plugins/<id>/
├── plugin.json            the manifest (source); the web build writes the built one
├── README.md
├── server/                optional: Maven module emc2-plugin-<id>
│   ├── pom.xml
│   └── src/main/java/dev/emcc/plugins/<idwithouthyphens>/…
└── web/                   optional: npm workspace @emc2/plugin-<id>
    ├── package.json, tsconfig.json, vite.config.ts, eslint.config.js
    ├── src/index.tsx      the entry module
    └── test/
```

- **Plugin id** = folder name = extension namespace = first part of every name you own (worker names need not repeat it).
- **Java:** package `dev.emcc.plugins.<id without hyphens>`, every package `@NullMarked`. Message types are named after their worker (`TileMsg` for the `tiles` worker).
- **Web:** CSS classes are `<id>` or start with `<id>-`, and panel ids start with `<id>`; a plugin's own service keys are `<id>.<name>`, and the `emc2.*` keys are the web SDK's.

## 3. Manifest (`plugin.json`)

Schema: `model/schemas/plugin-manifest.schema.json`; fields explained in `docs/plugins/sdk-v0.md` and `sdk-v1.md`.
- `sdkVersion`: `^1.0.0` for SDK v1, `^1.1.0` once you use a 1.1.0 addition, `^1.2.0` once you use a 1.2.0 one, `^1.3.0` once you use a 1.3.0 one, `^1.4.0` once you use a 1.4.0 one, `^1.5.0` once you use a 1.5.0 one, `^1.6.0` once you use a 1.6.0 one, `^1.7.0` once you use a 1.7.0 one, `^1.8.0` once you use a 1.8.0 one, `^1.9.0` once you use a 1.9.0 one (each accepts every later 1.x; `InstalledLayoutTest` checks that it accepts `Sdk.VERSION`, the SDK you build against). A plugin on `^0.1.0` is refused by SDK 1.0.0.
- `provides`, `requires` and `uses`: list in `provides` every service key you `provide`. **Every service key you get with `ctx.services.get`** (in `activate` or later) is in `requires` or in `uses`, never both:
  - `requires`: you cannot work without it. The shell activates the provider first, and does not load your plugin when none is loaded ("not loaded: requires …, which no loaded plugin provides").
  - `uses` (CR-0011): you work without it, and use it when it is there (e.g. `map-view-2d` uses `emc2.symbols` and draws markers without it). The shell orders and reports it like `requires`, but always loads your plugin; `get` then rejects at once, so catch it: `await ctx.services.get(SYMBOLS).catch(() => null)`.

  The shell plans from these lists only, and refuses cycles. Keys you read with `getAll` (zero or more providers, e.g. background maps) are not listed.
- `internet`: only if your brief says your server part reaches outside hosts: the default hosts and the reason (from SDK 1.2.0, `"hosts": []` with the reason when they all come from settings an admin fills in, CR-0022). From SDK 1.1.0 it is a declaration, shown in the monitor view, not an allow-list: your server part may reach any host (owner, 2026-10-18), but never one taken from a browser request, a message or an object's data (ADR-0030, CR-0013; owner, 2026-10-19). Every function must still work offline (for maps, Natural Earth).
- `connections` (SDK 1.2.0, ADR-0036 point 7): only if your server part opens connections of its own (connection tasks, section 5): their `kinds` (`tcp-client`, `tcp-server`, `udp`, `multicast`, `other`), their `direction`, the JSON Pointer to the links in your settings, and the reason. A declaration, not an allow-list. It covers the hosts an admin names there, internet hosts included, so it needs no `internet`: that one declares the SDK's outbound HTTP (ADR-0036 point 7).
- `network`: only for the deprecated listeners (section 5; from SDK 1.2.0 connection tasks replace them, ADR-0036), with `endpoints` (JSON Pointers to the settings that hold `host` and `port`) and the reason.
- `dataTypes`: the data types your brief names, each `<id>.<name>` with a name and its default behaviour (ADR-0023). Most plugins declare none and use `core.general` or another plugin's data type.
- `permissions`: the permissions you check, core ones (`objects.edit`, `layers.edit`, `settings.admin`) and your own `plugin.<id>.<name>`.
- `settings`: a JSON Schema with a `default` for every setting (section 7).
- `web.shared` is written by the build. Never write it by hand.

## 4. Built output (installed layout)

What `tools/build.mjs` assembles into `build/plugins/<id>/` for development runs and packaging, and exactly what the plugin host and the shell read:

| Installed | Comes from | Notes |
|---|---|---|
| `<id>/plugin.json` | `plugins/<id>/web/dist/plugin.json` if there is a web part, otherwise `plugins/<id>/plugin.json` | The built one carries `web.shared` |
| `<id>/server/*.jar` | `plugins/<id>/server/target/emc2-plugin-<id>-<version>.jar`, plus the jars of bundled libraries | Not `*-sources.jar` or `*-tests.jar`. The SDK and JSpecify are never bundled (ECore provides them) |
| `<id>/web/` | everything else in `plugins/<id>/web/dist/` | The entry module and CSS named in the manifest, plus assets |

- Folders whose names start with `_` or `.` (the template) are never assembled or installed.
- The host loads `<id>/` only if the folder name equals the manifest's id.
- **Bundled libraries:** none of the M0 plugins needs one on the server. A plugin that does pins it in its own POM (from M9, whose parent is `emc2-plugin-parent`; before, in `server/pom.xml`, CDA) and asks the MCA how the build copies it; licences as in `CLAUDE.md` section 4. A library **shaded** into the plugin's jar needs nothing more: `InstalledPluginIT` loads it from the jar. Separate library jars beside the plugin's jar are not covered by that test; extend it to copy them too.

## 5. Server part

- **Entry class:** public, with a public no-argument constructor, implementing `Plugin`. `init` creates workers and registers endpoints and subscriptions; `start` starts timers and first requests; `stop` cancels timers. Each runs under a 5 s budget; no I/O and no waiting in any of them.
- **Workers:** all work happens in workers. One worker per independent piece of state (e.g. a tile cache), not one per request. A handler handles one message at a time, so its fields need no locks; it never blocks, sleeps or starts threads.
- **Messages:** one `sealed interface <Name>Msg extends Message` per worker, one `record` per message, immutable fields only (`List.copyOf`, `Bytes`). Requests that need an answer carry a `ReplyTo`; ask with `ctx.ask(…)` and a timeout, and handle `Ok`, `Failed` and `TimedOut`. After a restart, tolerate answers to asks you no longer know.
- **Mailboxes:** choose capacity and overflow per worker: `dropNewest` (default) for requests, `dropOldest` for "latest wins" data, `coalesceByKey` for updates of the same thing. `send` never blocks; check `DROPPED` and `CLOSED` where it matters.
- **Endpoints:** `GET`, and from SDK 1.2.0 `POST` with a JSON body for commands (CR-0026), registered in `init`; answer every request through its `ResponseHandle`, also on errors (`HttpReply.status(404)`, `502`). ECore answers `503` and `504` itself. An endpoint that changes something or shows what not everyone may see declares its permission: `Endpoint.get(path).requires(permission)` (ECore answers `403`); `request.user()` is the caller, so check `request.user().has(…)` when it needs more than one. Prefer a change request from the browser, which the server checks, to an endpoint that changes objects or layers; one that does requires `objects.edit` or `layers.edit` itself (overview 4.4).
  - **A command is a `POST`:** `Endpoint.post(path).requires(permission)`, never a `GET` that changes something. `register` refuses a `POST` without a permission. ECore checks the body (`415`, `413`, `400`) and hands the worker `request.body()`, parsed. Answer with `HttpReply.json(status, value)`. ECore never repeats a request, so make a command idempotent where it matters (starting a running route does nothing).
  - **Its changes carry the plugin, not the user** (every server part's do); ECore logs who sent each `POST`. Check ids in the body against your own objects, and take no host from it (ADR-0030).
- **Outbound HTTP:** to any host, typically the ones your settings name, but never one taken from a browser request, a message or an object's data; declare the default ones under `internet` (ADR-0030, CR-0013; ECore checks no host from M2, T-058); the result arrives as a message. No redirects. Fail gracefully when the host is unreachable: offline is normal.
- **Connection tasks** (SDK 1.2.0; ADR-0036, rule C6): your server part opens its own sockets of any kind, with the JDK's classes, **only in a connection task**: `context.connections().start(spec, factory, events, mapper)`. ECore runs a fresh task from the factory on a thread of its own for each run, a platform thread on every OS (CR-0027: on Windows, JDK-8334574 can leave a virtual thread blocked writing a socket unwoken while another virtual thread reads it, so a task may write a socket while its child reads it), restarts it as its `Restart` says, closes what it registered when it stops, and shows its state and counters in the monitor view.
  - **Write a task as a class** that implements `ConnectionTask`, not a lambda: `PluginRules` allows sockets, socket factories, NIO network channels and name lookups (`InetAddress.getByName`, `new InetSocketAddress(String, int)`) only in such classes and their nested classes. Code that handles a socket goes in a nested class of the task (a `DatagramSocket`'s helper too); a helper outside it takes the streams. HTTP and files stay forbidden in tasks too.
  - **Register every socket** at once with `task.closeOnStop(socket)`, so that a blocked read or accept ends when the task stops. Return when `take()` gives `null`, or when `task.stopping()` is true. A task never sleeps or waits on its own: wait for work with `task.poll(timeout)`, and to retry after a failure, end the run and let its `Restart` back off.
  - **Hosts, ports and multicast groups come from your settings**, never from a browser request, a message or an object's data (ADR-0030). A link that listens reads its address with `ListenAddress.from(link)`, which **binds to loopback unless an admin sets another address**; only an admin chooses `0.0.0.0`. A multicast link uses `ListenAddress.multicast(link)`, which needs an `interface` an admin names: without one the link stays stopped, and its status says so. Give each link that listens this settings schema: `{"address": {"type": "string", "default": "127.0.0.1"}, "port": {"type": "integer", "minimum": 1, "maximum": 65535}, "interface": {"type": "string"}}`. For a multicast link `address` is the group, which `ListenAddress.multicast` requires, so it has no default there. Every setting is changed only by users with `settings.admin`; there is no mark per property. Report the address with `task.listening(...)` and the peer with `task.peer(...)`.
  - **Sending:** workers hand the task what to send with `ref.post(item)`, which never blocks; give the inbox `Overflow.coalesceByKey()` with items that implement `Coalescing` (e.g. by track id), so a slow protocol keeps only the latest per key. Count what a worker skips or drops with `ref.count(...)`.
  - **Received data is untrusted:** limit sizes, parse with safe parsers (no DTDs, no external entities), split and parse small pieces in the task, and pass CPU-heavy work to a compute worker (rule C7). No watchdog budget applies to a task.
  - **A TCP server** starts one child task per client with `task.startChild(...)`; children count toward the cap of 100 tasks. Name the children yourself, e.g. `client-1`, `client-2` from a counter in the task. Its accept loop catches the cap's `IllegalStateException`, closes the new client and counts it, so that one flood does not fail the server task.
  - **TLS** for a TCP client: `task.tls("credentials-name")` gives an `SSLSocketFactory` built from local server configuration; you never see the keys.
  - **Test** a task alone with `FakeTaskContext.of(name, items...)`, or the whole plugin with `FakePluginContext`: `ctx.connectionTask(name)` gives its state, inbox, counters, `fail(reason)` and `awaitIdle()`; tasks there may open real sockets on loopback.
- **Streams to your web part** (SDK 1.8.0 part E; CR-0044, ADR-0057), e.g. live video:
  - **Opening:** a worker opens the stream with `context.streams().open(StreamSpec.of(name, mediaType, permission, label))`, and hands the `StreamRef` to your connection task in a message.
  - **Writing:** the task writes each chunk with `write(chunk, startPoint)`, marking where a new viewer may start (for MPEG-TS, a random access point). It sets the `header` a new viewer gets first (the latest PAT and PMT). A `DROPPED` write is counted.
  - **Who serves it:** ECore serves every viewer, keeps the start buffer and drops data for a slow viewer. You never hold a browser connection.
  - **The permission:** name one in the spec, usually your own (`plugin.<id>.view`). ECore checks it at each viewer's start.
  - **Ending:** close the stream when its link stops; open it again under the same name.
  - **Converting:** MPEG-2 video goes through `context.conversions().start(ConversionSpec.mpeg2ToH264(stream), worker, mapper)` instead of being written to the stream. Its events say `Waiting` (no slot free: tell the user), `Running`, `Stopped` or `Failed`. Start a failed one again after `Conversions.RETRY_AFTER`. You never start a program yourself.
  - **Test** with `FakePluginContext`: `ctx.stream(name)` gives the chunks, the start points and `join()`, a viewer; `ctx.conversions()` holds, runs or fails a conversion.
- **Compute tasks** (SDK 1.9.0; CR-0048 point 5, ADR-0064), for CPU-heavy work that runs as long as it is needed, e.g. a renderer; a job that ends stays a compute worker (rule C7):
  - **Declare** them in the manifest, `"compute": { "threads": n, "reason": "…" }`; without it every start is refused.
  - **Start** one from a worker with `context.compute().start(ComputeSpec.of(name, Item.class), Task::new, worker, mapper)`; post to it with `ref.post(item)`, which never blocks. A start above the admin's `allowed()` or ECore's total cap is refused (`ComputeEvent.Refused`); ECore does not retry it, so say so in your status and try again later if you need to.
  - **The task** is a class implementing `ComputeTask`: a loop over `task.take()`, CPU work on data it owns, `task.send` to your workers, `ConnectionRef.post` to your connection tasks, `task.count` for the Monitor. It never uses the store, channels, HTTP, timers or the plugin's context (`PluginRules`). Pictures cross as `Bytes`.
  - **Test** with `FakePluginContext.builder(id).compute(n)`: `ctx.computeTask(name)` gives its state, inbox, counters and `awaitIdle()`; `ctx.compute().allow(n)` and `refuseNext(…)` drive the limits.
- **A channel kind of your own** (SDK 1.9.0; CR-0048 point 4): to take data from other plugins that the SDK's items do not carry, declare the kind in `channelKinds` with its payload's JSON Schema (self-contained), offer your channel with `declaredKinds` and a `toDeclared` mapper, and document the payload in your README. Senders send `DeclaredItem`s; ECore checks them against your schema. Change a kind compatibly only; an incompatible change is a new kind.
- **Every setting explains itself** (SDK 1.9.0; CR-0048 point 1, ADR-0060): a `title` and a `description` on every setting the form shows, and a `description` on every group. Keep the template's manifest guard, which checks it with `settingsTextProblem`.
- **Links and output channels** (SDK 1.2.0; ADR-0037): an in or out plugin keeps one **link** per configured connection in its settings, with a name (the data source of what it receives), a transport and a direction.
  - **An input link writes into one target layer**, picked with the layer picker (section 7). The link's actual layer is yours to keep: map each link to it in your plugin documents, create the layer when the setting names none, names "New layer", or names a layer that is gone, and use it from then on. **Two links that name the same new layer share one.** Report each link's actual layer in your status, since the setting keeps saying "New layer" (ACA note N1).
    - **1.4.0: the picker's "+" button** (T-133): the form creates the layer at once and saves it with its id, so a picked layer has an id. A picked layer that is gone is still made again by its name at the next data.
    - **1.4.0: the `ObjectWriter`** (`dev.emcc.sdk.store`, T-147) does all of this for you: create it in the worker that receives (`ObjectWriter.create(context, ctx.self(), "<external system>", MyMsg.Writer::new)`, then `start()`), give it the links' targets (`targets(...)` with each link's `LayerChoice`, label and `ref::count`), call `write(link, externalId, (stored, layerId) -> content)` for each received object, and pass its replies back to `handle(...)`. It keeps one change request in flight per external id (the latest wins), finds your objects again after a restart by their external identity, makes and shares new layers and keeps them in a plugin document, and counts what it created, updated and was refused.
  - **An output link sends the objects of its source layers** (picked with `"allowNew": false`), never an object whose `dataSource` is its own link (ADR-0037 point 3), and **is an output channel**: `context.channels().offer(ChannelSpec.of(link, name, outputType).can(ChannelCapability.DELETE).fields(...), worker, mapper)` when the link appears, `ref.withdraw()` when it goes. Each `ChannelItem` (`Update(id, content)` or `Removal(id)`) reaches your worker as a message; post it on to the link's connection task, whose inbox coalesces by the same key (`Overflow.coalesceByKey()`). A channel that cannot send a delete stops sending the object on a removal.
  - **1.4.0: output kinds** (ADR-0048 point 4): `ChannelSpec.kinds(Set.of(...))` says what your channel takes, `GROUND_TRUTH` (the default) and/or `SENSOR_REPORTS`. A sensor report is a `ChannelItem.SensorReport` (a sensor's platform, time, area and detections), keyed by its sensor, so a slow output loses whole reports (count them). A receiver that switches over `ChannelItem` adds a case for `SensorReport` or a `default`. `cot`, `ais` and `adsb` map each detection to an ordinary position of the detected object; `gmti` takes sensor reports only.
  - **Senders** (e.g. the simulator) watch the list with `context.channels().watch(worker, mapper)`: the current `ChannelList`, then a new one at each change. They keep a chosen channel by its `ChannelId` (plugin and link) and show one that is gone as missing, not silently dropped (N8). `send(id, item)` never blocks; `CLOSED` means the channel is gone. From 1.4.0 send a channel only the kinds it takes (`ChannelInfo.takes(kind)`): anything else throws.
  - **The highest classification:** every output link has the setting `highestClassification` (`{policy, classification}`, R7; schema in `ClassificationLimit`'s Javadoc). Read it with `ClassificationLimit.from(link.get("highestClassification"), context.defaultLabel())`, and send only what `context.classifications().within(label, limit)` allows: an object above it, of another policy, or with a classification outside the order is skipped. If `classifications().knows(limit)` is false, nothing passes: say so in your status.
  - **Skips are counted**, per link and reason, with `ConnectionRef.count` (and in your status), and logged at most once a minute per link (ADR-0037 point 7).
  - **Test** with `FakePluginContext`: `ctx.channels().deliver(id, item)` drives your offered channel, `pending(id)` shows its inbox, `addOther(info)` scripts other plugins' channels for a sender, and `sent(id)` records what was sent; `Builder.classifications(...)` sets the order (NATO by default). The fake hands over one item at a time and so coalesces more than ECore, which lets a few wait in your mailbox: do not test that an item is replaced after it was handed over.
- **Listeners** (blocking network I/O; **deprecated from SDK 1.2.0**: rule C6 now puts long blocking I/O in a **connection task**, in which the plugin opens its own sockets, ADR-0036; SDK 1.2.0 brings them, T-076; the listener stays in SDK 1.x, deprecated, and is removed in the next major version, ADR-0036 point 8): `context.listeners().start(spec, factory, events, mapper)`. ECore opens the connection; the loop only reads (and writes small amounts), splits and parses small pieces, and sends immutable messages to a worker through its `ListenerContext`. It never touches objects or a worker's state, and never computes for long (CPU-heavy work goes to a compute worker). Watch `Connected` and `Disconnected` in a worker, and report them in your status.
  - **Back-pressure:** a loop cannot wait for mailbox space (no `BLOCK_SENDER`, no sleeping). Give the worker a listener feeds `coalesceByKey`, keyed by what the message is about (e.g. a CoT uid), so a burst costs one message per key; count `DROPPED` sends and report them in your status (ACA review N4).
- **Compute workers** (rule C7): `WorkerSpec…compute(true)` for CPU-heavy work, so it cannot starve the rest.
- **Objects:** change only through change requests: `context.store().submit(Change…, timeout, self, mapper)`, never by keeping a copy and calling it the truth. Handle `Applied`, `Rejected` and `Unknown` (a create may be sent again with the same id). Your server part's changes have no user, so the object store checks no permission for them (overview 4.4). Write only your own extension namespace and forward all others untouched. Every object you create carries:
  - a security label (`defaultLabel()` unless your brief says otherwise);
  - a `dataType` from `context.dataTypes()` and a `dataSource`: `manual` only for drawn objects, otherwise the stream's name (ADR-0023);
  - for incoming data, its external identity (`withExternalRef`), so that you find it again after a restart with `store().query(ObjectQuery.byExternalRef(…))`.
- **Declared fields** (SDK 1.2.0; ADR-0038): declare the fields of your namespace that others should see or set in your manifest's `fields` (labels, units in SI, limits, `editableByOthers`, `dataTypes`). To set another plugin's editable fields (e.g. the simulator's events), name them: `Change.updateObject(current, content).withFields(List.of(new FieldValue("cot", "callsign", JsonString.of("ALPHA-1"))))`, never by writing its namespace into the content, which the store ignores on an update. Check a value first with `DeclaredField.problem(value)`; `context.declaredFields()` lists every loaded plugin's fields.
  - **The owning plugin's duty:** others may set your editable fields, so build your namespace from the **current** object on your own updates, keeping the values others set unless you mean to change them (as `cot` overwrites with its source's next event: last write wins).
  - **Test** with `FakePluginContext.builder(id).declaredFields(...)`: `FakeStore` checks and applies them as ECore does.
- **Updates that are not saved** (SDK 1.2.0; ADR-0041): `Change.updateObject(track, moved).notSaved()` is applied and sent as any update but not written to disk. **Only the simulator uses it in M3**; any other plugin needs the owner's approval. It may change only a move (geometry, time, the symbol's direction and speed) and carries no declared fields, else the store rejects it. Save your objects' whole state with ordinary updates at your own saving moments, together with your own state, and after a start or a worker restart place them from your own saved state. Test with `FakeStore.restart()` (each object comes back as last saved), `snapshotNow()` and `unsaved()`.
- **Workspaces** (SDK 1.2.0; ADR-0039): layers belong to a workspace (`LayerContent.workspace`, null for View); `context.workspaces()` lists them. **A store query without a workspace filter gives every workspace**, unlike every other default: a server part that passes objects on, to outputs or to browsers through its endpoints, filters by workspace itself (`ObjectQuery…inWorkspaces(...)`, N9), and keeps each workspace's data to the users allowed to see it. Create layers in a workspace by naming it; leave `workspace` out on updates. An object never moves to a layer of another workspace. Test with `FakePluginContext.builder(id).workspaces(...)`; `FakeStore.applyAs(actor, user, change)` checks a user's edit permission per workspace.

  "targetLayer": {
    "description": "Where received objects go.",
    "type": "object",
    "x-emc2": { "kind": "layer" },
    "properties": { "id": { "type": "string", "format": "uuid" }, "name": { "type": "string", "minLength": 1, "maxLength": 256 } },

## 8. Errors and status

- **Status:** set `OK` when ready, `DEGRADED` when the plugin works in part (e.g. upstream unreachable), `FAILED` when it cannot work at all, always with a short English detail. ECore and the shell may set a worse state; you cannot clear theirs.
- **Expected errors** (bad input, upstream down, rejection) are handled where they happen: an HTTP status, a `Failed` reply, a notification to the user. Never swallow them silently.
- **Unexpected errors:** let them throw. ECore logs a handler exception, drops the message and keeps the worker; the shell reports a failed `activate`. Do not catch `Throwable` to keep going.
- `notify({ severity, message })` (web) is for things the user must know, not for logging.

## 9. Logging

- Server: `context.log()` (or `WorkerContext.log()` in a handler) with `{}` placeholders: `log.info("fetched tile {}/{}/{}", z, x, y)`. Web: `ctx.log`.
- `info` for life cycle and rare events, `debug` for per-message detail, `warn` for degraded operation, `error` for failures with the exception.
- Never log secrets, tokens or whole objects with user data; log ids.

## 12. FAQ

**Must I densify geodesic edges when I draw?** Yes. Edges are the shorter geodesic between two positions (model rule 10). A renderer densifies them, so a shape looks the same in Web Mercator and polar projections; an edge may cross the antimeridian and is never split there.

**May I use a third-party library?** Yes, if its licence is allowed (`CLAUDE.md` section 4) and you pin its exact version. It **must not start threads or block** (no thread pools, no blocking I/O, no `Thread.sleep`). The ArchUnit rules check your code, not the library's: you check the library.

**May I use `synchronized`?** No, neither methods (checked by ArchUnit) nor blocks (not detectable, still forbidden). A handler needs no locks; state shared between workers is a message, not a field.

**How do I read local files, such as height data (SDK 1.4.0)?** Only through a folder your manifest declares in `folders`, whose path is a settings string that only an admin sets (model rule 19). `context.folders().folder(id)` lists one directory or reads a byte range, and the result arrives as a message, as with outbound HTTP. Never open a file yourself: `PluginRules` forbids file I/O, and a library you use must parse bytes you hand it, never a path. Paths are relative to the folder with `/` between names; ECore refuses one outside it. In tests, `FakePluginContext.builder(id).folder(id, tempDir)`.

**Where do my classes go?** `dev.emcc.plugins.<id without hyphens>` and its subpackages; `PluginRules.packageFor(id)` gives the name. Everything else is not checked, and ArchUnit fails if it finds no classes.

**How do I place or draw a tactical graphic (SDK 1.4.0)?** Ask the symbology service, never mil-sym-ts (ADR-0043 point 2). `graphicCatalog(standard)` lists the `core.multipoint` graphics it draws, with the geometry type each stores, its point counts, what each point is, in order, and its amplifiers; store the points in that order (a `Polygon` only where the catalogue says so). `renderGraphic(...)` draws one for a view, off the main thread, and resolves to lines, fills and labels in longitude, latitude, or to a reason, for the fallback marker. Both are optional members until the symbology plugin has them: check that they are there.

**How do I use field sets (SDK 1.4.0)?** Declare the fields of your protocol in `fields`, and group them in your manifest's `fieldSets` (`{ "id": "unit", "label": "CoT unit", "fields": ["callsign", "role"] }`; its full id is `<plugin-id>.unit`). An in plugin adds its set to what it receives: `writer.fieldSet("cot.unit")` with the `ObjectWriter`, or `content.withFieldSet(...)` if it writes itself (ADR-0050 point 4). An output channel names its set: `ChannelSpec....fieldSet("cot.unit")`. An editor shows sets with `DeclaredFields` (`fieldSets`, `objectSets`, `onAddSet`) and sends added ones with `changeRequests.withFieldSets`. Nothing removes a set, and an update without `fieldSets` keeps the stored ones.

**How do I write relations (SDK 1.4.0)?** Declare the kind in your manifest's `relationKinds` (id `<plugin-id>.<name>`, label, line, `defaultOn`). An update replaces the whole list, so build it from the stored object with `Relation.replace(stored.relations(), kind, ids)` (Java) or `replaceRelations(...)` (web), which keep other kinds' entries. The other object is never checked and never told. **An editor forwards `relations`**: spread the object's content, never rebuild it from its own fields, or the update empties the list.

**How do I show a vessel (SDK 1.4.0)?** Store `{ standard: 'vessel', sidc: vesselSidc({ context, identity, shipType }) }` (Java `Symbol.vessel(...)`) with `direction` and `speed` in `modifiers`, and let the symbology service draw it, as for APP-6. `vesselGroups()` gives the ship-type groups and their colours for a palette or a legend.

**How does my plugin follow the user's time (SDK 1.4.0)?** Declare `"capabilities": ["temporal"]` and implement it in the part that needs it, not in both (owner, Q11). Server: the plugin class implements `Temporal` and returns `Temporal.deliver(worker, MyMsg.TimeChanged::new)`; keep per session only what is not `now` (a session that ends is delivered `UserTime.NOW`), and read `request.userTime()` in endpoints. The time has a set time and an interval at once (CR-0032): read the part you need, `time()` (`null` for now) or `interval()` (`null` for none). Web: `definePlugin({ activate, capabilities: { temporal: { timeChanged } } })`. Test with `FakePluginContext.setSessionTime` and `CapabilityCheck.assertMatches`, or `activatePlugin` and `ctx.setTime` on the web.

**How do I follow the user's display settings (SDK 1.4.0)?** Read `ctx.display.value` and redraw on `ctx.display.onChange` (required since the 1.4.0 freeze); never write them, and apply no defaults yourself: the shell gives every part, and a switch for every loaded relation kind. A map view passes `symbolSize` and `labels` to `render` (owner, Q13). Test with `createFakeContext({ display })` and `ctx.setDisplay`.

**Who owns global library state?** Only `map-view-2d` registers projections with proj4; only `symbology` changes milsymbol settings. Every other plugin uses their services (`MapView`, `SymbolService`) and never changes these libraries' global state.

**How do I compare or cache SIDCs?** Use `canonicalSidc(standard, sidc)` (web SDK; `Symbol.canonicalSidc` in Java): a 30-digit APP-6E SIDC with digits 21–30 all zero and its 20-digit form are the same symbol (model README, "Conventions").

**My build says the shell's import map is missing.** Build the shell first: `npm run build --workspaces` at the repository root builds it before the plugins (it is the first workspace), or `npm run build -w @emc2/shell`. The shell writes `web/shell/dist/importmap.json` (T-014, merged 2026-10-08), and the SDK's build plugin fails on any shared module the map lacks. Copies of the template from before 2026-10-09 still contain a fallback for a missing map (`withoutShellImportMap` in `vite.config.ts`); it is no longer needed and can be removed (take the template's `buildPlugins`).

**How many asks and timers may a plugin have?** At most 10 000 outstanding asks and 1 000 active timers per plugin (ECore settings, CR-0005). Above that, an ask is answered at once with `Failed("too many outstanding asks")` and `once`/`every` throw `IllegalStateException`. A plugin that comes near these numbers has a design problem: one ask per piece of work in flight, and one periodic timer instead of many one-off ones. `FakePluginContext` enforces the same caps; `Builder.caps(asks, timers)` lowers them to test the refusals.

**Which SDK version am I on?** `dev.emcc.sdk.Sdk.VERSION` (Java) and `SDK_VERSION` (web) are always equal; both SDKs share one version because the manifest has one `sdkVersion`. The web part's `@emc2/plugin-sdk` dependency names that exact version.

**I copied the template before its review fixes (2026-10-08 and 2026-10-09). What do I take over?** Renamed into your package: `Manifest.java` (the plugin folder found from the compiled tests, so tests run from any directory), the folder check in `InstalledLayoutTest` (a copy must be named exactly like its id), and **`InstalledPluginIT` with the `packaged-plugin` surefire execution in `pom.xml`**, which replace the former `InstalledPluginTest` (it built its own jar from `target/classes`, so it could not see what Maven packages). In the web part: `cssFileName: manifest.id` in `vite.config.ts`, and the test that `web.css` lists `<id>.css`.

**Is there a teardown hook for a plugin (e.g. to remove a `document` listener)?** Not in SDK v0 or v1 (owner, 2026-10-10). A web part lives as long as the page: the shell never unloads a working plugin. When it **fences** a failed plugin, it removes its panels, overlays, map view, subscriptions and services itself and ignores the plugin's later SDK calls, so a listener left on `document` can no longer change objects or the UI through the SDK. Prefer listeners on your own elements (React `onKeyDown` on your panel); a `document` listener for a global key (e.g. Delete in `draw-symbols`) is acceptable. A hook becomes necessary only if plugins can be reloaded at runtime, which is not planned: plugins are loaded at start (ADR-0003), and settings changes at runtime (SDK v1, M1) arrive as events, without a reload. Its likely shape is `ctx.signal`, an `AbortSignal` the shell aborts when it removes the plugin, so that `document.addEventListener('keydown', h, { signal: ctx.signal })` cleans itself up. That would be an SDK change through a change request.

**Which data type and data source does my object get?** A drawn object: the user's pick, by default your setting (`core.general` unless your brief says otherwise), and `dataSource` `manual`. Incoming data: your own data type from your manifest and the stream's configured name. An update sends both unchanged; only a deliberate change of the data type changes it (`dataSource` never changes, model rule 14).

**How does my server part find its objects after a restart?** Give every incoming object its external identity when you create it (`Change.createObject(…).withExternalRef(new ExternalRef(system, id))`), and query it at start: `store().query(ObjectQuery.byExternalSystem(system), …)`. A second create with the same identity is rejected with `EXTERNAL_REF_EXISTS`, which also tells you a resent create had arrived.

**Where does my listener parse, in the loop or in a worker?** (The deprecated listener; a connection task works the same way.) Split and parse small pieces (one CoT event, one line) in the loop, and send the result as an immutable message; that lets the worker's mailbox coalesce by key. Anything slow (many objects, big documents) goes to a worker or a compute worker. The loop has no watchdog, so it must never compute for long.

**My panel must work without a permission. Hide it?** No: show it read only, with a short hint ("You may not edit objects"), and keep selecting and viewing. Users then see why they cannot act.

**My panel looks right in the right pane but breaks in the bottom pane.** From 1.1.0 the user moves panels (ADR-0031). Let content wrap or scroll, avoid fixed widths and heights, and test with the panel wide and low as well as narrow and tall.

**Can I keep my own Delete button for my kind of objects?** No (ADR-0032, owner 2026-10-14): the shell's shared Delete covers every selection with one confirmation, also mixed ones. Provide Edit only.

**How do I bring an object from a list into view?** Call `MapView.zoomTo([id])` or `centreOn([id])` (1.1.0). They fetch objects the map does not hold. Do not run the map view's action by its id.

**I need a colour the tokens do not have.** Use the nearest token, and ask the PDA for a new one through a change request. Never a fixed value: the three looks would not follow it.

**I need something the SDK does not offer.** Do not work around it. Write a change request to the PDA (`docs/change-requests/`) and continue with what you can do.
