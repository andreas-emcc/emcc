# fmv

STANAG 4609 full motion video in, over UDP, with the camera and its field of view on the map; from M9 also out: a simulated camera's video (the output link, below). Brief: `docs/plugins/briefs/fmv.md`; ADR-0057 (the stream channel), CR-0044 (SDK 1.8.0 part E), CR-0045 (ffmpeg), ADR-0058, ADR-0059, ADR-0064 and CR-0048 (SDK 1.9.0 part P). Built against SDK 1.9.0 (`^1.9.0`); **the output link's encoder is ECore's, from SDK part U (CR-0050)**. In the user's words (product name from M5): emcc.

## What it does

- **A link** (Settings › FMV) receives a UDP transport stream, unicast on an address and port (loopback unless an admin names another) or multicast on a group and the interface an admin names. A multicast link without an interface stays stopped and says so (ADR-0036 R4).
- **One stream per link:** the first program in the PAT whose PMT has video. The server part reads the tables, the KLV stream and the video's random access points, and passes every datagram on **unchanged**.
- **On the map**, per link, two objects with the link as their data source, joined by the relation `fmv.view`:
  - **the camera**, a `core.symbol` of data type `fmv.camera`, at the sensor's position (longitude first), APP-6D `10030100001103002000` (a UAV with photographic reconnaissance) with the link's standard identity, its direction from the platform heading, and the field set `fmv.camera` (ST 0601 values, read only for others);
  - **the field of view**, a `core.shape` `ArcBand` of data type `fmv.field-of-view`, from the camera, inner radius 0, an open line (no fill) in the link's colour. It aims at the frame centre (tags 23 and 24) when the set has it and reaches its ground distance; else it is heading plus relative azimuth (tags 5 and 18) and the slant range (tag 21). Its width is the horizontal field of view (tag 16), at least 0.01°.
- **The video:** the server part opens a stream (`GET /api/plugins/fmv/stream/<name>`, `plugin.fmv.view` needed) and ECore serves it to each viewer from the last keyframe. **H.264 and H.265** go through unchanged (H.265 plays only where the browser can decode it, and is never converted). **MPEG-2** is converted to H.264 by ECore's conversion service (a process of ECore, never the plugin's); the stream waits for a free slot and says so. Other formats (e.g. JPEG 2000) are listed and mapped, not played.
- **The web part:** the FMV panel in View lists each stream (camera name and link, format, size, bit rate over 5 s, age of the last set, state: Live, Stale, Waiting, Not playable, Stopped); the Watch icon opens the stream in a floating window with its classification line and a footer. The windows stay open when the panel's pane is closed. The player is mpegts.js 1.8.2 (Apache-2.0; es6-promise and events, MIT), bundled in the web part.

## The output link (M9 F1 and F2; brief section 10)

A simulated camera's poses (`fmv.camera-pose`, from `uav-simulation`) become STANAG 4609 out over UDP. **ECore encodes** (SDK part U, CR-0050; the CDA's C10 on the conversion service, with CR-0053's ffmpeg build): the compute task writes I420 pictures, the H.264 access units come back into its inbox. The tests drive the whole pipeline with the test kit's fake encoder.

- **An output link** is a `links[]` entry with `direction` `out` (Settings › FMV; the groups Connection, Video, Picture and Classification; `visibleWhen` on `direction`). **A new one has no destination and sends nothing** (O1) until an admin sets an address (or a group and its interface) and a port.
- **Its channel:** each enabled output link offers a channel that takes the declared kind `fmv.camera-pose` only (its schema in `plugin.json`'s `channelKinds`; ECore checks each pose against it, PQ2 A). **The channel's link name is `out-<the link's id>`**: a channel's link name must start with a letter, which a UUID v7 does not, so the id alone (as the brief's 10.2 point 5 writes) is refused by the SDK. A rename keeps it; disabling or removing the link withdraws it.
- **Its poses:** one camera holds the link until 2 s after its last pose (O2; another camera's poses meanwhile are counted `other camera`); a pose above `highestClassification` (absent: the classification of the server's default label, ADR-0037 point 8) is not rendered (`above release limit`); ST 0102's classification comes from the label's place in `classificationNames`, else the limit's (`unmapped classification`).
- **Its pipeline**, started by the first pose and stopped 2 s after the last: a **compute task** `render-<id>` (`fmv` declares 8 compute threads, O3; a refused start says "No render thread (<why>)" and is tried again 10 s later while poses come), **ECore's encoder** (`conversions().encode`, named `out-<id>-<n>`, a new name each start since ECore frees a name only when the old process has ended; the frame's size and rate, the link's `bitrate` and `keyframeSeconds`; one conversion slot), and a **connection task** `send-<id>` that sends paced UDP (a 4 MiB send buffer; multicast from the named interface with its `ttl`). A new frame size or rate, or a changed setting, restarts it (O10).
- **The encoder's events** (section 10.4): `Waiting` makes the link "Waiting for a conversion slot" (ECore drops the pictures until `Running`); `Failed` `UNAVAILABLE` (no converter) stops the task and the sender and says "No encoder installed", and **nothing starts again until the link's own settings change, or the plugin restarts** (owner, 2026-11-17); any other failure, or an end the worker did not ask for, leaves the task and sender running, renders nothing (`no encoder`) and starts a new encoder after `Conversions.RETRY_AFTER` (60 s; A1). Events of an older encoder are ignored.
- **The channel's state** (part U, `ChannelRef.state`): `NOT_SENDING` with the line's state ("No destination", "No render thread (…)", "Waiting for a conversion slot", "No encoder installed", "Encoder failed, …") while the link cannot send, else `READY`; `uav-simulation`'s panel shows it.
- **The compute task** skips a pose older than a frame period (`late`), renders it into I420, writes it to the encoder (`encoder dropped` when full), keeps it 2 s by its time, muxes each encoded picture with ST 0601 (every `metadataEvery`th) and ST 0102 from that pose, and posts the datagrams to the sender. It parses the DTED cells and decodes the tiles its worker posts; a restart starts clean and gets them again.
- **The terrain and the imagery** are read by the worker for 10 km round the camera, again after 5 km (O6), only through the declared folders `terrain` (`terrainFolder`, default `%emcc%/settings/terrain`) and `imagery` (`imageryFolder`, default `%emcc%/settings/imagery`). **One imagery set at a time** (B3): `imagerySet`, else the first set by folder name that covers the camera. **At most 256 million luma pixels a link** (about 256 MB; owner, Q4), nearest tiles first; the rest are grey and counted (`imagery over cap`). A set without a source or a licence is refused and named in the status.
- **The WMS imagery** (M9 F2; brief 10.5 point 17; off by default): where the link's set has no tile, the camera sees tiles from the WMS an admin names in the plugin-wide `wms` settings. **What is fetched** (owner, 2026-11-17): the grid tiles within **2 km of where the camera looks** (its line of sight on flat ground at 0 m; where that meets nothing within 10 km, the point 2 km ahead), nearest first, again when that point has moved 500 m; tiles the set covers are skipped. They take what the set's tiles leave of the link's 256 M pixels, at most 64 M (`wms over cap` beyond). **WMS 1.3.0 only** (owner, 2026-11-17), GetMap with `BBOX` in the CRS's axis order: latitude first in EPSG:4326, northing first in EPSG:3006. At most 4 requests at a time and 20 a second (O7), each timed out after 10 s, at most 512 KiB, through the SDK's outbound HTTP; `token` names a credential (`emc2.http.credentials.<name>.token`), never the token. **Nothing is fetched without a `source` and a `licence`**, and the status says why. The host comes only from `url` (ADR-0030); the manifest's `internet` declares no default host.
- **The tile cache:** one plugin document per tile, `wms-tile-cache.<crs number>-<metres per pixel>-<column>-<row>` (e.g. `wms-tile-cache.3006-1.0-2416-27031`), with the image as base64, its server, layer, format, source, licence and fetch time; **at most 900 tiles**, the least recently used removed first (O12). The grid counts from easting and northing 0 in EPSG:3006 and from 180° W, 90° S in EPSG:4326, so a column or row is never negative. Documents cannot be listed, so the order of use is one more document, `wms-cache-index` (outside the prefix), written at most every 30 s; a tile whose document survived a lost index is taken in when it is next used. **A tile is looked up in the cache before it is fetched,** so a flown area renders offline. A kept tile of **another server, layer or format** is used and fetched again when the server answers (owner, 2026-11-17); one of **another tile size** is never used (its ground differs). The worker fetches and keeps; the compute task gets the images as messages (ADR-0064 point 3) and samples them where the set has no tile.
- **Status** (one line per output link in `fmv`'s status): No destination, Waiting for a pose, Rendering <platform> <w>×<h> <rate>, Above release limit, No render thread (<why>), Waiting for a conversion slot, No encoder installed, Encoder failed (started again after 60 s), Disabled; poses, frames and datagrams a minute, and the counters that are not 0 (with the WMS: `wms fetched`, `wms from cache`, `wms failed`, `wms over cap`), and the imagery set in use with its source and licence. **One more line for the WMS** while it is on or tiles are kept: fetching from <host> or not fetching (<why>), the tiles kept and their size, the source and licence, fetched, from cache, failed, waiting, and the last failure. The same state goes to the channel for its senders (above). The compute task's own counters and render time are in the Monitor (ADR-0064 point 5).

The parts:

- **`out/geo`:** WGS84 (geodetic, ECEF, a local east-north-up frame at the camera) and SWEREF 99 TM (EPSG:3006, Krüger's series as Lantmäteriet publishes them).
- **`out/terrain`:** `fmv`'s own DTED reader (levels 0 to 2, every record's checksum checked; plugins share no code). `TerrainReader` is the worker's side: the cells within 10 km of the camera, read again after it moves 5 km (O6), **only through the declared `terrain` folder** (`LocalFolder`, ADR-0049), the highest level of each cell first (A4). The bytes go to the compute task, which parses them.
- **`out/imagery`:** `imagery.json` (A1, below) through a small strict JSON reader of `fmv`'s own (the SDK has none for plugins; owner, Q1). Tiles are JPEG or PNG, decoded by the JDK's ImageIO from memory only (owner, Q2): a grey tile keeps one plane, a colour one gets half-size chroma, all BT.709 limited range. **ImageIO needs `java.desktop` in the release's runtime (G20), and its JPEG reader starts one JDK daemon thread ("Java2D Disposer") the first time it is used.**
- **`out/render`:** the renderer after S10's `RenderBench.java` (rays through every 8th pixel, a fixed-point terrain search with the Earth's curvature (A3), bilinear or nearest, haze to 60 % at 25 km, sky above the horizon) into **I420** for ECore's encoder, and the frame centre by an exact ray. No imagery: grey `#808080`, counted. **No height data: flat at 0 m HAE** (`GroundFallback`; O5, accepted by the owner as a deviation from the ADRs' "flat at the frame's height"). Its speed on S10's Sundsvall data (2001 orthophoto, DTED level 2, 1280 × 720, one thread, this machine): **30.6 ms a frame bilinear with haze, 23.7 ms nearest** (S10: 36 ms and 25.9 ms without haze).
- **`klv/St0601Writer`:** ST 0601 for a frame (section 10.6 point 19) with tag 19 = −depression, and ST 0102 (point 20); tag 2 first, the checksum last. **A2:** ST 0601's tags 6 and 7 hold only ±20° pitch and ±50° roll, so a pose beyond them is written as `0x8000` (out of range); heights outside −900 to 19 000 m are clamped. Without a frame centre, tags 23 and 24 are `0x80000000` and tags 21 and 25 are left out.
- **`ts/TsMuxer`:** PAT, PMT on `0x0100`, H.264 on `0x0101` with the PCR, KLV on `0x0102` (`KLVA`); PAT and PMT before every third picture, 0xFF-padded; the PCR 100 ms before the PTS (PCR = PTS − 9 000 ticks); the random access indicator only on a keyframe's first packet. **Every datagram is 7 × 188 bytes:** a picture's last datagram is filled with null packets (PID `0x1FFF`), so no picture waits for the next. The input side's `TsReader` reads it back.
- **`out/Pacer`:** the sender's pacing at `maxRate`, with at most 2 s waiting (beyond it the oldest go, counted `send dropped`). The sender's `poll` waits in whole milliseconds while a datagram's time at 20 Mbit/s is half of one, so a sender woken late may catch up at most 2 ms of its schedule; an idle one gets no more.
- **`out/OutLink`, `PoseJson`, `OutputWorker`, `RenderTask`, `UdpSendTask`:** the settings, the pose, the worker, the compute task and the sender above.
- **`out/wms`:** `WmsSettings`, the tile grid and its GetMap request (`WmsGrid`), one link's tiles round where its camera looks (`WmsView`), and the fetching and the cache (`WmsCache`), the worker's helpers. The renderer samples the WMS tiles as a second layer under the set's, in their own CRS.

**`imagery.json` (A1):** `{"name", "source", "licence", "crs": "EPSG:4326" | "EPSG:3006", "tiles": [{"file", "min": [x, y], "max": [x, y], "width", "height"}]}`; `min` and `max` are the tile's outer corners (longitude and latitude, or easting and northing); `file` is a `.jpg`, `.jpeg` or `.png` path inside the set's folder; a tile whose picture is not `width` × `height` is refused, as is a set without a source or a licence.

## Settings

`links`, an array; one entry per link. The settings form shows the fields the link's mode uses.

| Field | Default | Meaning |
|---|---|---|
| `id` | filled in by ECore | The link's stable id (a UUID v7; CR-0047). Not shown in the form, never changed by a rename. The link's stream, task and objects are known by it |
| `name` | required | The link's name: it names the new layer and, with a camera that names none, the objects. **Renaming a link keeps its camera and arc** (same objects, new names). A new object's data source is the name in lower case with other characters turned into hyphens |
| `enabled` | `true` | Stopping or disabling a link keeps its objects and its row in the panel (Stopped); removing it deletes them |
| `mode` | `udp` | `udp` or `multicast` |
| `address`, `port` | loopback; required | `udp`: where to listen |
| `group`, `interface`, `port` | –; –; required | `multicast`: the group and the interface (both required) and the port |
| `targetLayer`, `label` | a new layer named like the link; the server's | The layer for both objects and the label of that layer and of objects whose stream's classification is not mapped |
| `classification`, `classificationNames` | `map`; NATO's | `map` gives objects and stream the classification of ST 0102 tag 1 (1 UNCLASSIFIED to 5 TOP SECRET), `link-label` the link's label |
| `cameraSymbol`, `cameraIdentity` | `10030100001103002000`; `friend` | The camera's APP-6D code and standard identity |
| `fovColour` | `#FFD400` | The arc's line |
| `time` | `received` | `received`: the server's clock; `stream`: ST 0601 tag 2 |
| `staleSeconds` | 10 | 2 to 300: without a set for this long the panel says Stale; the objects stay |
| `direction` | `in` | `in` receives (the fields above); `out` is an output link (the fields below; section 10) |
| `address` or `group` and `interface`, `port`, `ttl` | none; 1 | `out`: where to send; without them nothing is sent (O1). `ttl` 1 to 32, shown for a multicast link only and greyed on an input link (the form takes one condition per rule) |
| `highestClassification` | the server's default label's | `out`: a camera above it is not rendered |
| `bitrate`, `keyframeSeconds`, `metadataEvery`, `maxRate` | 4 Mbit/s, 1 s, 1, 20 Mbit/s | `out`: the H.264 video, ST 0601 every Nth frame, the pacing |
| `sampling`, `haze`, `imagerySet` | `bilinear`, on, empty | `out`: the picture; an empty set is the first that covers the camera |
| `classifyingCountry` | `//NATO` | `out`: ST 0102's tag 3 (`classificationNames` serves both directions) |

Plugin-wide: `imageryFolder` (`%emcc%/settings/imagery`) and `terrainFolder` (`%emcc%/settings/terrain`), the output links' declared folders; and `wms` (F2), off by default:

| Field | Default | Meaning |
|---|---|---|
| `enabled` | `false` | Fetch tiles from the WMS; off, kept tiles are still used |
| `url`, `layer` | none | The server (http or https, without parameters) and its layer |
| `crs`, `format` | `EPSG:3006`, `image/jpeg` | The tiles' CRS (or `EPSG:4326`) and format (or `image/png`) |
| `tilePixels`, `metresPerPixel` | 256, 1 | The grid: 256 or 512 pixels a tile, 0.25 to 10 m a pixel |
| `source`, `licence` | none | Both required to fetch; shown in the status and kept with each tile |
| `token` | empty | The name of an HTTP credential, never the token |

The manifest declares `internet` with no default host, for the WMS (owner AAA A, 2026-11-17). Every setting has a title and a description (SDK 1.9.0's texts rule, X1).

## Messages, permissions and endpoints

- **Permission** `plugin.fmv.view` ("Watch FMV"): the stream endpoint checks it. `GET /api/plugins/fmv/streams` (the panel's list) needs only a login.
- **Endpoints:** `GET /streams` (JSON array, one row per link that has received a stream). The stream itself is ECore's: `GET /stream/<name>`.
- **Worker messages** (`transport/TransportMsg`): `Up`, `Down`, `Chosen` (the program), `Size`, `Telemetry` (one ST 0601 set), `Traffic` (once a second), `Conversion` (ECore's news), `Writer`, `Removed`, `Found`, `Streams`, `Tick`. The task takes `LinkInbox`: `Stream`, `Conversion`, `Detach`.
- **Writes:** through the SDK's `ObjectWriter`, at most twice a second per link, the newest set winning; a set that changes nothing writes nothing; the camera first.

- **The receive buffer:** the link asks the system for 4 MiB before it binds (a default of 64 KB on Windows holds 0.1 s of a 4 Mbit/s video, and a sender that stalls and then catches up in a burst overflowed it: continuity errors in the stream). The monitor's task detail "receive buffer" says what the system granted (Linux: `net.core.rmem_max`).

## Counters (the monitor view, per link task)

`datagrams`, `bytes`, `not transport stream`, `KLV sets read`, `checksum`, `continuity gap`, `KLV too long`, `KLV truncated`, `value out of range`, `stream not open`, `stream dropped`, `stream closed`, `conversion input dropped`, `dropped: worker busy`; and per link from the worker: `unmapped classification`, `above layer label`, `no field of view`, `no camera position`, `stream not opened`, `rejected: …`. The last five are also warned of, once a minute per link.

## Known limits

- **ST 0601 and ST 0102:** the tag table was checked against ST 0601.14 and ST 0102.12 by the PDA and agrees. Tag 18 is defined relative to the platform, but in S9's sample it was a true bearing: the arc aims at the frame centre when the set has one. `0x80000000` in tags 23 and 24 means "no frame centre" and is not counted as out of range.
- **MPEG-2** converts only with ECore's conversion service and its converter (the minimal ffmpeg, `tools/ffmpeg/ffmpeg.exe` below the working directory or `emc2.conversions.ffmpeg`; Windows x64 in M8); without one the row and the status say "No converter installed". Seen live with the ESA's `day-mpeg2`: "Receiving MPEG-2 → H.264", the window plays (first frame about 0.15 s after Watch, 0.3 s behind live).
- **Watch is enabled only for a stream that can play:** live or stale. A stream that waits for a conversion slot, has no converter, whose conversion failed, is not a played format or is stopped has the button disabled, and the row and the button's tooltip say why.
- **`playable` in `GET /streams` agrees with the row's state:** false exactly where a running link's row is Not playable (a format that is not played, no converter, a failed conversion, no stream); a waiting stream is playable (it plays once its conversion has a slot), and a stopped link keeps its format's answer.
- **A window follows its link.** A window whose link has no row (removed, or not yet receiving) keeps its last row and says "The stream has stopped." A settings change that leaves out the links' ids makes new links with new ids and new streams (CR-0047 F2); a window whose link is gone moves to a new link of the same name that no other window shows, and plays its stream in the same window (owner, 2026-11-15). A renamed link keeps its id, its window and its stream. Without the ids the camera and the arc are new objects too, so a client sends the ids back.
- **The panel lists a stream only after the link has received a program.** A link whose PMT lists no video says "No video in the stream".
- **Windows live in a map pane overlay:** a workspace without a map has none. Closing a window also ends its picture-in-picture (a PiP left open would show its last picture, frozen).
- **Live and Stale follow only the ST 0601 sets** (`staleSeconds`, default 10): a viewer joining or leaving has no part in it. The ESA's 60 s recordings carry few sets (`day-h264`: at 0.1 s and five at 39.5 s of each round; `day-mpeg2`: at 0.1 s and 50 s), so with them a row is Stale for most of each round, whoever watches.
- **The list is read only while it is used:** every 2 s while at least one link is configured and the FMV panel is on screen or a window is open. The shell keeps a collapsed panel (or one behind another tab) mounted, so the panel watches whether it is on screen. A page with no window and the panel off screen, and every page of a server without links, asks the server nothing (the polls would otherwise renew a session's token and outlive its end).
- **The WMS round at a fine resolution:** at `metresPerPixel` 0.25 the 2 km round holds about 3 000 tiles of 256 pixels; a link takes the nearest that fit its 64 M pixels (about 980), more than the 900 the cache keeps, so a few of them are fetched again on the next flight over the area. 1 m and 256 pixels (about 240 tiles in the round) fits well.
- **A lost cache index leaves tiles behind:** if `wms-cache-index` is lost (a crash before it was written) or cannot be read, the tiles already kept are no longer counted. A tile is taken in again when it is used, but one never used again stays and counts toward the 1 000 documents a plugin may keep; with many of them a new tile may not be kept (`not kept` in the status). Documents cannot be listed, so `fmv` cannot find them.
- **The cache key has no tile size, server or format in it** (the brief's key): after a change of `tilePixels` the cache overwrites its tiles of the other size as it fetches.
- **A missing imagery or terrain folder is marked in the Monitor, links or not:** ECore marks every declared folder whose setting names a folder that is not there (ADR-0049 point 4), and `fmv` cannot turn that off while the setting holds its default. The release ships both `settings/imagery` and `settings/terrain`, empty but for a readme, so a fresh release has no mark (owner ACC A, 2026-11-18); a tree without them (a developer's) shows "Check".
- **The WMS was checked live against the ESA's GeoServer only** (WMS 1.3.0, EPSG:4326, Natural Earth's `sweden` group, 2026-11-17): fetched, kept, and rendered from the cache with the server stopped and after a restart. Not against Lantmäteriet's or another server in EPSG:3006.
- **The cost (criterion 35), measured live on the owner's 12-core machine (2026-11-17, other agents' runs on it):** one 1280 × 720 camera at 25 frames a second, bilinear, over the 1 m orthophoto and the Sundsvall DTED, takes one compute thread and one conversion slot as it should, but renders in about 42 ms a frame (median), so the task is busy about 99 % and renders about 23.5 frames a second. The criterion's busy share below 90 % is not met: **the owner accepts it for M9 and moves it to M10 (ABU A, 2026-11-17)**; the renderer needs to be faster.
- **The first picture leaves about 2.5 s after the first pose** (measured live): about 1.2 s while the pipeline starts (the first poses are late), and about 1.4 s in ECore's encoder (`h264_mf`) before its first access unit. Criterion 34's 2 s is not met: **the owner accepts it for M9 and moves it to M10 (ABU A, 2026-11-17)**; the encoder's start-up latency is ECore's (C10).
- **No RTP or RTSP, no files, no recording or playback of the past, no audio, no KLV over the video, no image footprint or VMTI** (brief section 9).
- **A data source is fixed when an object is made** (model rule 14), so a renamed link's camera and arc keep the data source of the old name; only their names and what a set gives change. New objects (an arc that comes later) take the camera's. An entry that cannot be read (a mistyped port, a group that is not a multicast address) stops its link but keeps its objects. A link with a new id is a new link.
- **A browser's decoder stops for good on a damaged frame** (media error 3). The ESA's sample has some (ffmpeg also reports them: at about 70–75, 85–90, 105–115, 130 and 165–190 s of its 200 s, and Edge fails on a plain MP4 of the stretch too). The window then makes a new video element and a new player at once (0.5 s if that fails again within 2 s) and starts at the stream's next start point: a pause of about 1 to 2 s per damaged frame, each a new request of the stream.
