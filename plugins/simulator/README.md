# simulator

A simulator for training and demos, in its own **Simulation** workspace (ADR-0040, ADR-0041; brief `docs/plugins/briefs/simulator.md`). Users place symbols, draw routes with a speed and an altitude at each point, put objects on the routes and run them. The server part moves the tracks once a second, with no browser open.

## What it does

- **The workspace** `simulator.simulation`, "Simulation", seen with `plugin.simulator.view` and changed with `plugin.simulator.edit` (the manifest's `workspaces`). Its layers are users' layers marked with the workspace. **The first layer** (from M4; BT, BX, A64): at a start, when Simulation has no layers, the server part creates "Simulation" there (the default label, visible), as ECore creates "Drawing" in View; once per start, so a layer deleted while it runs comes back only at the next start. Otherwise the simulator makes none, and it never writes View's.
- **Routes** are `core.shape` objects of the data type `simulator.route` (declared in the manifest, never faded or removed; from SDK 1.5.0 with `"manual": false`, so the editors leave it out of their data type selects, function 34): a `LineString` through the points. What users typed for each point is in the simulator's extension of the route ("The route's extension", below). The server part reads and checks every route it finds in the workspace. A route that fails a check cannot run, and one that fails while it runs pauses with its objects in place. The status and `GET /routes` say why.
- **The engine:** one worker, `engine`, owns the simulation. A timer ticks it once a second (`timers().every`). Each tick:
  - moves every track of a running route to where it is at the tick's wall-clock time, so a late tick does not slow it;
  - submits all its moves at once, each as `Change.updateObject(…).notSaved()` (ADR-0041): the position, with the altitude as the third coordinate, the symbol's `direction` and `speed` modifiers, and `time.observed`;
  - keeps at most one move per track in flight. A track still waiting is skipped and counted.

  Each move is built from the latest state the worker holds, so a user's change wins over a move in flight. The store refuses the move, which is counted, and the next tick builds on the new state. A dragged track on a running route goes back onto its route at the next tick (open question 11).
- **Only tracks move:** the `core.symbol` objects named in a route's list, in simulation layers. A standing track (stopped at its end) is not moved again.
- **The routes' lists decide which objects are on which route.** An object on two lists stays on the first.
- **The workspace is kept** (function 2): the store subscription and the query name `simulator.simulation`. The engine also keeps only layers marked with it, so a server that does not filter by workspace yet (before T-080) still gives it nothing of View.
- **A new snapshot** from the subscription replaces everything the worker holds. A restarted worker asks the store for the workspace's objects once, and applies the changes that arrived meanwhile.

## Movement (brief functions 5 to 7)

- **A track a user moved into another layer of Simulation** ("Move to layer…", ADR-0053) moves on along its route there: each move is built from the stored object, so its `layerId` stays (function 40, criterion 60; T-155). A copy is a new object on no route, and stays still.
- **Speeds:** a point's speed holds from that point on ("instant", a step at the point), or is reached at that point with a constant acceleration over the leg into it ("ramp"). A ramp on the first point acts as instant. So a leg runs at its start point's speed, unless its end point is a ramp.
- **Altitudes** (metres above the ellipsoid) work the same way: a step at the point, or a ramp over the leg into it in proportion to the distance. An empty altitude keeps the object's own.
- **Typed times** (the time helper): a time typed at a point is the time that point is reached, counted from the previous point or from the route's start.
  - At a ramp point it sets that point's speed: the leg's mean speed is the mean of its two ends.
  - At an instant point it sets the speed of the leg into it, which is the previous point's speed (the owner's Q2, 2026-10-26). If the time counts from the route's start and the previous point is a ramp, that speed also ends the ramp before it, so both legs are solved together.
  - A last point that is a step needs no speed of its own: the route stops there.
  - Two times that would set the same speed are a problem. A ramp point with both a speed and a time uses the time.
  - A computed speed is rounded to a whole unit of the unit the time was typed in.
- **Speed 0** (open question 13):
  - a ramp may start from or end at 0;
  - a step to 0 is a problem at the points between the first and the last;
  - every leg needs a mean speed above 0, so a first point of 0 needs a ramp at the second;
  - an altitude ramp needs altitudes at both ends.
- **Along geodesics** (`Geodesy.path`) with sharp turns at the points. At the last point a route stops: speed 0, still counted as running.

## Groups (brief functions 10 to 12)

- **A single object** runs the route's motion from the first point.
- **A convoy** waits at the first point and leaves one by one, in list order. Each member leaves when the one ahead has gone the spacing along the route, or has arrived when the route is shorter than the spacing (A7). So every member makes the same motion, later. With "stop", all stop at the last point.
- **A formation** has a centre, the mean of its objects' positions and altitudes when they are put on the route (open question 14). Each object's offset from it is recorded forward, sideways and up, relative to the direction of the route's first leg (Q16). The centre runs the route, and the shape turns with the direction of travel. Where the route's altitude is empty, the centre keeps the group's own altitude (A11). The formation stops when its centre reaches the last point (A8).

## Control and commands (brief functions 9, 10 and 14)

- **"Put on route"** makes the objects a group at the end of the route's list, and takes them off every other list (open question 8).
- **It names an object that has no name** (T-121; CZ, A73 to A76), since outputs such as `cot` take their callsign from the name: the route's name, a hyphen and one more than the highest number a symbol in Simulation has after it, in the order put (`Alpha-1`, `Alpha-2`; `Track-1` for a route without a name). A blank name counts as none; a named object keeps its name. It is written with the saved update that places the object, and is an ordinary name: a reset does not undo it, it stays after "Take off route", and an event may change or clear it; a cleared name is given again only at the next "Put on route".
  - The server part writes the lists. Each write is built from the latest version it holds, with one in flight per route; until the store applies it, the engine works with the list as written.
  - The objects go to the first point at once, with a saved update (open question 9). On a running route they leave at once (Q6, 2026-10-27). Put on a route again, an object starts again from the first point.
- **"Take off route"** takes the objects off their lists. They stop in place with speed 0 and keep their altitude, with a saved update.
- **Start** runs a paused route from where its objects stand. On a route stopped at its end, also when paused there, it runs the route again from the start (Q7, 2026-10-27). Starting one route that cannot run is refused (409); starting every route skips the ones that cannot run.
- **Pause** stops the route's objects where they are, with speed 0, as a saved update.
- **Reset** puts every object of the route back at its start (a convoy waiting at the first point) and leaves the route paused.
- **At the end** a route stops (`"end": "stop"`, the default; still counts as running) or restarts (`"restart"`: a reset, then a start).
- **An object taken off a list by any write** (a user's, too) stops in place in the same way. A convoy member still waiting keeps its time to leave when one ahead of it leaves the list.
- **A saved write the store refuses** is tried again from the latest state, up to 3 times in all; a route's list at the next tick. Then it is given up and logged, and an id it would have taken off a list is not asked for again.

## Events (brief function 13)

A point's `events` fire for each object of the route as it passes the point (A17).
- **Passing a point:** a single object or a convoy member passes it when its distance along the route reaches the point's, after it has left the first point. A formation member passes it when the centre's distance plus its forward offset does; at the end, every member has passed the last point (A8). So an event at the first point fires as each object leaves it (A13).
- **Which objects:** an event with `objects` applies to those; without, to every object on the route as it passes.
- **"Change a field"** (`"kind": "set"`) sets core fields (`core`: `name`, `description`, `sidc`, and `texts`, the symbol's text modifiers by their model name; `null` clears one) and other plugins' declared fields (`fields`: `[{plugin, name, value}]`, written with `Change.withFields`, ADR-0038). It is a saved update, written with that tick's move (A18). An event whose declared fields the store refuses by name, such as one that is not editable by others, is logged and counted, and not tried again. Anything else a refused write carried (a hide, a reset's restore, an event of core fields only) goes with the write when it is tried again, up to 3 times in all.
- **"Hide"** (`"kind": "hide"`): the object stops where it is with speed 0 and is marked `"hidden": true` in the simulator's extension of the track, with a saved update; each chosen output gets a `Removal` (A19). It stays on its route's list (A14), and counts as arrived when the route's other objects reach the end (Q9, 2026-10-27). A hidden object gets no more events, also none later at the same point.
- **What a reset restores lives on the track** (Q8, 2026-10-27), in the simulator's extension next to the hidden mark, written in the same update as the change: the first value each event replaced, `null` for a value that was absent. A reset writes them back, shows hidden objects, and clears both; "Put on route" shows a hidden object again (Q18).

```json
"simulator": { "hidden": true,
  "restore": { "core": { "name": "Alpha" }, "texts": { "uniqueDesignation": null }, "fields": { "cot.team": "Cyan" } } }
```

## Outputs (brief function 18)

- **The channels** other plugins offer are watched (`channels().watch`). Users with `plugin.simulator.edit` choose them (`POST /outputs`). From M5 these are the **Ground truth outputs**: only channels that take `GROUND_TRUTH` are listed and sent to; channels for sensor reports are chosen per sensor.
- **Field sets** (function 31): each item sent lists its channel's field set (`ChannelInfo.fieldSet`) in its content, never the stored track; the panel names the set by its label.
- **The choice is kept by channel id** (plugin and link), in the saved state. A chosen channel that is not offered now, or that answered `CLOSED`, is shown as **missing, not dropped** (N8); it is used again when it is offered again, and a user may keep or remove it (A20).
- **While the simulation runs** (a route running or stopped at its end), each tick sends an `Update` for every symbol in Simulation, on a route or not, hidden ones excepted, to each chosen channel that is not missing (A21). The item carries the newest content and `time.expires` = the tick's time + `outputStaleSeconds`; the stored object never has that expiry. When every route is paused or reset, nothing is sent, so the tracks go stale at the receiver (A8). **A pause or a reset sends its tracks' last state once** (the ITA's mass test 2; the owner, 2026-11-23, in this role's session): as its saved update is written, each track of the route goes out with that content and the same expiry, where it stopped with speed 0 or at its start, so a receiver does not keep the last tick's position, up to a step short of the stop. A track whose write is in flight goes when it is written; while another route runs, the ticks send it instead. A route that pauses itself because it became invalid does the same; a clean stop of the plugin does not.
- **A "change a field" event** sends what it sets to the outputs in its own tick, declared fields included: the item carries them as the store writes them (T-112, A71).
- **`send` never blocks;** `DROPPED` and `CLOSED` answers are counted. Each output link applies its own highest classification (ADR-0037 point 8).

## Sensors (brief functions 27 to 30; CR-0033 to CR-0035)

- **A sensor sits on a track** of the simulation, its platform, chosen with "New sensor" while that one track is selected. Its id in sensor reports is the platform's id. A deleted platform leaves the sensor, shown as missing; a hidden one sends nothing (A104).
- **Its settings** are generic physical values in SI units (owner, JQ): revisit time (from M6 a ground radar's "Revisit interval") 1 to 600 s (10), range band 0 to 1 000 km (20 to 150 km), bearings from the platform's heading 0 to 360° (45° to 135°; an end below the start wraps across north; equal bearings look all round, the owner's MX A), probability of detection 0 to 1 (0.9; a new ground radar from M6: 1), range and cross-range errors 0 to 10 000 m (20 m, 50 m; **0 is no error**, the owner's A100), minimum detectable speed 0 to 100 m/s (2; a new ground radar from M6: 0, the brief's A5), most detections per dwell 1 to 1 024 (200), Mission up to 64 characters (none), and "Detect all in range" (off). The panel shows the speed in the user's unit, ranges in km and errors in m (the owner, 2026-11-08). They are saved in the `state` document with the rest.
- **A revisit** (A93): the first at the first tick after the simulation starts (or after the sensor is added while it runs), then every revisit time; none while everything is paused. It looks at an `ArcBand` turned with the platform's direction (a `Circle` of the max range with "Detect all in range"), and detects **every track type** (the owner's A99, 2026-11-08: an output decides what it sends; STANAG 4607 has aircraft classes) inside it whose speed along the line of sight reaches the minimum, with one draw of the probability per track. The measured position moves by Gaussian errors along and across the line of sight. The nearest ones up to the cap are kept; the rest are counted. Random numbers come from one generator per sensor seeded from its platform's id.
- **One `SensorReport` per chosen sensor output** at each revisit (from M6 at each dwell of a ground radar, below), empty ones too, with `ChannelItem.Sensor`: the platform's name (or "Ground radar" or "Generic sensor", was "GMTI sensor"), the Mission, the revisit time, the errors, the minimum speed, the probability (no errors and no minimum speed but a probability of 1 with "Detect all in range"), and the platform's direction and speed when it has them. Each detection's content is the track's with the measured `Point`, the expiry of function 18 and the channel's field set.
- **Beyond an output's depth** (CR-0035): a detected track whose true distance from the platform is more than the area's near edge (the min range, 0 with "Detect all in range") plus a chosen output's `maxAreaDepth` gets a relation of kind `simulator.beyond-reach` (red, on by default) instead of `gmti.pairing`; the others get `gmti.pairing`, written only when `gmti` declares it. The server part judges this at each revisit and at once when a sensor's outputs or the channels change. `GET /sensors` names those outputs (`outOfRange`), and the web part shows "<platform>: some units are out of range for <output>" at the bottom of the Simulation map. The kind's id is `simulator.beyond-reach`, not the brief's `simulator.beyondReach`, which the SDK's id rule refuses (owner, 2026-11-08).
- **The platform's relations** are a saved update, with its next move when it is on a route, written only when they change (A103); other kinds' entries are kept. Every content the engine builds keeps `relations` and `fieldSets` (ADR-0051 point 9).
- **Coverage on the map** (function 33, criterion 49; T-158, the owner's Q25 to Q29 A): the web part draws each sensor's area round its platform's current position, turned with its `direction` (0 without one), as one overlay of its own (`MapView.createOverlay`, an `area` per sensor), in Simulation only. It is the area a revisit looks at: the band from the min to the max range between the bearings (one ring, the outer arc clockwise and the inner arc back, or the platform in place of the inner arc at a min range of 0); with equal bearings, 0° and 360° among them, the ring between the circles with the inner one a hole; with "Detect all in range" the disc of the max range. Arcs are 1° apart, from a WGS84 direct geodesic (Vincenty) within 1 m of the server's `Geodesy`. A dashed outline, 1.5 px, no fill, in the platform's standard identity colour (as `gmti`'s dwell area: yellow for unknown and pending, `#00A8DC` friend, `#00E200` neutral, `#FF3031` suspect and hostile; from the SIDC of APP-6B, APP-6D, APP-6E and vessel symbols). Shown whether the simulation runs, is paused or is reset, also while the Sensors panel is closed (the overlay then reads `GET /sensors` itself, every 2 s); none for a missing platform; cleared in another workspace. Nothing is stored or sent: no output and no scenario file sees it. "Show coverage" is read only when the user has saved it (the documents are listed first), so a new user's first read makes no request that answers 404. **Equal bearings look all round** (the owner's MX A, 2026-11-09): with equal start and end bearings (e.g. 45° and 45°, or 0° and 360°) the revisit looks all round, as drawn.
- **Measured** (R4 on CR-0031): one sensor with 200 detections at a 10 s revisit: the revisit's tick took 7.6 ms in the test kit, and the relations add 14 800 bytes (74 per relation).

## Sensor types, dwells and the job area (brief functions 36 to 39; T-168, T-169)

- **Types** (function 36): **in M6 "New sensor" makes a ground radar** without asking (owner, PX, 2026-11-11: no real plugin has an output for a generic sensor yet). The **generic sensor** is built and kept for later: `OFFERED_KINDS` in `web/src/sensors.ts` lists the types offered; with more than one, "New sensor" asks for the type. The server part still takes `type: "GENERIC"` (`SensorType`; `POST /sensors` `{platform, create: true, type}`, a ground radar when absent), and its tests (`SensorTypesTest`, `web/test/generic.test.tsx`) stay. **A scenario file's generic sensor** is left out on import and listed as "<name>: generic sensors come later; not loaded"; its platform and the rest load as usual (Q52 B). The type is fixed (A5: a body naming another is refused, 400). Each report says it in `Sensor.type`, and carries the job area in `Sensor.jobArea`.
- **Outputs by type:** a sensor is offered only the channels whose `sensorTypes` take its type (empty takes every type; CR-0039 point 7), so `gmti` (ground radars) is never offered to a generic sensor. `GET /sensors` gives each channel's `sensorTypes`; the panel filters by them, and a chosen channel that no longer takes the type is missing.
- **Old sensors** (A7, the owner's A4): a saved sensor or a scenario file's sensor without a `type` is a ground radar with its own values, the preset "Custom" and dwell values that keep M5's look: the search width the sector's span (360° all round), the dwell depth the band (1 to 1 000 km), 1 s, no empty dwells. The scenario format stays version 1; `type`, `preset`, the dwell values, `range`, `positionError` and `jobArea` are new optional settings.
- **The ground radar's settings** (function 37): beside function 27's, a preset (from M8: Default 2°, 20 km, 0.2 s, Random, which was M7's Narrow wedge; Narrow wedge 1.7°, 95 km, 0.1 s, Systematic, a Target revisit of 2 s, like the AFSERS radar; Medium wedge 40°, 50 km, 1 s, Random, the default; Wide wedge 180°, the whole band, 4 s, Random; Custom), search width 1° to 360°, dwell depth 1 to 1 000 km, dwell interval 0.1 to 60 s, the **Mode** (`mode`, `random` or `systematic`; Random by default and for a sensor saved without one) and the **Target revisit** (`targetRevisitSeconds`, 0.5 to 60 s, default 2; shown in Systematic only). Choosing a preset sets the three values and the Mode, the Narrow wedge also the Target revisit; changing one of them, the Mode included, makes it "Custom" (A4), on the server part too. A sensor saved with values that match another preset than its own shows that one (a sensor saved with M7's Narrow wedge, 2°, 20 km and 0.2 s, shows "Default"). Until M7 the presets also set an "Empty dwells" share (`emptyShare`); from M8 it is gone, and a stored or imported value is read and ignored (T-196, UQ A). The Wide wedge's depth follows the band (A3), and a dwell's depth is never above the band's where it is used (it is not refused).
- **A revisit's dwells** (function 37; `Dwells`, pure): at the revisit's start, the tracks function 28 detects in the search area and the job area (probability and minimum speed then, A6) are walked clockwise from the search area's start bearing; a dwell takes the next ones while they lie within the search width of its first one and it holds fewer than "most detections per dwell" (A1), so the cap splits instead of dropping. It is the search width wide and the dwell depth deep, placed over its targets, kept inside the search area where it fits, and grows wider or deeper when its targets need more, also when they moved by the time it is sent (true and measured positions). **On a moving platform** (T-193, M7 RC2): each dwell is sent and drawn round where the platform is at its tick, the position its report gives, with the bearings planned at the revisit's start (so a turn does not swing it round); a dwell with targets is placed again over them from there by the same rules. Before, every dwell lay round the revisit's start position, and gmti out, which then read an area off the sensor by the angle it spans there, sent a 2° dwell a few hundred metres off an air platform as up to a full ring. PCA-gmti found the same cause and fixed its side (`pca-gmti/m7` `120c06f6`, its format rule G12): an `ArcBand` now goes by its own shape wherever its centre lies, and a receiver draws it from the report's platform position. With both, the band sent is centred there, so Simulation and View draw the same band. **Empty dwells:** from M7 spread over the whole search area (function 44, below under "The sensor package (M7)"); M6's were beside the dwells with targets (A2).
- **Time** (Q40 A): the dwells follow each other at the dwell interval, clockwise, nearer first at one bearing. A revisit lasts its dwells times the interval, at least the revisit interval; the next starts when it ends. Each dwell is one report, sent at the 1 s tick its time has come (a tick may send several), with `time` the dwell's time, `area` its `ArcBand` (equal bearings all round), its targets measured at their positions at that tick (one gone or hidden by then is left out), and `SensorReport.Sequence(revisit, dwell, lastOfRevisit)`, the revisits counted per sensor from 0. The pairing and the warning are set at the revisit's last dwell from all its targets. A change of the sensor's settings, or its platform hidden or missing, drops the revisit begun; the next starts at its time.
- **The generic sensor** (function 38; not offered in M6, owner PX): revisit time 1 to 600 s (10), range 0.1 to 1 000 km (50), probability 0 to 1 (1), position error 0 to 10 000 m (50, one sigma east and north each), most detections per report 1 to 1 024 (200), Mission; no "Detect all in range" (A7). Each revisit it detects every visible track within the range (and the job area), of any type and speed, with the probability, measured with the error, the nearest up to the cap; one report without a sequence, `area` a `Circle` of the range, `Sensor` with the position error as both errors and no minimum speed. Its coverage is the disc of its range.
- **The job area** (function 39): "Draw job area" (`MapView.draw('rectangle')`), "Draw job area as four points" (`'polygon'`; refused with "A job area has four corners" unless it has four) and "Clear job area", for users with `plugin.simulator.edit`, each saved at once (`POST /sensors` `{platform, jobArea}`, a GeoJSON `Polygon` of the four corners in the order drawn, closed, or `null`; the server part refuses another with the same message). It is saved with the sensor and in scenario files, limits detection to the tracks inside it (a ring in longitude and latitude), and is drawn with the coverage: from M7 dotted, 3 px, with a 15 % fill of its colour (function 41).
- **ECore's inbox** keys by `item.id()` until the CDA's part 3 (SDK 1.5.0, `ChannelRegistry`): until then a revisit's dwells sent to one channel replace each other there, and only the last reaches the receiving plugin. The tests use the test kit's `FakeChannels`, which keeps one per sensor and dwell number (CR-0040 point 2).

## The sensor package (M7; brief functions 41 to 46)

- **The job area's look** (function 41, T-177; M7-S1): an overlay `area` with a 3 px dotted outline (`strokeDash: 'dot'`) and a faint fill, `fillColor` its outline's colour at `fillOpacity` 0.15, in the job-area colour (function 46). The job areas come first in the overlay's items, so the coverage's dashed line lies on top. "Draw job area" draws with the same look.
- **All round by default** (function 42, T-178): a new ground radar has bearings 0° to 360°, which look all round in detection and drawing, as equal bearings do. Saved sensors and scenario files keep their own bearings; the presets set none.
- **Empty dwells over the whole search area** (function 44, T-180; `Dwells`, pure):
  - **The grid** (M7-S3): the search area (and the job area) is divided into nominal dwells, the search width wide and the dwell depth deep, in the revisit's order: clockwise from the start bearing, near to far at one bearing. The last column and row are moved back to end at the area's edge (all round, the last column wraps past the start), so each place has the nominal size.
  - **Free places:** one that holds no track, overlaps no dwell with targets and, with a job area, has its centre inside it.
  - **The spread** (M7-S4): with *k* free places and *e* empty dwells, every (*k*/*e*)-th free place in the revisit's order, the first at an offset from the revisit's random draw (the sensor's seeded generator), so successive revisits differ.
  - **How many** (T-196, M8; the owner's answer of 2026-11-13 in this role's session, "fill the revisit"): a revisit holds the revisit interval over the dwell interval (rounded down, at least one), 100 at 10 s and 0.1 s, so the radar sends one dwell per dwell interval; the empty dwells fill what the dwells with targets leave. With fewer free places than empty dwells, places are taken again, each about as often; none when no place is free. More dwells only when the targets need more (the revisit then takes longer, as before). Until M7 the count was `round(n × share / (1 − share))` for `n` dwells with targets, at most `maxEmptyDwellsPerTargetDwell` × `n` (Q55 B, Q56 A), and a revisit idled after its few dwells until the revisit interval ended.
  - **The floor** (the owner, 2026-11-12, in this role's session): a revisit that would have no dwell at all (no targets and no free place) still sends the owner's Q1 dwell: one empty dwell of the nominal size at the search area's start, or the first place clockwise whose centre is in the job area. So every revisit sends at least one report.
  - **The setting** `maxEmptyDwellsPerTargetDwell` (M7, Settings › Simulator) is removed in M8 (T-196, UQ A): a stored value is read and ignored, as is a sensor's "Empty dwells" share.
  - **M7's Narrow wedge** was 2° (5° before); from M8 those values are the Default preset. A saved sensor keeps its values: its preset shows "Custom" when they match no preset (M7-S5), e.g. a Narrow wedge saved with 5°.
  - **Cost:** the grid is at most 360 × 1 000 places (1° by 1 km over a 1 000 km band all round); with a job area each place's centre is computed, about 0.3 s per revisit in that worst case. The presets give at most a few thousand places.
- **Systematic** (function 50, T-197, M8; TQ A, TR B, TS B; `Dwells.scan`, `Dwells.around`, `Sensors.scan`):
  - **The grid:** the search area (with a job area, the cells whose centre is inside it; at least one) in rows of the dwell depth from the min range outwards, each row in cells of the search width from the start bearing clockwise, side by side, the last cell and row cut to the area.
  - **A pass** (one revisit, `Sequence`'s revisit number): bearing first, row by row, one dwell per dwell interval. Its last cell carries `lastOfRevisit`, and the next pass starts one dwell interval later, from where the platform is then and how it heads; the Revisit interval is not used (greyed in the Sensors panel, with a note). Every cell is a dwell, holding the tracks function 28 detects in it at its time (the minimum speed, the probability, the errors, at most "most detections per dwell", the nearest first); no empty dwell is chosen.
  - **Found targets:** a track detected in a scan dwell is found. Each found target gets a dwell of its own, the search width and the dwell depth centred on where it truly is at the dwell's time (M9, owner YV A; as the view has it at the dwell's tick, so dwells sent in one tick share it; where it was last measured only when it is gone or hidden), every Target revisit, interleaved: when one is due it takes the next slot and the scan goes on after it. Due targets whose dwells would overlap share one dwell, placed over them as Random's dwells are. A target dwell detects as a scan dwell does, but finds no new targets; its detection keeps the range and cross-range error. After 3 of its own dwells in a row find nothing the target is dropped until the scan finds it again. A found target outside the arc at its dwell's time (its bearing off the start and end bearings from the heading then; at any range) gets no own dwell, which counts as one of the 3 (M9, owner YW2 A).
  - **Numbering:** a pass's dwells are numbered in the order sent, scan and target dwells together, so its count varies; function 43 draws them by index as Random's.
  - **The pairing and the warning** are set at each pass's last dwell, from every track its dwells found, each once.
  - **The scan turns with the platform** (M9, owner YW): each dwell lies round the platform where it is when sent (T-193), with its bearings from the platform's heading then, so every scan dwell lies inside the arc; after a turn the pass goes on from its next cell (same row and column) in the turned frame. Random keeps the bearings planned at its revisit's start (T-193, owner YW3 A). With a job area, a pass's cells are chosen with the heading at its start, so after a turn in a pass its remaining cells may lie off the job area until the next pass.
  - **Unlike Random:** a scan cell does not grow to cover a measured position just outside it; a Random dwell does.
  - **Reset:** a settings change, a pause and a hidden platform end the pass; a settings change and a pause also forget the found targets.
- **The dwells drawn** (function 43, T-179; Q57 A; M7-S2):
  - **The server part** keeps per sensor the drawn set: each dwell index's latest dwell (its `ArcBand` as sent, time, revisit and index). A dwell replaces the drawn one of its index; a revisit's last dwell removes the higher indices. So the latest revisit stays whole while the next sweeps across it. While paused they stay; a reset (of all routes, or of the route the platform is on), a removed sensor and a missing platform clear them.
  - **`GET /sensors/dwells[?since=n]`** (`plugin.simulator.view`, as `GET /sensors`) answers `{seq, whole, sensors: [{platform, dwells: [{index, revisit, time, area}]}]}`. With `since` only the sensors whose set changed after `n` (`whole` false), or every set (`whole` true) when a sensor was removed or a reset came after it; 304 when nothing changed. The numbers start at the plugin's start in microseconds since the epoch, so a number from before a restart is never taken for a later one. `GET /sensors` carries the current number as `dwells`.
  - **The web part** draws each dwell as an `area` beside the coverage on the same overlay: a 2 px solid outline, no fill, in the dwell colour (function 46), as `gmti` draws its dwell areas (T-181). It reads the endpoint about once a second while Simulation is shown, "Show dwells" is on and the simulation runs; once after a pause and after a switch back; and once when `GET /sensors`'s `dwells` number changes while paused (a reset). Not objects: not stored, sent, put in a scenario's file or picked.
  - **"Show dwells"** under "Show coverage" in the Sensors panel, on by default, per user in the same user document as "Show coverage" (`sensors-view`: `{showCoverage, showDwells}`); read-only users have it too.
- **Labels and a live preview** (function 45, T-184):
  - **Labels** (overlay `label` items, with "Show coverage"): the start and end bearing as set (from the heading, M7-S6), in whole degrees, at the middle of each straight edge, none when looking all round; the max and min range in km with at most one decimal at the middle of their arcs, none for a min range of 0. Looking all round (0° to 360°, equal bearings, or "Detect all in range") the range labels are ahead, at the heading plus the start bearing (the owner, 2026-11-12). In the coverage colour, size 12, with the map view's halo; they move and turn with the coverage.
  - **The live preview:** while a sensor's form is open, its coverage, labels and job area are drawn at once from the fields' values. An invalid field keeps the last valid drawing; closing the form without saving brings back the saved sensor's. Nothing is sent until Save.
- **Display classes** (function 47, T-182; SDK 1.6.0 part D; Q58 A): the coverage, its labels and the job area carry the overlay's `displayClass` `sensor-coverage`, the dwells `dwell-area`. The map view hides each class while the user's display switch for it ("Sensor coverage", "Dwell areas") is off (`map-view-2d` function 40), so an item is drawn only when both its check box in the Sensors panel and its class's switch are on. The simulator does not read the switches itself.
- **Colours** (function 46, T-185): three admin settings in Settings › Simulator, `jobAreaColour`, `coverageColour` (with the labels) and `dwellColour`, each `{use: "identity" | "fixed", colour: "#RRGGBB"}`. From M8 (T-189, SU A, SV A) `fixed` is the default, with `#BDCF3D` for the job area, `#FD0909` for the coverage and `#7EF26A` for the dwells, as `gmti`'s in View; a setting saved without a valid colour takes its own fixed colour. `identity`, the platform's identity colour (M7's default), stays selectable. `colour` is shown only with `fixed` (`visibleWhen`), its schema default the setting's fixed colour (M7: `#FFFF00`, M7-S7). `colour` is marked `"x-emc2": {"kind": "colour"}` (SDK 1.6.0 part F; Q60 A), so the settings form shows a colour picker with its hex value, and a text field where it cannot; the pattern `^#[0-9A-Fa-f]{6}$` stays. A change applies at once in every browser (`ctx.onSettingsChange`).

## Scenarios (brief functions 32 and 48; T-143, T-152)

- **Where** (function 48, from M7; SDK 1.6.0 part F): the top bar's **"Scenario"** button (`ctx.ui.addTopBarItem`, id `scenario`, order 20, `workspaces: ['simulator.simulation']`), in Simulation only, after the bookmarks. Its menu has "Export scenario…" and "Import scenario…"; Import is greyed with its reason below it (no right, or the simulation runs; the run state is read while the menu is open). A problem or an import's result is shown in the menu, opened again for it. It replaces function 32's two buttons in the Routes panel. The shell's top bar keeps it to Simulation by `workspaces`. Export needs only `plugin.simulator.view`, without which the plugin adds nothing, so it is never greyed for a right.

- **The file** `<name>.emcc-scenario.json`: `{format: "emcc-simulator-scenario", version: 1, name, exportedAt, layers: [layer content with id], objects: [object content with id], simulator: {outputs: ["plugin/link"], sensors: [{platform, settings}]}}`. The layers and objects are Simulation's, as the live picture has them, with `relations` and `fieldSets` and without `version` and `meta`; the routes keep their groups and events in their extension. The simulator part holds the chosen Ground truth outputs and the sensors with every setting, the Mission included (A108). Progress and run states are not exported: an import resets.
- **Export** ("Export scenario…"; `plugin.simulator.view`) asks for a name (by default "Scenario", A112).
- **Import** ("Import scenario…"; `plugin.simulator.edit` and `plugin.simulator.run`, only while nothing runs). The file is checked first: its format, a `version` above 1 refused with a message, and a simulator part of at most 1 MiB; nothing changes before that passes. Every layer and object gets a new id, and every reference to them in the file is remapped: a layer's objects, a route's groups and events (every string in `extensions.simulator` that is an exported id), `relations` (a relation to an object not in the file is dropped) and the sensors' platforms (A111).
  - **As new** asks "Delete N layers and M objects of Simulation?", then resets the simulation, deletes Simulation's objects and layers, and creates the scenario's (A110).
  - **Merge** adds the scenario's layers and objects beside the current ones, adds its sensors and combines its outputs (A109).
  - Layers and objects go as ordinary change requests, one at a time, the routes after every other object: the server part takes an id that is no track of the simulation off a route's list at once (function 9a), so a route created before its tracks would lose them (the ITA's finding, 2026-11-08). A locked layer is locked after its objects are in it. Each refusal is listed. Then `POST /scenario-state` sends the simulator part. Outputs whose channels this server does not offer are kept, shown as missing.

## Saving and restoring (brief functions 19 to 21; ADR-0041)

- **Moves are not saved** (`notSaved()`); everything else is: placings, pauses, events, the route lists.
- **The saving moments** (A22): start, pause and reset; a route reaching its end; "Put on route" and "Take off route"; the choice of outputs; any change of the simulation's routes (their lines, values, lists or events, or a route added or deleted); and a clean stop. There is no periodic save.
- **A save happens at the next tick** (A12): that tick writes every track as a saved update (with its move, if it moves) and the documents with that tick's state, so they agree. A track whose previous write is still in flight is saved one tick later.
- **The documents** (A15, A24): `state` (the format, the time, each route's state, the chosen outputs, how many track documents) and `tracks-0`, `tracks-1`, … with up to 1 000 tracks each: route, at the start or not, seconds on the route, leg and fraction, and the first point whose events it has not passed. Track documents a smaller save no longer needs are deleted.
- **When the worker starts** (the plugin's start, or a worker restart), it reads the documents before anything moves; commands answer 503 until then (A23). Then:
  - every route is paused;
  - the routes' lists decide which objects are on which route (S2). An object with saved progress on its route is placed at the saved leg and fraction, so a route edited after the save still places it on the route; a convoy member still waiting keeps its time;
  - an object on a list without saved progress, or with progress for another route, is placed as "Put on route" places it;
  - progress for an object on no list is dropped, and the object stays where it is; a track deleted meanwhile is counted;
  - every track gets a saved update to its place. The hidden marks and what a reset restores are on the tracks already.
- **A clean stop** pauses every route and saves at once, best effort (ADR-0041 point 6). A document that cannot be read is read again at the next tick, and nothing moves until all are read; a track document that is missing leaves its tracks placed as "Put on route" places them. A document that cannot be written is logged and counted.

## Edits and deletes (brief functions 9 to 9b)

- **An edit of a route** is a change of its line or its points' values.
  - With a new move-or-disconnect choice of "disconnect" (an `edit.number` not seen before), the route's objects are taken off it and stop in place.
  - Otherwise, its objects move with it: they keep their leg and the fraction of it. A leg past the new last leg is the last (A9). A convoy member still waiting goes on waiting. On a paused route they are placed there at once, with a saved update.
  - Edits by other plugins, such as a reshape in `draw-shapes`, leave the extension as it was, so their choice number is not new: the objects move with the route.
- **A route that becomes invalid** pauses, its objects in place with speed 0. They keep where they were on it, and go on from there once the route is valid and started again. While its extension cannot be read at all, the route keeps the last object list read.
- **A route deleted, or no longer of the data type `simulator.route`,** disconnects its objects. The simulator never writes that object. A route moved to a layer outside Simulation would be treated as deleted too; the store refuses that move (an object stays in its workspace, ADR-0039).
- **A track deleted** is taken off its route's list, and counted in the status. So is any id on a list that is not a symbol in Simulation (A10).

## The route's extension

Under the plugin's namespace `simulator` on each `simulator.route` object. It keeps **only what users type** (the ACA's S1). The server part computes everything else and never writes it back. Speeds are in m/s and altitudes in metres, whatever unit is shown.

```json
{
  "points": [
    { "speedKind": "instant", "speed": 8.33, "altitudeKind": "instant", "altitude": 120, "events": [] },
    { "speedKind": "ramp", "time": { "seconds": 600, "from": "previous", "unit": "kmh" },
      "altitudeKind": "ramp", "altitude": 300 }
  ],
  "groups": [
    { "kind": "single", "objects": [{ "id": "…" }] },
    { "kind": "convoy", "spacing": 50, "objects": [{ "id": "…" }, { "id": "…" }] },
    { "kind": "formation", "altitude": 150,
      "objects": [{ "id": "…", "forward": 20, "right": -10, "up": 0 }] }
  ],
  "end": "stop",
  "edit": { "number": 7, "objects": "move" }
}
```

| Field | Meaning | Checked |
|---|---|---|
| `points` | One entry per point of the line, in order | Exactly as many as the line has points, at most 1 000 |
| `speedKind`, `altitudeKind` | `instant` (default) or `ramp` | |
| `speed` | The typed speed, m/s; absent when a ramp point's time was typed last | 0 to 2 000 |
| `time` | A typed arrival time: `seconds`, `from` (`previous`, default, or `start`), `unit` (`mps`, `kmh`, `kn`, `mph`) for rounding | `seconds` up to 7 days; later than the previous point's arrival |
| `altitude` | Metres above the ellipsoid; absent: the object keeps its own | −1 000 to 30 000 |
| `events` | The point's events ("Events", above): `kind` (`set` or `hide`), `objects` (ids; absent: all), and for `set` its `core` and `fields` | The objects are on the route; the kind and the core fields are known; the store checks declared fields |
| `groups` | The route's objects in list order: `single` (one object each), `convoy` with `spacing` in metres, `formation` with offsets in metres from the centre, relative to the first leg, and the centre's `altitude` when assigned (absent when no object had one) | Each object once; a spacing of 1 m to 100 km; offsets up to 100 km |
| `end` | `stop` (default) or `restart` | |
| `edit` | The move-or-disconnect choice of the last edit: `objects` (`move` or `disconnect`) and the editor's edit `number` (function 9) | A number not seen before is a new choice |

- **The commands** are `POST` endpoints (CR-0026): ECore checks the permission and the JSON body before they reach the engine. The body of "Put on route" and "Take off route" is at most 256 KiB and names at most 5 000 objects; the others take the default 64 KiB.
- **Every id is checked** against the simulation's own objects: a route must be a route in Simulation, and an object a symbol in Simulation (404 otherwise). A bad body answers 400. While the engine loads its picture or its saved state, it answers 503.
- **CR-0026's edge** is on `integration/sdk-v1.2` (`8c58da2`), so a running ECore delivers them. Before it, ECore answered `405`, which the panels still show as "not taken yet".

A route has:
- `id`, `version`, `name`, `layerId`;
- `state` (`running`, `paused`, `ended`), `runnable`, and `problems` (`point`, null for the whole route, and `message`);
- `objects`, `lengthMetres` and `durationSeconds`;
- `points`, each with `legMetres` (the leg into it), `distanceMetres`, `arrivalSeconds`, `speed` (m/s) and `speedFrom` (`typed`, `time` or `next-time`).

A value that cannot be computed is `null`. The editor shows the values only when `version` is the version it shows (function 6).

## The web part (brief functions 22 to 24)

`web/`, the package `@emc2/plugin-simulator`. Everything it adds appears in Simulation only (`workspaces: ['simulator.simulation']`, A15).
- **Default panes** (from M4; BS, A70): Routes in the left pane (after Symbols and Shapes); the route editor, Ground truth outputs, Sensors and the Event panel in the right. In the route editor, "Reshape" and, from M7, "Append" are at the right end of the row of "At the end" (A65).
- **Its live picture** is one subscription to the whole Simulation workspace, whichever workspace is shown (CR-0025 part 5; Q11, 2026-10-27). The simulation is small by design, and the fade list and the object actions need every track and route in it.
- **The server part** is read through the GET endpoints once a second while a panel that shows them is mounted, and at once after each command; never while none is (A25), except `GET /sensors`, which the coverage reads every 2 s while Simulation is shown and "Show coverage" is on (function 33). A panel that opens while another watches reads at once too. The commands are `fetch` POSTs with a JSON body under `ctx.serverBase`. A call without an answer within 10 s ends as a 504 does. The end behaviour is a change request on the route's `end`, built from the newest route object; it is a value edit, so it never asks move-or-disconnect (Q10, A30).
- **Route colour** (T-088, BE a, Q17, A62): one colour for all routes, shared by every user since it is each route's `style.strokeColor`. The field shows the routes' colour (the most common one if they differ). A colour picked or typed is sent when committed (the picker closed, or Enter), as one update per route of another colour, changing only `strokeColor`; a new route gets it too. With no routes yet, the choice applies to the next new route drawn in this browser. A refused update is shown with how many routes kept their colour. It needs `plugin.simulator.edit`.
- **Ground truth outputs panel** (named "Outputs" before M5): every channel that takes ground truth, with its field set by its label (function 31), with its plugin, output type, whether it sends deletes, and the declared fields it uses (by their labels where a loaded plugin declares them). A checkbox chooses it (`POST /outputs` with the whole choice). A chosen channel that is not offered, or that answered `CLOSED`, is marked missing; one not offered can be removed (N8).

## Messages and workers

- Worker `engine` (`EngineMsg`, mailbox 10 000, `dropNewest`, restartable). It receives:
  - `Updated` from the store subscription and `Found` from its own query;
  - `Tick` once a second, and `Written` with each of its writes' outcomes;
  - `Control`, `PutOnRoute`, `TakeOffRoute` and `ChooseOutputs` from the commands, and `GetRoutes`, `GetRoute` and `GetOutputs` from the GET endpoints;
  - `Channels` from the channel watch, `Settings` from the settings subscription, `Document` with each document's answer, and `Stop` from the plugin's `stop()`.
- Store: one subscription and, after a worker restart, one query, both naming `simulator.simulation`. Writes time out after 2 s, the query after 10 s. Documents answer within the SDK's 10 s.
- **Writes:** moves are not saved; placing, stopping and pausing a track, events' changes, and the route lists are saved updates. At most one write per object is in flight. A saved write whose answer is lost is written again, an event's change included.
- Status (monitor view):
  - running or paused, with routes running and tracks on routes;
  - the last tick's duration and moves;
  - moves submitted, skipped, refused, lost (no answer) and answered;
  - new snapshots;
  - route lists written and refused, and tracks deleted;
  - events fired and refused, and hidden tracks;
  - the outputs chosen, the missing ones (the first 3 by id), and the items sent, removals, `DROPPED` and `CLOSED`;
  - saves, and documents that could not be read or written;
  - the routes that cannot run and why, then each route's name and state (running, paused, at its end), as many as fit in the SDK's 512 characters, then how many more.

  It starts with "reading the saved state" until the worker has read it.

  A tick longer than 0.5 s makes it a warning.

## Permissions and internet

- `plugin.simulator.view`: the workspace, and the GET endpoints.
- `plugin.simulator.edit`: changes in the workspace's layers (the store checks it), and "Put on route" and "Take off route".
- `plugin.simulator.run`: start, pause and reset.
- No internet and no connections: the simulator sends only through other plugins' output channels.

## Known limits
- **The route editor saves each value at once,** from the newest route object: a change another user makes to the same route in the same moment can be overwritten, as with any editor that replaces an object's content as a whole (model rule 5).
- **A route's object list** is changed only through "Put on route" and "Take off route", not in the editor.
- **A crash or a stop during a run** comes back at the last saving moment (ADR-0041); the moves since are not saved.
- **Events only fire on running routes,** as the objects pass. A route edited with "move with it" counts the events behind each object as passed.
- **The server part's writes win over a user's change made just before them,** as the brief accepts (function 9a).
