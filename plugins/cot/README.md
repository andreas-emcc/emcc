# cot

Cursor on Target (CoT) for emc2. Owner: PCA-cot. Brief: `docs/plugins/briefs/cot.md` (T-040 and T-084). Server part only, on SDK 1.3.0 (`sdkVersion` `^1.3.0`).

**This version receives and sends CoT** over links: a TCP or TLS client to a TAK Server, UDP, and multicast. It sends the objects of chosen layers (brief functions 14 and 17 to 21), and every output link is an **output channel** that other plugins, above all the simulator, hand tracks to (function 15; see "Sending").

## What it does

**Receives CoT from TAK systems and shows it on the shared map, and sends the objects of chosen layers to them.**

- **Links.** A *link* is one configured connection, an entry of the setting `links`: a name, a direction (`in`, `out` or `both`), a transport and a few fields for that transport. Every link runs in a **connection task** (SDK 1.2.0; the one place plugin code blocks and opens sockets, rule C6), restarted by ECore with a back-off of 1 s, doubling, at most 60 s. One link failing never affects another.
  - **`tcp` and `tls`:** a TCP client to the CoT streaming input of a TAK Server (protocol version 0, XML): `host` and `port` (8087 plain, 8089 TLS). The task sends **one presence event** on each connection (a `t-x-c-t` ping with the callsign `emc2`), for TAK Servers that send a client nothing until it has sent one event, and reads. An `out` or `both` link uses the same one connection to write, with its reader in a child task; an `out` link throws away what the peer sends (a TAK Server sends each client what the others send, and a client that never reads would stall it). A link that receives nothing for the idle time (default 5 minutes) is closed and connected again; an `out` link has no idle time. It can be switched off (`sendPresence`); TAK Server 5.7 does not need it (see "Known limits").
    - TLS uses a client certificate. The certificates and their passwords are **local server configuration**, a *TLS credential* that ECore names on its own (`emc2.tls.<name>.*`, ADR-0062; the old `emc2.listeners.credentials.<link name>.*` keys are ECore's to deprecate). They are never in the settings, the repository, a log or the browser. The peer's certificate must name the host.
    - **A TLS link picks its credential** (M9, K1; brief function 33): `links[].tlsCredential`, a select in the form of the names ECore has. Empty: the credential named like the link, as before, so a renamed link without a picked credential still needs its credential renamed. A changed credential restarts the link's task. A name ECore lacks, or an expired or unreadable credential, fails the task's start before any connection to the host is opened; the link's status says so (`the TLS credential 'tak-ca' is missing`, or ECore's message, which names the credential and the date and no path), and ECore restarts it with the back-off. The other transports ignore the field and keep its value (greyed).
  - **`udp`:** one datagram is one event. `in`: received on `address` and `port`. `out`: sent to `host` and `port`. `both`: one socket bound to `address` and `port`, which also sends to `host` and `port` (the same port at both ends, as for peers of one SA network; a test peer on this computer binds another address such as `127.0.0.2`, so that the link does not send to itself). **The address defaults to loopback (127.0.0.1)**: only an administrator who sets another address, or `0.0.0.0`, receives from the network.
  - **`multicast`:** `in` joins the group, `out` sends to it, `both` does both. The group is in `address` (for example TAK's mesh SA, `239.2.3.1`) and `port`, joined on the network interface that an administrator names in `interface` (its name or its display name). **Without an interface the link stays stopped**, and its status says that an administrator must name one.
  - **Hosts, ports, addresses, groups and interfaces come only from the link's settings**, never from a received event, a message or an object's data (ADR-0030).
- **Sending** (`out` and `both`, brief functions 14, 17 to 21). A link sends the **objects of its source layers**, picked in the settings form (existing layers only, View's workspace; one subscription per layer however many links use it).
  - **What goes out:** a `core.symbol` with a point becomes a CoT atom (`a-<affiliation>-<dimension>-<function>`). Anything else is skipped: a shape ("not a symbol"), a symbol CoT has no type for such as a tactical graphic or a symbol set with no CoT battle dimension ("no CoT type").
  - **When:** when the link comes up, the current objects of its layers (paced, at most 5 000 a second); then each create and update. **Only real changes go out:** an object is sent again only if its event differs from the last one in anything but its times and the `<_flow-tags_>` element a TAK Server adds, except for the refresh. A link that went down and came up sends everything again (what was deleted while it was down is simply not there: no stale event is sent for it).
  - **An object that leaves** what the link sends (deleted, moved to another layer, or raised above the link's classification) goes out as **one event that is stale at once**, made from what was sent before (uid, type, position), so an object that was raised gives away nothing of its new state.
  - **Never back to where it came from:** not when its data source is the link, nor when its last change came in on it.
  - **Stale time and refresh** (brief function 18): `@stale` is the object's expiry if it is in the future, else the object's declared field `staleSeconds`, else the link's `staleSeconds` (default 60 s). An object whose expiry has passed is not sent again. **The refresh:** an object of a source layer that has not changed is sent again after `refreshSeconds` (default 30 s; 0: only changes go out), until its expiry has passed, so that TAK does not show a static marker as stale. The link's status warns when `refreshSeconds` is 0 or longer than `staleSeconds`.
  - **The highest classification** (`highestClassification`, `{policy, classification}`; absent: the classification of the server's default label): an object above it, of another policy, or with a classification outside the policy's order is skipped. If the server does not know the limit, nothing passes and the status says so.
  - **Rate:** the task's inbox keeps only the latest event per object (at most 20 000 waiting), so a slow peer never builds up a queue. A burst beyond 10 000 events in one second (a large layer, a changed limit) waits in the worker and goes out paced, 5 000 a second, so that nothing is evicted from a full inbox; an event is recorded as sent only when the task has taken it. Skips are counted per reason (not a symbol, no CoT type, above the highest classification, unknown limit, expired, backlog) in the status and the monitor view, and logged at most once a minute per link.
  - **The event** (`CotMapper.encode`, in the codec): the uid is the `externalRef` id for an object that came from CoT and the object id for the others; `@time` and `@start` are the sending time; `how` is the original's or `h-e`; `ce`, `le`, `access`, `caveat` and the rest come from the extension for an object that came from CoT. The **type** is the SIDC's: APP-6B by the table in reverse, APP-6D and APP-6E by a closed table (`CotSymbolsNumeric`, made by `generate-app6d-table.mjs` from milsymbol's own correspondence: a numeric symbol drawn from the same icon parts as an APP-6B function is that function; 147 rows), with the parent, then the dimension's generic symbol, as fallbacks. An object that came from CoT, with its symbol unchanged, keeps its type. The **`<detail>`** (from T-129, see "Symbol codes and amplifiers" below, also the symbol code and its amplifiers): for an object that came from CoT the raw detail with the changed callsign, remarks, course, speed, team and role put over it and everything else in it unchanged byte for byte (an unchanged object gives the detail it came with); for the others built from the name (or the unique designation), the description, direction, speed, team and role.
- **Reading.** The task cuts a TCP stream into events (a datagram is one already) and parses each one with the JDK's XML parser with **DTDs and external entities off** (no XXE). An event that is larger than the limit (64 KiB), does not parse, has a DTD, or is of a type the plugin does not show (chat, tasking, drawings, pings) is counted and dropped; the link continues, and the worker logs at most one warning per minute per link, with how many were dropped since the last (text of the peer is cleaned of control characters and cut first). Malformed input does not swallow the events after it: the framer ends the broken document at a mismatched end tag, a `<` inside a tag, or the next `<event>`.
- **Mapping** (interop note, section 7). Atoms (`a-…`) and map points (`b-m-p-…`) become `core.symbol` objects with `dataType` `cot.cot` (display name "CoT"):

  | CoT | Object |
  |---|---|
  | `point/@lon`, `@lat` (`@hae`) | `[lon, lat]` (altitude left out when `9999999.0`) |
  | atom type `a-f-G-U-C-I` | APP-6B SIDC `SFGPUCI--------`: affiliation, battle dimension and function from a closed table; a function it lacks falls back to its known parent, then to the dimension's generic symbol |
  | map point `b-m-p-…` | the generic point symbol `GUGPGPP--------` |
  | `detail/contact/@callsign` | `properties.name`, and the symbol's `uniqueDesignation` (the text next to the symbol; owner, 2026-10-12) |
  | `detail/remarks` | `properties.description` |
  | `detail/track/@course`, `@speed` | modifiers `direction` (degrees from true north) and `speed` (m/s) |
  | `detail/__group/@name`, `@role` | the declared fields `team` and `role` (below), when the value is one of TAK's own |
  | `@time`, `@start`, `@stale` | `time.observed`, `time.validFrom`, `time.expires` |
  | everything else | the plugin's own extension `cot`, see below |

- **Extension `cot`** keeps what the core has no field for, so CoT stays lossless: `type`, `how`, `version`, `access`, `qos`, `opex`, `caveat`, `releasableTo`, `ce`, `le` (as written, `9999999.0` stays exactly that), and `detail`: **the whole content of `<detail>` as XML text, exactly as received**. It includes `contact`, `remarks`, `track` and `__group`, which also have core fields or declared fields, because they carry attributes with none (`endpoint`, `phone`, `slope`, …). No other namespace is written; other plugins' extensions are forwarded untouched (ADR-0018).
- **Declared fields** (ADR-0038, brief function 16): the manifest declares `team` (TAK's 14 team colours) and `role` (its 8 roles), in the extension `cot`, editable by other plugins' editors through the "+". A received `__group` sets them; a value outside TAK's lists stays only in the raw `detail`, and an event without `__group` leaves both as they are, so a value an editor set survives the next event. They go out as `__group`. A third declared field, `staleSeconds` (an integer, 1 to 86 400 s), sets the stale time of what is sent for this object.
- **Identity.** `meta.externalRef` = `{system: "cot", id: <uid>}`, so repeated events move the same object, also after a restart (the plugin finds its objects again through a store subscription). A CoT uid is globally unique: **the same uid on two links is one object**, which keeps the `dataSource` and the layer of the link that created it; `meta.created.by.system` and `meta.modified.by.system` name the link of each change. An update never changes an object's layer, label, style or data source.
  - An event older (by `@time`) than the one last applied for its uid is dropped. Events for one uid wait in the worker's mailbox with the latest winning, so a burst costs one change request.
  - Objects changed by emc2 users stay editable; the next event for the uid overwrites the core fields (last write wins) and leaves other plugins' extensions alone. A deleted object is created again by the next event.
- **Expiry.** The plugin sets `time.expires` from `@stale` and declares the defaults of `cot.cot`: shown faded from the expiry on, **removed by ECore** 10 minutes after it (configurable per data type in the settings view). **The plugin never deletes an object.**
- **Target layer** (ADR-0037). An input link writes into **its target layer**, picked in the settings form: one of View's layers, or a new one made with the form's **+** button (SDK 1.4.0, T-133), which creates the layer at once and saves it with its id. So a picked layer exists before the first event, and the plugin uses it as it is. Absent means a new layer named like the link, made at the first event. **A layer that is deleted later is made again**, on top and with the label of the link, under the name the form saved, at the next event; two links that name the same gone layer **share the new one**. The plugin keeps what it made in the plugin document `layers`. The status shows each link's actual layer, since the setting keeps the id of the one that was deleted. A value without an id (saved before 1.4.0; the form no longer saves one) is read as before: a layer by that name, shared and made at the first event.
- **Label.** The link's label setting, by default the server's default label. Mapping CoT's `access`, `caveat` and `releasableTo` to STANAG 4774 labels comes with access by label; the raw values are in the extension.
- **Status** (monitor view): per link `name: state, N read, N created, N updated, dropped N (why), N echoes ignored, events per second, N sent, N write stalls, layer 'x' [in tcp host:port]`: connected (or listening) since when, or not connected with the last error and the next try, or stopped with the reason. Without a configured link the plugin starts, does nothing and says `no link configured`.
- **Stored `streams`** of M1 and M2 are **not read** (owner, 2026-10-26: no migration). The plugin starts, and its status (`DEGRADED`) names them and says to enter them as links. The layers the streams made stay, to be picked as a link's target layer; a link named like an old stream finds the objects it had made and goes on updating them (the uids are the same), and the plugin document of M1 and M2 (the layer of each stream, by the stream's name) is still read, so that such a link finds its layer even when it is empty.

## Settings

Edited in the settings view by users with `settings.admin`; changes apply without a restart (a link whose own settings and the shared ones below are unchanged keeps its connection; a change of the target layer or label applies to the objects made from then on, and a change of `idleTimeoutSeconds`, `maxEventBytes`, `sendPresence` or `presenceCallsign` reconnects every link).

| Name | Default | Meaning |
|---|---|---|
| `links` | none | The connections to TAK systems: a list of entries with the fields below. The plugin does nothing until there is one |
| `links[].name` | – | The link's name and key: the data source of what it receives, the status entry, the name of its TLS credentials unless it picks one (`tlsCredential`) and its task. Lowercase words separated by hyphens, at most 64 characters (`tak-north`); `manual` is reserved |
| `links[].id` | – | The link's stable id: a UUID v7 that ECore gives it and never changes (SDK 1.8.0 part F). The plugin does not read it; no form shows it |
| `links[].direction` | – | `in` receives, `out` sends the objects of its source layers, `both` does both over one connection |
| `links[].transport` | `tcp` | `tcp`, `tls` (client certificate from local configuration), `udp` or `multicast` |
| `links[].tlsCredential` | `""`: the link's name | `tls`: the name of the TLS credential in the server's local configuration, picked from ECore's names (M9, function 33); greyed for the other transports |
| `links[].host`, `links[].port` | – | `tcp` and `tls`: the TAK Server's CoT streaming input (TLS 8089, plain 8087). `udp`: `host` is where `out` and `both` send to. `udp` and `multicast`: `port` is the port received on and sent to |
| `links[].address` | `127.0.0.1` | `udp`: where to listen (loopback unless an administrator sets another address). `multicast`: the group, required |
| `links[].interface` | none | `multicast`: the network interface that joins the group, required: without it the link stays stopped |
| `links[].targetLayer` | absent | The layer picker: a layer from the list, or one made with the **+** button (picked with its id). Absent: a new layer named like the link |
| `links[].label` | the server's default label | `{policy, classification}` of a new layer and of the objects |
| `links[].sourceLayers` | none | `out` and `both`: the layer picker, existing layers only: the layers whose objects the link sends |
| `links[].highestClassification` | the default label's | `out` and `both`: `{policy, classification}`: objects above it are not sent |
| `links[].staleSeconds` | `60` | `out` and `both`: the stale time of what is sent when the object has no expiry in the future and no `staleSeconds` of its own (1 to 86 400) |
| `links[].refreshSeconds` | `30` | `out` and `both`: an unchanged object is sent again after this many seconds; `0`: only changes go out (0 to 86 400) |
| `links[].enabled` | `true` | Whether the plugin runs the link |
| `idleTimeoutSeconds` | `300` | A TCP or TLS link silent for this long is closed and connected again (1 to 3600) |
| `writeStallSeconds` | `60` | An `out` or `both` TCP or TLS link on which one write (one event, or the presence event) has not finished for this long (the peer stays connected but stops reading) is closed and connected again (5 to 3600). Read by the worker only: a change does not reconnect the links |
| `maxEventBytes` | `65536` | The largest event accepted (1 KiB to 1 MiB); a larger datagram is dropped too |
| `sendPresence` | `true` | One `t-x-c-t` presence event on each TCP or TLS connection. See "Known limits" |
| `presenceCallsign` | `emcc` | The callsign in the presence event |

**Fields a link does not use** (SDK 1.3.0, T-107; from SDK 1.8.0 the form hides them instead of greying them): the settings form shows a link field only when the link uses it, and keeps its value, so switching a link from `both` to `in` and back loses nothing. The manifest says so with `x-emc2.enabledWhen` on `direction`: `targetLayer` and `label` in `in` and `both`; `sourceLayers`, `highestClassification`, `staleSeconds` and `refreshSeconds` in `out` and `both`; and on `transport`: `host` in `tcp`, `tls` and `udp`, `address` in `udp` and `multicast`, `interface` in `multicast`. Validation does not change: a greyed field's value is still checked, and the plugin ignores it (an `in` link that kept `sourceLayers` runs and sends nothing; an `out` link ignores `targetLayer`). `writeStallSeconds` is one setting for all links, not a link field, so it is not greyed.

**The field set `cot.unit`** (SDK 1.4.0, ADR-0050; T-132, T-131): the manifest declares the fields `callsign` (text, at most 64), `team`, `role`, `staleSeconds`, `how` (text, at most 16), `ce` and `le` (numbers in metres, 0 to 9 999 999; 9 999 999 is CoT's "unknown") and the set `unit`, "CoT unit", with all seven. Every field is editable by others, on every object, so an editor can add the set to a manual symbol or a simulator track and fill in the CoT values. The values are the plugin's own, in `extensions.cot`. **From SDK 1.5.0 (M6, T-165, brief function 30) the data type `cot.cot` names the set** (`"fieldSets": ["unit"]` in the manifest), so the object store gives `cot.unit` to every `cot.cot` object, a symbol a user places by hand as CoT included, and to one whose data type changes to it; the plugin still adds the set to what it receives itself (the store adds it only once). The data type stays one that users make by hand (`manual`), and its objects that come from CoT keep `time.observed` (the event's `@time`), so tracks fade and go by the data type as before; a symbol placed by hand has none and does not expire by it.
- **In:** every object `cot` creates or updates from an event carries the set, so an object made before M5 gets it at its next event; an update also carries the stored object's relations and sets (an update replaces the relations). `contact/@callsign` fills `cot.callsign`, the Name and the unique designation; an event without a callsign leaves `cot.callsign` as it was. `@how`, `point/@ce` and `@le` fill the set's `how`, `ce` and `le`. **A value the declared field does not take stays out of the set** (a `how` of more than 16 characters, a `ce` or `le` that is not a number or is outside 0 to 9 999 999, a callsign of more than 64): the object is still stored, its Name and its raw detail keep what was received, and the sent event falls back to the defaults below.
- **Out, for every object sent** (also a simulator track or a manual symbol that never came from CoT): the callsign is `cot.callsign`, else the Name, else the unique designation; `@how` is `cot.how`, else `h-e`; `point/@ce` and `@le` are `cot.ce` and `cot.le`, else `9999999.0`.
- **The channel** of an out link names the set (`ChannelInfo.fieldSet` is `cot.unit`). Its `fields` (`team`, `role`, `staleSeconds`) stay until the simulator reads the set.
- **Vessels out:** a symbol of the standard `vessel` goes out as a surface unit of its identity, `a-<affiliation>-S`: the second digit of its code gives `p`, `u`, `a`, `f`, `n`, `s` or `h` for 0 to 6; the first digit, the context, is not sent. Incoming CoT stays APP-6.

A bad entry is left out and reported in the status (`DEGRADED`), the others work. A link that cannot run (a multicast link without a group or an interface, a TCP link without a host) stays in the status with the reason and is not started. The settings schema keeps its top level open, so that ECore still accepts stored settings that hold `streams`.

## Messages and services

- Provides and requires no services; no topics, endpoints or web part. Manifest: `kind` `general`, `properties` `["ingoing", "outgoing"]`, `connections` (`tcp-client`, `udp`, `multicast`; direction `both`; pointer `/links`), one data type `cot.cot`, the declared fields `team`, `role`, `staleSeconds`, `callsign`, `how`, `ce` and `le`, and the field set `cot.unit` (see "The field set"). No `network` (no listener) and no `internet`.
- **Connection tasks:** one per enabled link, named like the link: `TcpLinkTask` (TCP and TLS client) or `DatagramLinkTask` (UDP and multicast), with `Restart.always` and the back-off above. Each run gets a fresh task. The task cuts what it receives into events (`EventFramer` for TCP) and hands each to `InputPipe`, which parses it and sends `ApplierMsg.Received` (an event, coalesced per link and uid), `ApplierMsg.Counted` (counters, coalesced per link) and `ApplierMsg.Connected` to the worker. ECore's `ConnectionEvent`s arrive as `ApplierMsg.LinkEvent`. The task counts `events in` for the monitor view.
- **Channels:** one `ChannelRef` per out or both link (`LinkRuntime.channel`), offered and withdrawn by `OutputEngine.syncChannels`; each item reaches the worker as `ApplierMsg.FromChannel` (coalesced by link and object id).
- **Output** (`OutputEngine`, run by the worker, with `LinkOutput` per link): one store subscription per source layer (`ObjectQuery.inLayer(...).inWorkspaces("core.view")`), the objects of each layer, and per link what was sent (a digest, the tick, and the uid, type and position for an event that is stale at once). It posts `LinkInbox.Send(id, xml, expires)` to the link's task, whose inbox coalesces by object id (`expires` is a channel item's own expiry, or null); the task writes it and tells the worker how many it has written and how many it skipped as expired because the expiry passed while the event waited (`ApplierMsg.Written`, both cumulative). The classification check is `context.classifications().within(label, limit)`.
- **Worker `applier`** (`ApplierMsg`; mailbox 50 000, `coalesceByKey`): owns all state. It submits changes with `Change.createObject(...).withExternalRef(...)` and `Change.updateObject`, at most one per uid in flight and at most 1 000 in all, and holds a subscription to `ObjectQuery.byExternalSystem("cot")`. A lost answer (`Unknown`) is followed by a query of the uid and a new try, three at most.
- **Timer:** one, every second: status, rates, a new try for a layer that could not be made, the objects still to send after a link came up, and the refresh of every output link (one timer for all, not one per object).
- **Plugin document** `layers`: `{"named": {"<layer name>": "<layer id>"}}`, the new layers the plugin made, by the name the links that share them give.
- **Code:** `codec/` is the CoT codec (event ↔ object content in both directions, the SIDC tables, the XML, the detail editor, the team and role), `stream/` cuts the stream into events, the rest is the SDK side.

## Permissions and internet

No permissions of its own. Users edit the objects with `objects.edit`; changing the links needs `settings.admin`. **No internet**: the plugin connects and listens only where its links' settings say, which is the local network, and the manifest's `connections` declares it. ECore checks no host (owner, 2026-10-18): the rule is kept by the plugin and the reviews.

## Sending

Two things go out of an `out` or `both` link: the objects of its source layers (above), and what other plugins hand to its **output channel** (brief function 15, ADR-0037).

- **The channel.** Every enabled `out` or `both` link with no problem is offered with `context.channels().offer`: the id `cot/<link>`, the link's name as its display name, the output type `cot`, the capability `DELETE`, and the declared fields `cot.team`, `cot.role` and `cot.staleSeconds`, so that a sender such as the simulator can offer them. A link that is disabled, removed, has a problem or no longer sends **withdraws** its channel; **a renamed link** withdraws the old id and offers the new one, so a sender that saved the old id shows it as missing. The channel stays through a reconnect and a change of the link's host or port.
- **An `Update` goes out as an event** (the same codec as for a source layer's object: type from the SIDC, position, callsign, direction and speed, team and role as `__group`). **It goes out as it comes**, also when its content is unchanged: a sender's standing tracks are sent every second, and its next item is their refresh, so the link **never refreshes channel items** and does not compare them with what it sent before. The uid is the item's id.
- **The echo of what emc2 sent is not an object** (owner, 2026-10-27 and 2026-10-28, from the ITA's finding on `ita/m3-flows`). With an input and an output on the same TAK network and the output sending from the input's layer, the TAK Server relays what emc2 sent back to the input. A track that came from TAK has its uid as its external identity, so its echo finds the object and changes nothing (the comparison above). But a symbol drawn in emc2 goes out with a uid emc2 made up (the object's id) and has no external identity: its echo would come in as a second object in the input's layer, and the output would send that one too. So the worker keeps **the ids of the source-layer objects, not made from CoT, that any out link sent, and the layer each was sent from** (`SentUids`; also the stale events of their deletes, which are echoed too) until the stale time of what was sent plus 60 s, renewed by each new send, at most 200 000 (one entry evicted per send at the cap; expired ones swept every 5 s). An incoming event with such a uid, **no object stored under it, and an input link whose target layer is the layer the object was sent from**, is the echo: it is **not stored** and is counted as "N echoes ignored" in the input link's status (not as a drop). **Through an input link that targets another layer the same event is a round trip and is stored**: it becomes an object of that layer, with the link as its data source (the ITA's criterion 15); only the same layer would get a second object next to the symbol, and only that is a loop (the output sends that layer).
  - **Channel items are not remembered** (owner, 2026-10-28; brief function 19: echo loops come from source layers, not from a sender). A sender such as the simulator hands tracks to a link and expects them back through another link into a layer; they are stored like any event from TAK. Nor is a uid that came in from CoT and went out again (a relay): it is the object's external identity, and an event for it must create or update its object.
  - **Not covered:** an echo that comes after the stale time and the 60 s, or after the plugin was restarted (the links send everything again at start, which fills the memory again). The other side of the rule: a genuine event from another TAK peer that carries a uid emc2 made up (a client that moved emc2's symbol and kept its uid) is taken for the echo and ignored while no object is stored under that uid and the uid is remembered; the memory covers every input link of the plugin, not only those of the TAK network the symbol went to.
- **A `Removal` goes out as one event that is stale at once**, made from the identity (uid, type, position) the link kept when it sent the item; nothing else of an item is kept. **An identity is kept only until the stale time of the event that was sent** (each item the sender sends again renews it): after that TAK has dropped the track, a removal sends nothing, and the identity is forgotten on the tick, so the count (in the status: "N channel items tracked") falls for a sender that stops without a removal. At most 200 000 identities per link at once. Past that, an item is still sent but its removal is not: it is counted as **"removal not kept"** when it is sent (a skip reason in the status and the monitor view; one warning a minute). A removal for an item the link does not remember, for any reason (past the cap, past its stale time, never sent), sends nothing and is not counted. An item that was sent and is later raised above the highest classification goes stale at once, from what was sent before. The brief says the link remembers nothing of channel items; a removal event needs a uid, a type and a position, which the removal itself does not carry, so this is the smallest memory that makes it work.
- **The same rules as for a source layer:** the link's highest classification (checked on the item's label), the stale time (the item's expiry if in the future, else its `staleSeconds`, else the link's: the simulator sets each item's expiry), skips counted per reason (not a symbol, no CoT type, above the highest classification, unknown limit, expired, removal not kept, dropped) in the status and the monitor view, and one warning a minute per link (for the skips the worker makes; "expired" at the moment of writing is only counted). "Removal not kept" is counted **per send**: a standing track that is past the cap and sent every second is counted every second. An item whose data source is the link is not sent back to it (a channel item carries no change history, so the data source is all there is to compare).
- **Rate:** ECore keeps one inbox per channel that holds only the latest item per object and hands items to the worker's mailbox, which coalesces them by link and object id; the worker posts each event to the link's task, whose inbox coalesces by object id too. So ten updates for one object while the task is busy send only the latest.
- **While a link is down** (owner, 2026-10-27, brief function 21): its channel items wait in the task's inbox, one per object, and go out when it is up again.
  - **The times** are those of the moment the item was handed to the channel (`@time`, `@start`, and the stale time counted from then), so an item **without an expiry** that waited longer than its `staleSeconds` arrives already stale. **An item with an expiry** gets it as its stale time, so it does not arrive stale; if the expiry passes while it waits, the task skips it when it comes to write it and counts it as **"expired"** (the simulator's tracks carry an expiry, so after a long outage they are skipped and TAK lets them go stale itself).
  - **At most 20 000 objects wait.** The 20 001st is not posted and is counted as **"dropped"**; an item for an object that waits already replaces it.
  - **A removal replaces a waiting update.** If TAK never had the item (its first event was still waiting), nothing goes out for it, and the waiting update is gone; if TAK did have an earlier one (and its stale time has not passed), an event that is stale at once goes out. A removal that finds 20 000 other objects waiting is itself refused and counted "dropped", and TAK keeps the track until it goes stale.
- **The target** (acceptance criterion 25): 1 000 tracks at 1 Hz through the channel to one `tcp` link are sent without a growing backlog (the test kit's load test, ten seconds: no item waits in the channel or the worker after each second).
- **A peer that stops reading does not hold a link for ever** (owner, 2026-10-28, Z1). A write to a socket has no timeout in Java, so the task that blocks in one cannot notice. Before each write it tells the worker (the `Written` message, coalesced per link, with `writing` set); after it, it tells it again. The worker's tick (one a second) sees the same write, the same run and the same count, again and again: when that has lasted `writeStallSeconds` (default 60, 5 to 3600) it stops the task, which makes ECore close the socket and so ends the blocked write, and starts the link again. The status says `not connected (write stalled, reconnecting)` and then counts `N write stalls`; a warning is logged at most once a minute per link. The new connection sends every object of the source layers again, paced, as after any reconnect. Not stalled: a peer that is slow but takes data (the next write is another write), a link with nothing to write, a link that is down. A second stall takes the limit again, so a peer that never reads makes one new connection a minute at most; there is no other back-off. **What waited in the old task's inbox is lost**: the channel items posted since (up to 20 000), which are live tracks that the sender's next items replace. An `in` link is not watched; its read has the idle time. A stall is noticed with up to a second's delay.

The codec's object to CoT direction knows nothing of layers, links or sockets (`CodecIndependenceTest`, acceptance criteria 13 and 26).

## Symbol codes and amplifiers (M5, T-129; brief functions 26 to 29)

**ATAK's format both ways, WinTAK's read** (owner, MD A). ATAK writes `<__milsym id="SFG*U-----*E***">` (a 15-character MIL-STD-2525C code, `*` for an empty position; `__milicon` is the same again) with the amplifiers as children, `<unitmodifier code="C">12</unitmodifier>`. WinTAK writes `<mil2525c SIDC="…"/>` and `<amp unique_designation="…" higher_formation="…" quantity="…" status="…"/>`. Recordings of ATAK 5.6 are the fixtures in `server/src/test/resources/fixtures/atak-5.6/`; WinTAK's in `wintak-reconstructed/` are **rebuilt from the recorded values, not raw**.

- **In:** the code is `__milsym/@id`, else `__milicon/@id`, else `mil2525c/@SIDC`. It becomes an **APP-6D** symbol (`symbol.sidc`, 20 digits); the CoT type stays in the extension. Without a code, or when it cannot be converted, the symbol comes from the type as before (and the element stays in the raw `detail`). The amplifiers become text modifiers (`C` quantity, `F` reinforced/reduced, `G`, `H`, `J`, `K`, `L`, `M` higher formation, `N`, `P`, `R2`, `T` unique designation, `V`, `W`, `X`, `Y`, `AA`, `AD`, `AE`, `AF`, `AG`, `AO`); WinTAK's `<amp>` attributes the same by their camelCase name (`status` is the combat effectiveness); ATAK's win. A code or attribute not in the table, an empty value (ATAK's empty `F`) and one over 128 characters are left out and stay in the raw `detail`. **The unique designation `T` wins over the callsign**; the callsign still sets the Name. `<remarks>` stays the description and is not parsed. WinTAK's type suffix (`a-f-G-U-C-I-C`) is not read.
- **Out:** every symbol gets `<__milsym id>` and `<__milicon id>` with the 2525C code and a `<unitmodifier>` per amplifier that is set (in the order above), besides its type. An APP-6B code goes out as stored; a vessel and a code that cannot be converted get neither. **The unique designation is not sent while it is the callsign** (an object without a designation has the callsign as one, so ATAK would show it twice). For an object that came from CoT, a received `mil2525c` and `amp` are taken out and `__milsym`/`__milicon` put in place, unless they already say what the object says (then the detail is untouched, an empty `F` included). The type is the usual one: an object from CoT whose symbol is unchanged keeps the type it came with (a WinTAK suffix too).
- **The conversion** (`Sidc2525c`): the symbol set, entity and sectors come from `Sidc2525cTable`, **generated by `generate-2525c-table.mjs` from mil-sym-ts 2.10.9's `c2d_default` table** (Apache-2.0, `@armyc2.c5isr.renderer/mil-sym-ts-web`; the origin goes into the third-party notices). The positions it stars (identity and exercise context, status, headquarters/task force/dummy, echelon, mobility) are fixed tables from APP-6(E)(2) Annex A, checked against mil-sym-ts's `C2DLookup.getDCode` and milsymbol 3.0.4. A function the table lacks gives its parent. ATAK's plain unit `S*G*U-----` is a land unit with no function (entity `000000`) with its echelon, not `110000` Command and Control. Where several 2525C ids have the same APP-6D key (7 among the symbols), the first in the table's order.
- **What the generator does to the source** (`node plugins/cot/generate-2525c-table.mjs --check`): keeps the symbols (`S…`), leaves out the 6 records of version 15 (a draft) and 5 records whose sector modifier is not two digits (a defect in the source), and gives the 44 whose 11th character is `-` or `H` the starred basic id mil-sym-ts's own lookup makes (it never finds them as they are; none becomes the same as another). The class adds two empty frames the table lacks, sea surface (set 30) and subsurface (set 35), so that a mobility or an echelon on them has a symbol.
- **Without an equivalent** (left out): in, 2525C's installation (`H` in the 11th position) and the country code and order of battle; out, sectors that no 2525C id has (the parent's code goes out), APP-6E's digits 21 to 30, the leadership indicator, and an HQ, task force or dummy beside a mobility (position 11 holds the mobility). Any status character other than the listed ones counts as present, as mil-sym-ts has it (WinTAK writes `SFSSCL---------`).
- **Recorded in no client:** HQ, task force, feint/dummy and mobility (ATAK has no setting, WinTAK sends none of them). They are defined from the 2525C positions and checked against the standard, not against a recording.

**A moved track stays where the user put it** (SDK 1.5.0 part 5, ADR-0053 point 8; brief function 31, T-155). A user may move a received object into another layer ("Move to layer…"); the next event for its uid updates it **in that layer**, from any link, and only a new uid goes to the link's target layer. A copy ("Copy to layer…") has no external identity, so the plugin never updates it. This is how the plugin always wrote updates (the object keeps its layer, label and style); a test now holds it.

## The settings form (T-204, M8; SDK 1.8.0 parts C, D and F)

- **The icon** `Radio` in the manifest (`icon`), for the Settings list. `cot` has no web part, so no panels: nothing for part C.
- **A link's side form** (`x-emc2.groups` on the link items): name, transport, direction and enabled first, unheaded; then **Connection** (host, port, address, interface), **Layers** (receive into, send from), **Classification** (the label of what is received, the highest classification sent) and **Sending** (stale time, refresh). The page: the links' list, then **Connections** (idle timeout, write stall, presence) and a folded **Advanced** (the largest event).
- **The links' list** (`x-emc2.item`): a link is named by its `name` ("New link" for an unsaved one with no name, "Link 3" for a saved one), its state is `enabled`, its columns direction, transport, host and port, its noun "link" ("Add link", "Delete link?"). The source layers have `item` too (name, noun "layer"); the form shows them as the layer picker they are.
- **A stable id** (part F, `item.id`): each link has an `id`, a UUID v7 that ECore gives it and never changes, shown by no form (a string, `readOnly`, not required). **The plugin does not read it**: a link is still known by its name, which is the data source of what it receives and the key of its TLS credentials, so a rename is still a removal and an addition for `cot`. A change that only gives the links their ids restarts nothing (`SettingsTest`).
- **Hints** (`x-emc2.hint`, at most 80 characters) for every property whose description is longer; the description stays behind the info button. **Units:** seconds on the stale time, the refresh and the two timeouts; bytes on the largest event. Titles on the fields whose name is not a label ("Stale time", "Receive into layer").
- **Checked by** `check/settings-hints.test.mjs` (the SDK's `settingsHintsProblem` finds nothing; the sections, words, columns, the id, the hints, units and widths).

## The palette "CoT" (M7, SDK 1.6.0 part G; brief function 32, T-156)

The manifest declares one symbol palette, `cot.cot` (name "CoT"), which `draw-symbols` offers in its Symbols panel: **one symbol per row of the closed APP-6D and APP-6E table** (`CotSymbolsNumeric`, 147 rows, in its order). Each is `APP-6D` with the row's 20 digits, the standard identity friend and status present (`draw-symbols` sets the identity the user chooses), and the label `<CoT type without its affiliation> – <entity name>`, e.g. "G-U-C-I – Infantry" (the owner's assumption C1). A symbol placed from it goes out as that CoT type through an `out` link, because the table is the same. Nothing is written at runtime: the palette is only declared.

- **Made by** `node plugins/cot/generate-palette.mjs` (writes the `symbolPalettes` block of `plugin.json`; `--check` compares). The entity names are mil-sym-ts's (`MSLookup`, 2.10.9, Apache-2.0, the repository's own dependency). **One row has no name there** (`10163400=GUSS`): its label is the type alone. A name over the schema's 128 characters loses its last " / " alternatives (one row: the unmanned aircraft).
- **Kept in step by tests:** the Java `PaletteTest` (the manifest's palette and the table have the same rows in the same order; each code goes out as the row's CoT type through the codec) and `check/palette.test.mjs` (the manifest validates against the 1.6.0 manifest schema; the palette is what the generator writes). A row added to the table without its palette entry, or the other way round, fails both.

## Known limits

- **The presence event is on by default, and a real TAK Server 5.7 does not need it.** Checked by hand on 2026-10-19 against TAK Server 5.7-RELEASE-14 (plain TCP and TLS, with and without the event, and two restarts of the server): it accepts the event and answers with a pong (`t-x-c-t-r`), which the plugin counts as "not shown", and a client that has sent nothing receives all the same. The brief says to send it only if the real server needs it, so the default is the owner's call; switch it off with `sendPresence`. Not seen: a TAK Server or version that sends nothing until it has received an event, and a real ATAK or WinTAK client. The details are in `docs/handover/pca-cot.md`.
- **A TAK Server drops what it has seen** (checked on 2026-10-27 against TAK Server 5.7): an event that carries its own `<_flow-tags_>` element, such as one it relayed to us, is answered with "Duplicate message - already processed by this takserver" and not relayed again. So an input link and an output link to the same TAK Server, the output sending from the input's layer, do not loop: emc2 sends each real change once (as the status counts) and the TAK Server drops the copy. The flow tags are kept in what we send, so that a track relayed between two different TAK networks still gets the second network's tag; the comparison for "only real changes" leaves them out. The relayed echo differs from the original in nothing else but `@time`, which the server rewrites to whole seconds.
- **A TAK Server sets `@time` itself** (checked on 2026-10-29 against TAK Server 5.7, raw clients only): every event it relays carries the server's receive time, cut to whole seconds, whatever `@time` the sender wrote (an hour ago, a minute ahead); `@start` and `@stale` are left as sent. Two consequences. The rule "an event older by `@time` than the one applied is ignored" cannot protect against a late event that came through a TAK Server: it arrives as new, and the plugin applies it. And a removal (an event that is stale at once, with `@stale` equal to `@time`) reaches the receiver with `@stale` up to a second after `@time`, as `@time` is cut down and `@stale` is not.
- **WinTAK needs a dot as Windows' decimal symbol** (T-117; the ESA's sheet in `external/tak-server/README.md` says the same). A comma, the default of for example a Swedish Windows, does not work: set the decimal symbol in Windows' region settings (Additional settings) before using WinTAK with emc2's events or the ESA's TAK Server. Not checked by the plugin.
- **A write stall is judged per write, not per byte:** the worker sees which write (which event) is in progress, not how many bytes the peer has taken of it. One event that takes longer than `writeStallSeconds` to write counts as a stall, even from a slow peer; a slow peer is safe as long as each event is written inside the limit. The presence event that is written first on a connection of a `both` link is checked like any other write (owner, 2026-10-28, AE1), but a real peer can hardly block it: it is some 350 bytes written into an empty send buffer. **An `in` link is not checked** (AF1, AG1): its reader keeps receiving, and a restart would interrupt a working input; its presence write is not watched either. The warning of a stall shares the once-a-minute limit of the link's other warnings. A peer that stops reading is noticed after `writeStallSeconds` (see "Sending"); the first version of the plugin had no such check.
- **The status is cut at 512 characters** (the SDK's limit). The stored streams and the settings problems come first; with many links the end of the line, which holds the last links' `[direction transport where]` and warnings, is lost. The monitor view shows each task's counters (events in and out, skips by reason).
- **Static markers go stale in TAK** when `refreshSeconds` is 0 or longer than the stale time; the status warns. The simulator's tracks (channel items) are not refreshed by the link: the next item from the sender is the refresh, so the tracks of a paused simulation go stale in TAK.
- **The APP-6D and APP-6E table is closed and partial:** 147 rows (land units, equipment and installations, air, sea, subsurface, mines, a space entity), found by milsymbol's own icon parts. A symbol it lacks falls back to its parent entity, then to the dimension's generic symbol (`a-f-G`), so a rarer unit is sent with a coarser CoT type. A symbol set with no CoT dimension (control measures, activities, weather, cyberspace) is skipped ("no CoT type"). Shapes, routes and drawings are not sent.
- **Several links to the same TAK Server** see the same events. Each is its own data source, but a uid is one object that stays with the link that created it. Hiding that data source later (ADR-0023) therefore also hides tracks another link reports too.
- **No limit on addresses.** An administrator can point a link at any host and port, and make a UDP link listen on any address (SRA, T-046).
- **No limit on the number of objects.** A peer that sends endless new uids makes endless objects; ECore removes them only after their expiry. An event with no `@stale` never expires.
- **Events that are already long stale** are created and removed again by ECore (the plugin does not know the effective removal time). A TAK Server that sends its stale history on connecting makes this churn.
- **Events within one burst** are ordered by arrival (the latest wins), not by `@time`; the `@time` rule applies to what has been applied or is in flight.
- **TAK protocol version 1 (protobuf)**, a TCP server that TAK clients connect to, chat, tasking, drawings, routes and data packages are not supported. APP-6D and APP-6E symbols from CoT are not made (a received atom becomes an APP-6B symbol; an object that came from CoT keeps its type when it is sent again, while its symbol is unchanged).
- **A source layer's objects are held in the worker** (one map per layer, shared by the links that use it): a layer of 100 000 objects costs memory in proportion. Objects are sent paced, 5 000 a second, after a link comes up.
- **Multicast** needs an interface that carries it, which an administrator names; the loopback interface does not carry multicast on every platform. A multicast group joined on one interface also receives unicast datagrams sent to its port on this computer where the platform cannot bind to the group (Windows).
- **A UDP link that cannot bind** (the port is in use) is retried by ECore with the back-off, and the status shows the error.
- **Altitude** is the height above the ellipsoid, as CoT's `hae`; `ce` and `le` stay in the extension.
