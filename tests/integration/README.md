# tests/integration/

Integration tests of the combined system. Owner: ITA (`agents/ita.md`).

## Tools

- **Playwright Test** (`@playwright/test`, Apache-2.0, pinned in `package.json`) for browser tests and for HTTP and WebSocket API tests. One toolchain for both; dev-only, nothing here ships.
- **Chromium** only, installed by Playwright outside the repository (`%LOCALAPPDATA%\ms-playwright` on Windows, `~/.cache/ms-playwright` on Linux).
- JUnit is not used for now. Java ↔ TypeScript round trips and schema examples are covered by the PDA's codec contract test and the `model/` tests, which `node tools/test.mjs` runs.
- Own `package.json`, lock file and `node_modules`, like `model/`; not a workspace of the repository root's npm project (CR-0006). Install with `npm ci` in this folder, never at the root.

## Setup (once per machine)

```
cd tests/integration
npm ci
npx playwright install chromium
```

The browser download needs internet; the tests themselves do not. The test plugins and the test certificates also need the JDK's `javac`, `jar` and `keytool` on the PATH (JDK 25, the one that runs the server).

How a run uses the server (`lib/server.mjs`):

- `server/app/target/emc2-app.jar` with the `dev` profile, `--server.address=127.0.0.1` and `--server.port=0`: the server picks a free port and the runner reads it from the log, so parallel runs never race for a port.
- Fresh temporary `--emc2.data.directory` and `--emc2.plugins.directory` for every run and for every test that starts a server of its own, in `folders/` of the run's output folder (`lib/server.mjs`, `makeRunFolders`; `out/manual/folders/` for runs by hand). A passing test removes its folders; a failing one keeps them, and they go with its run when the run is pruned (owner, 2026-10-15: not in the system's temporary folder, where they piled up). After passing tests the runner fails the run if a test left a folder there. Folders of failed tests in runs by hand (`out/manual/folders/`) are not pruned: delete them when done. Nothing is written into the repository's tracked files.
- **Plugins:** every plugin that `tools/build.mjs` assembled into `build/plugins/` is copied into the run's plugin folder (`lib/plugins.mjs`). The template is never assembled, so it never runs.
- **No internet, also not from the server:** basemap-osm fetches its tiles from a **fake tile server** the runner starts on 127.0.0.1 (`lib/fake-tiles.mjs`: a PNG of one colour per zoom level, generated in Node). A run starts with each plugin's default settings, so the run's *copy* of basemap-osm's `plugin.json` gets `upstreamUrl` pointing at the fake server. Its `internet` declaration stays the plugin's own: since T-058 (ADR-0030) ECore no longer limits a server part to the declared hosts; the declaration is shown in the monitor. The plugin's own files are never changed. The real OpenStreetMap is never contacted.
- Stopped with `POST /api/dev/stop`; a graceful stop is `202` followed by exit code 0. Otherwise, or after 30 s, the process tree is killed and the run fails.
- **Ctrl+C, Ctrl+Break, SIGTERM or a closed console (SIGHUP)** to the runner: it stops Playwright (SIGINT to its process group on Linux, the process tree on Windows) or a server start in progress, stops the server, reports and exits with 130. A second signal kills everything at once.
- **Processes:** every child (build, Playwright, servers) runs in a process group of its own on Linux, so a kill reaches everything it started; on Windows the process tree is killed (`lib/processes.mjs`).
- **Servers started by tests** are recorded in the run's server registry (`servers/` in the run's output folder). After the tests the runner reports and kills every server a test did not stop, with its log and data folder, and fails the run (an interrupted run only reports). It kills a recorded pid only if that process still runs `emc2-app.jar`, since pids are reused. A test process that exits kills its servers too.
- If the server never logs its port (`Tomcat started on port …`), the start fails after 90 s with that message, not with a plain timeout.

The run passes only if the build, the server start, every test, the graceful stop, the checks for folders and servers left by tests and the **server log check** pass. The log check (`lib/log-check.mjs`) fails on Spring Boot `ERROR` lines, uncaught JVM errors, and `WARN` lines followed by a stack trace.

Output (not committed): every run writes into a folder of its own, `tests/integration/out/run-<UTC time>-<pid>/`, so parallel runs never share output. The newest 10 run folders are kept. In it: `server.log` of the shared server, the HTML report in `report/`, the temporary data and plugin folders in `folders/` (those of failed tests; beside them each server's `emcc/` folder, its working directory, with the empty `settings/terrain/` a release ships, so terrain's default `%emcc%/settings/terrain` is there: T-157, owner SB A), and in `test-results/` the logs of the servers that tests start themselves and the traces and screenshots of failed tests. The runner prints the folder at the start and the end.

Against a server you started yourself: `EMC2_BASE_URL=http://127.0.0.1:8080 npx playwright test` in this folder (no log check then; output in `out/manual/`).

## Quick run

T-063 (`agents/ita.md`, "Quick and full runs"; which run a merge needs: `agents/mca.md`, merge procedure, step 3). `lib/quick.mjs` decides, the same way every time:

1. **The paths:** `git diff --name-status <base-ref>...HEAD`, the changes since the merge base, as the merge brings them.
2. **The full run** (every suite, as without `--quick`) when one path needs it. Markdown files never do. These do:
   - `server/`, except a `server/pom.xml` diff that only adds `<module>../plugins/<id>/server</module>` lines;
   - `web/` (the shell, the web SDK, anything else there);
   - `model/`, `tools/`, any file at the repository root (`package.json` and `package-lock.json` included);
   - `tests/integration/` outside `specs/` and `fixtures/` (the runner, `lib/`, the configuration, the lock file), a file in `specs/` that is not a spec file, a fixture that is not in the mapping;
   - **any path the mapping below does not cover** (for example `spikes/`).
3. **Otherwise the quick run:** the `@always` spec files, plus what each path selects, without the tests tagged `@full`:

| Changed path | Selects |
|---|---|
| `*.md` anywhere, and any file in `docs/` or `documents/` | nothing more (other files of `agents/` or `.claude/` are not covered: full run) |
| `plugins/<id>/…` | the spec files with the area `@plugin-<id>` (none: only the `@always` files, which load every plugin) |
| `plugins/_template/…` | nothing more (the template is never assembled) |
| `server/pom.xml`, only `<module>` lines of plugins added | the area `@plugin-<id>` of each |
| `tests/integration/specs/<folder>/<name>.spec.ts` | that file (added or changed; a deleted one nothing) |
| `tests/integration/specs/performance/…` | nothing more (its own option, `--performance`) |
| `tests/integration/fixtures/plugins/ita-compute/…` | `limits/compute` |
| `tests/integration/fixtures/plugins/ita-limits/…` | `flows/m1-settings`, `harness/log-check`, `limits/caps`, `limits/compute`, `limits/sdk-version`, `limits/watchdog` |
| `tests/integration/fixtures/plugins/ita-listener/…` | `tak/listener` |
| `tests/integration/fixtures/plugins/ita-stream/…` | `flows/m8-streams`, `keycloak/streams`, `live/streams` |
| `tests/integration/fixtures/plugins/ita-probe/…` | `criteria/map-view-2d`, `criteria/selection`, `criteria/symbology`, `flows/m2-actions`, `flows/m2-bookmarks`, `flows/m2-objects`, `flows/m2-shapes`, `flows/m3-drag`, `flows/m3-sim-panels` |
| `tests/integration/fixtures/data/m0/…` | `live/persistence` |

**Areas.** Each spec file names its areas in its first line, `// Quick run: @plugin-cot @tak`; `specs/harness/quick.spec.ts` checks that every file has one with known areas. A new or changed spec file keeps the quick run (it runs itself); a new area or fixture is a change of `lib/quick.mjs`, so a full run.
- `@always`: `smoke/`, `offline/`, `server/` and the basic live picture API (`live/handshake`, `live/protocol`), plus `harness/quick`.
- `@plugin-<id>`: the specs of a plugin, its criteria and the flows that use it: basemap-osm (`criteria/basemap-osm`, `flows/draw`, `server/tiles`), basemap-naturalearth (`criteria/basemap-osm`, `flows/draw`), coordinates (`flows/coordinates`, `flows/m1-settings`), cot (`criteria/cot`), draw-symbols (`criteria/draw-symbols`, `criteria/selection`, `flows/draw`, `flows/edit`, `flows/layers`, `flows/two-browsers`, `keycloak/permissions`), layer-panel (`criteria/map-view-2d`, `flows/layers`, `keycloak/permissions`), map-view-2d (`criteria/map-view-2d`, `criteria/selection`, `flows/draw`, `flows/edit`, `flows/two-browsers`), symbology (`criteria/symbology`, `flows/draw`), draw-shapes and object-list (`criteria/selection`, until their own specs come with T-056).
- `@release`: `release/`, a built release zip (T-187). Its tools give the full run anyway (`tools/`), and it runs only where `EMC2_RELEASE_ZIP` is set.
- `@live`, `@persistence`, `@settings`, `@limits`, `@login`, `@tak`, `@harness`: the other areas. Today the paths that would select them (`server/`, `web/`) give the full run; they are named so that a finer mapping can use them later.

**`@full`:** a test too slow for the quick run's budget runs only in the full run: Playwright's tag (`test(title, { tag: '@full' }, …)`); the quick run passes `--grep-invert @full`. Today: map-view-2d criterion 22 (200 000 objects, 80 s) and the 600 000 cap of `live/subscriptions` (69 s).

**Budget:** about 3 minutes of integration tests (`agents/ita.md`). Measured (2026-10-16, `docs/test-reports/2026-10-16-run-times.md`): the `@always` files alone 30 s of tests (35 s with the runner, without the build); a change of coordinates 2.1 min, draw-symbols 2.6 min, map-view-2d 2.9 min, cot 2.3 min, basemap-osm 1.7 min; one changed spec file (`flows/coordinates`) 1.3 min. The full run's suite: 12.4 min. A branch that changes several plugins adds up their files; when a selection grows beyond the budget, a slow test gets `@full` or gets faster (the ITA proposes, the owner decides).

The Keycloak specs chosen by a quick run run as in any run: when the ESA's Keycloak runs, or with `--keycloak`.

**What the tool does not decide:** the MCA's other full-run cases (an integration branch that combines the branches of two or more roles, a milestone tag or demo, the sixth tested merge after five quick-only ones; `agents/mca.md`, step 3) depend on what the MCA merges, not on paths: `--explain` may say "quick" for such a branch, and the MCA still runs the full run. `--explain --head <ref>` reads the spec files' areas from the files checked out now, not from `<ref>`. `specs/harness/quick.spec.ts` checks past merges in `main`'s history, so it needs a clone with that history (not a shallow one).

**TAK test double** (`lib/tak-double.mjs`, T-043; for PCA-cot too). A stand-in for a TAK Server's CoT streaming input (TAK protocol version 0: XML events one after another). emc2's cot plugin connects to it as a client.
- **Transports:** plain TCP, or TLS that requires a client certificate signed by the test CA (`startTakDouble({ certs })`). `lib/test-certs.mjs` makes the CA, the server certificate (127.0.0.1, localhost) and the client certificate with the JDK's `keytool`, with random passwords, into the run's output folder; `listenerCredentialArgs(certs, name)` gives the server options `--emc2.listeners.credentials.<name>.*`. Nothing of it is committed.
- **Scripting:** `send(cotEvent({ uid, lon, lat, type, how, time, start, stale, callsign, remarks, course, speed, hae, ce, le, access, qos, opex, detail }))` (it refuses lat = lon, ADR-0007), `sendRaw(text)`, `stream({ rate, uids, seconds })`, `goAway()` (connections reset, port closed; `'reset'`: new connections reset at once, each attempt's time in `refused.times`, which shows a client's back-off) and `comeBack()` on the same port, `receivedText()` (what clients wrote: the presence event), `connections` (with the client certificate's name under TLS).

- **What clients send** (M3, T-086): `receivedEvents()` parses it (`parseEvents`: uid, type, how, times, position, callsign, course, speed, `__group`); `startTakDouble({ relay: 'others' })` passes each complete event on to the other clients, as a TAK Server does, and `relay: 'all'` to the sender too (an echo).
- **UDP and multicast peers** (`lib/udp-peer.mjs`, M3): `startUdpPeer()` on a free port of 127.0.0.1, or `startUdpPeer({ multicast: { group, address } })` as a member of a group on the run's multicast interface (`lib/multicast.mjs`); each records the datagrams it gets (`received`, `events()`) and sends one event per datagram (`send(event, { port })`). `freeUdpPort()` for a link that binds its port itself.
- **From the command line** (for checks by hand and PCA-cot): `node tests/integration/tak-double.mjs [--port N] [--tls] [--certs DIR] [--name NAME] [--script FILE] [--rate N --uids N --seconds N]`; it prints its port, the credential options and each connection. The script has one JSON object per line: `{"after": ms, "event": {…}}`, `{"raw": "…"}`, `{"hostile": "malformed" | "truncated" | "huge" | "externalEntity" | "entityExpansion"}`, `{"goAway": true | "reset"}`, `{"comeBack": true}`.
- **The cot brief's criteria and what the double offers:** 1, 2, 3, 5 `send` with the uid, position and times; 4 `detail` (a private element) and `how`, `ce`, `le`; 6 `hostile.*` and `entityRequests`; 7 `goAway('reset')` with `refused.times` for the back-off (1 s, doubling, at most 60 s), `comeBack`, two doubles for "another link"; 8 two doubles; 9 `certs`; 10 `stream({ rate: 1000, uids: 10000 })`; 12 no double at all; function 9 `receivedText()`.

**Geodesics** (`lib/geodesy.mjs`, `lib/GeodesyQuery.java`, M3; owner, 2026-10-29, Q5). The simulator moves along the Java SDK's `Geodesy`, so the tests check against the same SDK rather than a formula of their own: `inverse`, `distance`, `direct` and `along` (as `GeodesicPath.at`), positions [longitude, latitude]. The SDK's and GeographicLib's jars are taken from the built server jar with the JDK's `jar` (into the run's output folder, once per build; nothing is installed), and the query file runs with the JDK's single-file launcher, one `java` call per batch of queries.

**Login with Keycloak** (T-043; `lib/keycloak.mjs`, `lib/login.ts`, `keycloak-realm.mjs`). Keycloak is the ESA's external service (T-068; `external/keycloak/README.md`: Keycloak 26.8.0, port 8180, Windows only); the tests change nothing in its installation or its `keycloak.conf` and work only through its admin REST API, inside their own realm.
- **When they run** (T-069): without an option, `run.mjs` asks the service's status command (`node external/keycloak/status.mjs`, exit code 0 when healthy) whenever the run has login specs; when it runs, and with `--keycloak` in any case, it checks that Keycloak answers and the admin login works (a failure fails the run), then passes `EMC2_KEYCLOAK_URL` to the specs (default `http://localhost:8180`, or that variable when set). When Keycloak does not run, or with `--no-keycloak`, they are skipped and the run prints why. The rest of the suite needs no Keycloak and stays offline.
- **Admin credentials, never in the repository:** `EMC2_KEYCLOAK_ADMIN` and `EMC2_KEYCLOAK_ADMIN_PASSWORD`, or else the ESA's admin login for tests, `keycloak.json` in the service's credentials folder outside the repository (`admin.user`, `admin.password`; `credentials\keycloak\` under `EMC2_EXTERNAL_ROOT`). Without either, the login specs are skipped with the reason, as when Keycloak does not run; with `--keycloak` the run fails. Since T-069 the owner's `keycloak.local.json` is no longer read.
- **The test realm** (`createRealm`): made afresh before each spec file and deleted after it. A confidential client `emc2` with the standard flow, PKCE S256, the redirect, post-logout and back-channel logout URLs ("session required") of the test's server (set once its port is known), and a Group Membership mapper (`groups`, no full path, in the ID token). Groups `drawers`, `editors` and `admins`, mapped as in `server/README.md` plus the drawers (`objects.edit` to drawers, editors and admins, `layers.edit` to editors and admins, `settings.admin` to admins and setters). Users `ita-viewer` (no group), `ita-drawer` (drawers: `objects.edit` only, so that the two edit permissions are tested apart; owner, 2026-10-14), `ita-editor` (editors), `ita-admin` (admins) and `ita-setter` (setters: `settings.admin` only, the Settings workspace without `objects.edit`; T-175), among others, with random passwords. Keycloak events (login, logout, code exchange, renewal and their errors) are on: the tests read them as evidence.
- **Secrets:** the client secret is Keycloak's own, read after the realm is made, and reaches the server in its environment (`EMC2_LOGIN_OIDC_CLIENT_SECRET`), not on its command line. The passwords are random per realm. The browser types them into Keycloak's own login page, as a user would.
- **The login server** (`withLoginServer`): `startServer({ login: true })` starts the jar without the `dev` profile, so in the login mode (`emc2.login.mode=oidc`). It has no stop endpoint (`dev` only), so it ends with a hard kill; its log is still checked. Browser contexts may reach the server, and Keycloak only for page navigations and the pages Keycloak serves; anything else fails the test, and so do console errors on emc2's pages. A Node live picture client with login sends the session cookie and the server's own `Origin` (with login the handshake needs a browser's `Origin`).
- **For checks by hand** (CDA, PCAs, the owner): `node tests/integration/keycloak-realm.mjs setup [--realm emc2] [--server http://localhost:8080]` makes the same realm (issuer `http://localhost:8180/realms/emc2`, as in `server/README.md`) for a server at that address, and writes the server's login settings with the client secret, and the users' passwords, to `tests/integration/keycloak-<realm>.local.properties` (ignored by git; nothing secret is printed). Use it as `application-local.properties` with the profile `local`. `teardown` deletes the realm and the file. `setup` leaves an existing realm of that name alone; `setup --force` makes it afresh with new secrets. Keycloak's own realm `master` is refused. The realm is a test realm, not the lasting demo realm (T-061).
- **Not tested here:** Keycloak unreachable (the `503` path; that would mean stopping the ESA's Keycloak; the CDA's tests cover it with their `FakeIam`), the user cancelling at the IAM (Keycloak's login page has no cancel), HTTPS, a reverse proxy.

**Test probe.** `fixtures/plugins/ita-probe/` is a test-only plugin: a plain ES module (no build) that gets services through the SDK like any plugin and hands them to the test as `window.__itaProbe` (the SymbolService and the MapView: `pick`, `viewport`, `goTo`, `selection`, `dragObject`). It is installed only into the servers of tests that ask for it (`withM0(..., { probe: true })`), never assembled and never shipped.

**Independent projection maths.** `lib/projections.mjs` writes out EPSG:3857 and EPSG:3413 (Snyder's polar stereographic on the WGS84 ellipsoid) without OpenLayers or proj4. The map-view criteria fit a scale and offset to the two symbols drawn farthest apart and require every other symbol within 1.5 px; colour centres use pixel centres (index + 0.5) of the largest connected patch of the colour.

**What the M0 helpers can simulate** (`withM0` options): the probe; basemap-osm's upstream unreachable (`upstream: 'unreachable'`: the fake tile server resets every connection and keeps its port); a slow upstream (`tiles.setDelay(ms)`); console errors a test expects (`allowConsoleErrors`); a setup step before the app loads (`open(beforeLoad)`, e.g. to capture requests or WebSocket frames); a clean restart of the server on the same folders (`restart()`; pages opened before keep the old address); a page that has not picked a coordinate format (`open(beforeLoad, { pickFormat: false })`), so it follows the coordinates plugin's `defaultFormat`.

**Timing criteria depend on the machine.** Several tests assert wall-clock limits from the plugins' briefs: symbology 5 (median of five runs; measured here 17–37 ms for 120 renders against 100 ms, 10–20 ms for 100 000 cached lookups against 50 ms), draw-symbols 1 and map-view-2d 2 (second browser within 1 s; measured 170–630 ms, upper bounds that include the screenshots). The cot criteria bound times too: criterion 1 (shown in two browsers within 2 s of the event, upper bounds with the screenshots) and criterion 7 (the next tries 1 s after the loss, then 2, 4 and 8 s apart, within 1.2 s, read from the plugin's status to the second). The protocol v2 area-query test (`subscriptions.spec.ts`) also bounds times: the first four answers within 700 ms of each other, the fifth at least 700 ms after the first, all eight within 5 s. They passed also with the CPU at 100 % from another session's build. On a much slower machine they can fail; then it is the machine or the plugin, and the measured values in the test's annotations tell which. The performance criteria proper (map-view-2d 8 and 9) are measured, not asserted (below).

**The performance suite** (`specs/performance/`, `lib/load.mjs`, `lib/perf.ts`). Each case runs on a server of its own with the probe.
- **Load:** a Node client (`LoadClient`) sends the change requests over `/api/live` like any client, with at most 80 waiting. It does not subscribe and keeps only counts, so 100 000 objects cost the test process little. Since T-039 each case first raises the map view's object budget to 100 000 through its settings (owner, 2026-10-12), so the map view draws the objects one by one as criteria 8 and 9 describe, not clusters; and the map view gets only the objects in its area. The objects are APP-6D units in 24 appearances, each with a unique designation and a direction, on a grid over the visible area ("in view") or over an area 4 × 3 times as large ("spread"). The stream moves objects chosen by a seeded random generator, 1 000 per second in ticks of about 10 ms, and records the rate it reached and the changes it skipped.
- **When the load has reached the map view:** five sentinel objects, created last at pixels whose positions the cursor display gave, are looked for with `MapView.pick` from the page's start. That is the map view's data; when the pixels show is not measured.
- **Measuring** goes through Chromium's DevTools protocol (Playwright's CDP session): frames from `requestAnimationFrame` (fps, gaps), the main thread's busy share (`Performance.getMetrics` `TaskDuration`) and long tasks, the heap after a garbage collection, JavaScript CPU profiles, and a Chromium trace of the main thread for what the profile shows only as "(program)".
- **Playwright's trace is off** in this suite: it snapshots the page, the map's canvas included, at every mouse action, which alone cost hundreds of milliseconds per step.
- A case fails only when something does not work (an object missing, a console error, a refused or lost change, the page's live picture connection closed). The results are JSON files in the run's `performance/` folder; `performance-report.mjs` makes the tables.
- It runs in Playwright's headless Chromium shell. The full Chromium build would not start on the ITA's machine (`spawn UNKNOWN`), so headed or full-browser numbers are not available here.

**Known behaviour reported to the owner (2026-10-09), not encoded as an expectation:** two clicks within OpenLayers' double-click time zoom the map in one level (also 120 px apart, also outside placing), and while placing each of them creates a symbol. The tests click at a user's pace (600 ms apart) where this matters.

The live picture tests use `lib/live.mjs` (a client on Node's built-in WebSocket speaking protocol version 2: `subscribe()` opens the whole picture as `all`, `subscribe({ id, objects, area, resolution, budget })` any subscription, `moveArea`, `eventsOf(id)`, `waitForSequence(n, timeout, id)`, `boxArea`; raw handshakes, `Host` headers, test objects) and `lib/raw-socket.mjs` (a minimal client that can stop reading). Nothing extra is installed.

**Limits not tested, because a client cannot reach them deterministically:** the 2 Mi character inbound budget (close 1008) depends on how fast the session works through the messages; 60 bursts of 1 MiB messages never reached it, while one burst of 50 large valid change requests did. Whether more than 100 change requests wait for the store depends on the store's speed; the flood test therefore checks the kinds of answer (applied, or rejected with `INTERNAL_ERROR`), not that a rejection happens. Tests that send large messages keep below 2 Mi characters in flight.

Tests that need a server of their own (other folders, restarts) use `withOwnServers` from `lib/own-server.ts`: fresh folders, a `start` function for servers on them, every server stopped at the end, and the folders removed after a pass or a known fault's expected failure (`test.fail`), or kept and named (annotation and console) after any other failure. `stopOwnServer` requires a graceful stop and a clean log.

A test for a feature that is not delivered yet is written as `test.fixme` and names its task. It is switched on when that task merges.

## Rules

- Deterministic: no retries (`retries: 0`). A flaky test is a bug in the test.
- No fixed sleeps: wait for a condition (polling with a deadline is fine). Pauses that set a user's pace (clicks 600 ms apart, the steps of a pan or a drag) are not waits for a condition and are allowed. So is a window of a few seconds where a test must show that something does not happen or has settled (protocol v2: fewer area answers than moves; the map view's items no longer changing at the widest zoom).
- One worker for now; the shared server is used by all tests of a run.
- The smoke and offline suites must stay fast (seconds, plus the build). The whole run takes about a minute plus the build.

## Known limits

- **A runner killed hard** (`taskkill /F`, SIGKILL) runs no cleanup. On Windows its servers end with it anyway: Node puts its children into a job object that Windows closes with the process (checked 2026-10-08). On Linux they are detached and stay running. On Windows a signal from another process also ends Node at once, so there the handling only runs for a real Ctrl+C in a console (which also reaches the server directly).
- **The Linux paths** (process groups, SIGTERM to the runner alone) are written but untested.
- **Linux is untested** (owner, 2026-10-07): no Linux environment available to the ITA.
- The offline guard sees requests made by pages and their dedicated workers. Service workers are blocked by the configuration. Requests the browser makes on its own (updates, telemetry) are not the application's and are not checked.
